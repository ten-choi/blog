> The index found the row — great. Now the real bill arrives: **going to the table to fetch it.** This part is about paying that bill as rarely as possible, and about stopping early when you can.

# 3.1 Minimizing Table Access and Partial Range Processing

This part opens Chapter 3 — Index Tuning.

## 3.1.1 Minimizing table access

- **Index ROWID**

  - An index ROWID is a **logical address**.
  - It is **not the same thing as a physical pointer** in memory.
  - Table access via ROWID is a **more expensive operation than you'd think**.

- The more that rows sharing the same value for a given column are **physically stored close together** (= the better the clustering factor of the column you index), the faster data lookup becomes.

- The moment the amount of data you need to read crosses a certain threshold (= the **index break-even point**), **an Index Range Scan actually becomes slower than a Table Full Scan**.

  - Because a Table Full Scan is **sequential access**, while table access via index ROWID is **random access**.
  - Because a Table Full Scan uses **multiblock I/O**, while table access via index ROWID uses **single-block I/O**.

- The index break-even point shifts depending on the **index Clustering Factor (CF)**.

  - The better the CF, the **further back** the break-even point moves.
  - In other words, **if you build the index on a column whose equal values are stored physically close together**, an Index Range Scan is less likely to fall behind a Table Full Scan even when fetching lots of data.

- **Adding a column** to an existing index can reduce table access.

  - For example, say a table has an index on `(a, b)` and we run this query:

  - ```sql
    select *
    from table_name
    where a = 30 and c >= 2000;
    ```

  - Add column `c` to the existing index to make it `(a, b, c)`, and **the amount of index scanned stays the same** but **the amount of table access goes down**.

- The case above is tuning for when the `WHERE` clause filters out a lot of rows. So what about when **almost nothing gets filtered out**?

  - For example, the query below filters out almost no records (assume an index exists on the department number):

  - ```sql
    select dept_no, sum(quantity)
    from sales_summary
    where dept_no like '12%'
    group by dept_no;
    ```

  - In cases like this, you can tune it so that table access never happens at all by **including every column the query uses (quantity, here) in the index**.

  - A query where **all the required columns are contained in the index, so it's answered from the index alone**, is called a **covered query**, and that index is called a **covering index**.

  - The payoff is great, but **it often becomes impractical when the number of columns to add grows too large**.

## 3.1.2 Making the most of partial range processing

- With **partial range processing**, you can get a **blazing-fast response time** no matter how many records the index would eventually touch.
- Instead of fetching everything up front, the client **requests a fixed amount (the array size) per fetch call** and processes it piece by piece.
- Partial range processing is only meaningful **if the database can stop early**.
  - If there's a step that has to read *everything* and sort it, **the database can't emit just the first few rows**.
  - You need to **build the index so that reading and returning just the front portion is enough**.

### The Top-N query pattern

Queries of the "**most recent / top / most popular N rows**" flavor are the textbook use case for partial range processing.

```sql
-- The 20 most recent orders
SELECT * FROM orders
ORDER BY created_at DESC
LIMIT 20;                                   -- MySQL / PostgreSQL

SELECT * FROM orders
ORDER BY created_at DESC
FETCH FIRST 20 ROWS ONLY;                   -- Oracle 12c+

SELECT * FROM (
  SELECT * FROM orders ORDER BY created_at DESC
) WHERE ROWNUM <= 20;                       -- Older Oracle (inline view required)
```

- With an index on `(created_at)`, the optimizer does a **descending index scan**, **reads only the first 20 rows, and stops**.
- Whether the table has 10 thousand rows or 100 million, **the response time stays almost constant**.

(We'll revisit this exact pattern from the sort side in Part 5.3.)

### Pagination — beware the OFFSET anti-pattern

Pagination is the case people get wrong most often in real-world code.

```sql
-- ❌ Anti-pattern (OFFSET-based)
-- Page 100 (20 rows per page): OFFSET 2000 LIMIT 20
SELECT * FROM orders
ORDER BY created_at DESC
LIMIT 20 OFFSET 2000;
```

- `OFFSET 2000` means **reading the first 2000 rows and throwing them away**, then returning the next 20.
- The deeper the page, the more you **read-and-discard — and it grows linearly** → later pages get slower and slower.
- Page 100 might be tolerable, but **page 1000 is a disaster**.

```sql
-- ✅ Cursor-based paging (Keyset Pagination)
-- When requesting the next page, pass "the last created_at value of the previous page" as a condition
SELECT * FROM orders
WHERE  created_at < :last_seen_created_at
ORDER BY created_at DESC
LIMIT 20;
```

- Every page performs **consistently, regardless of how many rows came before it**.
- A single index can cover every page.
- Downside: **you can't jump to an arbitrary page N** — only sequential navigation (perfect for infinite scroll / feeds).

### When partial range processing doesn't work

```sql
-- ❌ ORDER BY needs a full sort → can't read just the first N rows
SELECT * FROM orders ORDER BY total_amount DESC LIMIT 20;
-- (Without an index on total_amount, the whole set must be sorted first)

-- ❌ GROUP BY / aggregation means you can't stop early
SELECT dept, SUM(sal) FROM emp GROUP BY dept LIMIT 5;

-- ❌ DISTINCT also requires scanning everything
SELECT DISTINCT category FROM products LIMIT 10;
```

- Once aggregation, sorting, or deduplication is involved, **"look at the front and stop" no longer holds**.
- In those cases, you need a strategy: **design an index** that lets the database skip the aggregation/sort, or **maintain a separate results table**.

---

### 📝 One-line takeaway

> **"Table access via ROWID is expensive random I/O — so either shrink it with a covering index, or design the index so the database can stop after the first N rows."**
