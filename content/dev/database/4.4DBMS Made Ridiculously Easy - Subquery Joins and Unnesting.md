> Syntactically, a subquery is just "a query inside a query" — but from the optimizer's point of view, most of the time it ends up being resolved as **just another form of join**.

# 4.4 Subquery Joins and Unnesting

From here on, the category shifts: **"a query inside a query"** is different territory from the NL / Sort Merge / Hash joins we've covered so far — yet the optimizer usually **unwinds a subquery into a regular join** and executes it as one of those three.

## 4.4.1 The three types of subquery

| Type | Location | Example |
|---|---|---|
| **Inline view** | `FROM` clause | `FROM (SELECT ... FROM emp) x` |
| **Nested subquery** | `WHERE` clause | `WHERE dept_id IN (SELECT id FROM dept WHERE ...)` |
| **Scalar subquery** | `SELECT` clause | `SELECT name, (SELECT ... FROM dept WHERE ...) FROM emp` |

## 4.4.2 Subquery Unnesting

> **Unnesting** = the optimizer's query-transformation technique that **flattens** a subquery into a join.

```sql
-- Before transformation: nested subquery
SELECT * FROM emp e
WHERE dept_id IN (SELECT id FROM dept WHERE loc = 'SEOUL');

-- After transformation (Unnesting): flattened into a join
SELECT e.* FROM emp e, dept d
WHERE e.dept_id = d.id AND d.loc = 'SEOUL';
```

**Why unnest?** Once it's a join, the optimizer is **free to choose the join order and the join method (NL/Hash/Merge)** — a much better position to be in.

## 4.4.3 What if Unnesting can't happen?

The subquery falls back to the **Filter method**, where it is **executed once for every row of the outer query**.

```
Outer query row 1 → run the subquery
Outer query row 2 → run the subquery
Outer query row 3 → run the subquery
...
```

→ This is the **worst-case version of an NL join** (N outer rows × the subquery's cost). If the subquery has no index, it's a full-blown disaster.

## 4.4.4 Nested subqueries: EXISTS vs IN

| Form | Meaning | Characteristics |
|---|---|---|
| `IN (subquery)` | Is the value in the set? | Tries to materialize the entire subquery result |
| `EXISTS (subquery)` | Just checks existence | **Returns true the moment it finds one match** → great for partial range processing |

> For large-volume queries where you "only need to check existence," **`EXISTS` wins**. It's also easy for the optimizer to resolve as a Semi-Join.

## 4.4.5 Scalar subqueries and caching

```sql
SELECT e.name, (SELECT d.name FROM dept d WHERE d.id = e.dept_id) AS dept_name
FROM emp e;
```

- A scalar subquery makes use of a **result cache (the Scalar Subquery Cache)**
- For the same input value, it doesn't query again → **the more duplicate values, the more efficient it is**
- ⚠️ But once you exceed the cache capacity, it falls back to repeated execution → **with high cardinality it actually becomes poison**

## 4.4.6 Inline views and View Merging

```sql
-- inline view
SELECT * FROM (
  SELECT dept_id, COUNT(*) cnt FROM emp GROUP BY dept_id
) x
WHERE x.cnt > 10;
```

When the conditions are right, the optimizer **merges the view into the main query** so it can optimize more freely. Note, though, that **when the view contains aggregation or sorting, merging is sometimes impossible**.

---

### 📝 One-line takeaway

> **"The happy path is for the optimizer to turn your subquery into a join via Unnesting — when that's blocked, the Filter method kicks in and performance goes off a cliff."**

- `EXISTS` checks existence, `IN` compares against a set — they differ in both meaning and performance.
- Scalar subqueries are efficient thanks to the **result cache**, but backfire when there are many distinct keys.
- With inline views, keep aggregation and sorting to what's strictly necessary so **View Merging** stays possible.
