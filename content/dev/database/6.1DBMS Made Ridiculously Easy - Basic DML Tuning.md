## 6.1.2 Indexes and DML performance

### (1) INSERT
When you insert a record into a table, you also have to insert it into **every index** on that table.

An index is a sorted data structure, so the database must perform a **vertical traversal** to find the block where the new entry belongs.

<img width="800" src="https://user-images.githubusercontent.com/60383031/149665948-c000f581-9400-428b-9bed-714cca50e58d.jpeg">


### (2) DELETE
When you delete a single record from a table, the database has to **find and delete the matching entry in every index**.

### (3) UPDATE
Only the indexes that reference the **changed columns** need to be touched.

The catch: for each row changed in the table, the index sees **two operations** — a delete and an insert.

Example) Change A → K: the value's storage position inside the index moves.

## 6.1.3 Integrity constraints and DML performance
Constraints like PK, FK, Check, and Not Null *could* be enforced directly in the application, but **letting the DBMS enforce them guarantees data integrity far more completely**.

Just remember that they come with a **trade-off against performance**.

PK and FK validation is the expensive part, because verifying them **requires actually querying the existing data**.


## 6.1.4 The WHERE clause and DML performance
UPDATE / DELETE is ultimately a two-step job: **"first find the target records, then change them."**

- The cost of finding the rows to change is governed by exactly the same things as **SELECT performance**: the **WHERE clause + indexes**.
- In other words, if the `WHERE` condition can't use an index, you're already slow at the **"finding" step** — before any changing even begins.
- In large UPDATE/DELETE jobs, it's common for the **I/O cost of locating the target rows** to eat more than half of the total runtime.

> 💡 **Tuning point**: When an UPDATE is slow, don't stare only at the UPDATE. **Making the equivalent `SELECT ... WHERE` fast first** is the fix in most cases.


## 6.1.5 Subqueries and DML performance
Subqueries inside DML are everywhere: `INSERT ... SELECT`, `UPDATE ... WHERE col IN (SELECT ...)`, `MERGE`, and so on.

- You should assume the subquery's execution plan **determines the performance of the entire DML statement**.
- If the subquery resolves as a **Filter operation** that re-executes for every row, it's a disaster → you need to **steer it toward Unnesting** so it resolves as a join.
- In bulk-load situations like `INSERT ... SELECT`, the subquery side accounts for most of the I/O, so **tuning the subquery *is* tuning the DML**.

> 💡 Subquery join optimization is covered in detail in [Part 4.4 — Subquery Joins and Unnesting](<./4.4DBMS Made Ridiculously Easy - Subquery Joins and Unnesting.md>).


## 6.1.6 Redo logging and DML performance
### The Redo log
Oracle records **every change made to data files and control files in the Redo log**.

The Redo log is used to **replay transactions and restore the database to its pre-loss state** when transaction data is lost.

Since every DML operation must generate Redo, it affects performance.

The one exception: for INSERT specifically, Redo logging can be **skipped** (Direct Path Insert, etc. — that's Part 6.2's topic).

### What the Redo log is for
**(1) Database Recovery**

Used to recover from **media failures** — e.g., a disk physically dying.

**(2) Cache Recovery**

The buffer cache exists to boost I/O performance, but it's **volatile**.

When the instance shuts down, the buffer cache is gone — the Redo log is what restores it.

**(3) Fast Commit**

Changes are first quickly written to the log file in **append mode**, and the actual synchronization between memory buffer blocks and data file blocks is handled later, in batches, by the **DBWR (DB Writer) and Checkpoint processes**.

> 💡 Writing a modified memory buffer block down to its disk data block is **random access** — very slow. That's why Redo takes the fast path: **append (sequential write) the log now**, defer the real write to disk until later.

## 6.1.7 Undo logging and DML performance
Undo is the log used to **roll a transaction back — turning the present back into the past**.


<img width="800" src="https://user-images.githubusercontent.com/60383031/149776429-55b098c8-7cde-426e-b177-1f493167b2a7.png">

Every time Oracle **inserts, updates, or deletes** data, it leaves a record in an Undo segment.

### What the Undo log is for
**(1) Transaction Rollback**

Used when a transaction's changes are **rolled back** instead of committed.

**(2) Transaction Recovery**

Once the Redo-based roll-forward phase finishes, **even uncommitted changes have been restored**.

So the transactions that were still uncommitted at shutdown have to be rolled back again — and **that's where Undo comes in**.


**(3) Read Consistency**

Used to guarantee **read consistency** for queries (the heart of MVCC).

### The MVCC model (Multi-Version Concurrency Control Model)
**(1) Current mode**

Reads the **original (current) block, exactly as it is right now**, loaded from disk into the cache.


**(2) Consistent mode**

When the reader hits a block that another transaction has modified, it makes a **copy of the original block** and **applies Undo data to it**, reconstructing "how the data looked at a past point in time."


<img width="800" src="https://user-images.githubusercontent.com/60383031/149789962-6452c001-b8c5-4a55-87db-ca3960454cc7.png">


**※ SCN (System Change Number)**

A **global variable** holding the point in time of the most recent commit.

**※ Block SCN**

To track when each block was last changed, an **SCN is recorded in every block header**.

**※ Query SCN**

Every query **checks the global SCN first** before it starts reading. That value is called the "query SCN."

**※ Putting it together**

Consistent mode reads data by **comparing the query SCN against each block's SCN**, checking whether the block was changed while the query was running.

If it hits a block whose **block SCN is greater than the query SCN** → it makes a copy of the block and applies Undo, rewinding it to **how it looked when the query started**.

**Where you read from changes depending on the transaction isolation level!**

- **READ_UNCOMMITTED**: reads straight from the InnoDB buffer pool or the data file → it reads the value whether it's committed or not
- **Any level above that**: reads from the Undo area


**※ Example recap**

Run the UPDATE query → the InnoDB buffer pool is changed to the new data immediately, and **the old data is copied into the Undo area**.

COMMIT at this point → InnoDB makes no further changes and **finalizes the current state as permanent data**.

Roll back instead → the **backup data in the Undo area is restored into the InnoDB buffer pool**, and the Undo contents are discarded.

## 6.1.10 Commits and DML performance
A commit isn't just a "finalize the change" command — it's a **heavy operation that comes with physical I/O and log writes**.

- At commit time, the **Redo log buffer is flushed to the on-disk Redo log file** (LGWR) → **synchronous disk I/O**
- At commit time, **Undo segments are cleaned up** and block-header SCNs are updated
- Commit too often?
  - Repeated Redo log file writes cause the **"log file sync" wait event**, dragging down overall throughput
  - Example: a 1-million-row loop that **commits every single row** → 1 million file I/Os
- Commit too rarely?
  - **Undo segment bloat** and the dreaded **ORA-01555 (Snapshot too old)** error
  - Long-running transactions → **blocking** for other sessions

> 💡 **Real-world guide**
> - For large batches, commit in **chunks of thousands to tens of thousands of rows** (batch commit)
> - For OLTP transactions, commit only at **business-unit boundaries** (preserve atomicity)
> - "Committing every row because it feels faster" — the **anti-pattern** you'll run into most often
