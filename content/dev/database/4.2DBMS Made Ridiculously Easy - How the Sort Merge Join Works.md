# 4.2 How the Sort Merge Join Works

## 4.2.1 How the sort merge join works

The idea: **sort each table by the join key**, then **sweep both sides sequentially and match them up**.

**The steps**

1. **Sort phase** — sort table A and table B, each by the join key (using the Sort Area in the PGA)
2. **Merge phase** — advance a cursor on each side simultaneously, matching rows whose join keys are equal

```
Table A (sorted by key)      Table B (sorted by key)
[1, 3, 5, 7]                 [1, 2, 3, 5, 9]
       ↓ advance both cursors together ↓
Match: 1, 3, 5
```


**Forcing a sort merge join with hints**

```sql
SELECT  /*+ ORDERED USE_MERGE(B) */
        A.*
      , B.*
FROM    ITEM A
      , UITEM B
WHERE A.ITEM_ID     = B.ITEM_ID         -- (1) join condition
AND   A.ITEM_TYPE_CD = '100101'         -- (2) filter condition on A
AND   A.SALE_YN      = 'Y'              -- (3) filter condition on A
AND   B.SALE_YN      = 'Y'              -- (4) filter condition on B
;
```

What the hints mean:

- `/*+ ORDERED */` — a hint that says **join the tables in the order they appear in the FROM clause**. In the example above, the order is pinned to `ITEM A` → `UITEM B`.
- `/*+ USE_MERGE(B) */` — a hint that says use the **Sort Merge Join method** when joining `B`. The optimizer won't pick NL or Hash on its own — it's locked to Sort Merge.

What the conditions do:

- **(1)** the **join condition** that ties the two tables together on `ITEM_ID` (this becomes the sort key for the Sort Merge)
- **(2), (3)** **filter conditions** that shrink the `ITEM` side only (applied before sorting, they lighten the load on the Sort Area)
- **(4)** a **filter condition** on the `UITEM` side

> 💡 For a Sort Merge to pay off, it's important to **apply the filter conditions first so the sets being sorted are as small as possible**. A query like the one above — with filters on both sides — is the textbook shape for a Sort Merge.

## 4.2.2 How it differs from the NL join

| Aspect | NL join | Sort merge join |
|---|---|---|
| **Join method** | Compare one row at a time (random access) | Sort, then match sequentially |
| **Driving/driven** | Driving table matters a lot | Weak notion of "driving" (both sides get sorted) |
| **Index dependence** | High (driven table needs an index) | Low |
| **Upfront cost** | Small | Large (sorting cost) |

## 4.2.3 When the sort merge join wins

- When there's **a lot of data to join** and **the driven table has no suitable index**
- When you're joining **sets that are already sorted** (the Sort phase can be skipped)
- **Non-equi joins** — join conditions like `BETWEEN`, `>`, `<`
  → Since the hash join only supports equality joins, this is exactly where the sort merge shines

## 4.2.4 Limits of the sort merge join

- **Sorting is expensive** — the more data, the heavier the PGA load (worst case, it spills to disk Temp)
- **If the sort can't finish in memory**, it switches to a disk sort → perceived performance falls off a cliff
- These days the **hash join is faster in most cases** → sort merge is a niche tool for things like "joins that aren't equality joins"

## 4.2.5 Field notes

> MySQL traditionally **does not support the sort merge join** (this is an Oracle/PostgreSQL concept).
> To get a similar effect in MySQL, the key strategy is to design so that **an index already provides the sort order**, avoiding unnecessary sorts.

---

### 📝 One-line takeaway

> **"Sort merge join = sort both sides, then sweep them once."**

- It wins when the driven table has no index, or when the join is non-equi.
- In practice it's rarely chosen over the hash join — but **you have to understand how it works before the hash join's strengths come into focus**.
