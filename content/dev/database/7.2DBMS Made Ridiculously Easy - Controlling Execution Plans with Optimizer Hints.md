# 7.2 Controlling Execution Plans with Optimizer Hints

## 7.2.1 Why hints exist

The optimizer finds the **optimal execution plan** most of the time, but it gets it wrong in cases like these:

- When the **statistics are stale or inaccurate**
- When the **data distribution differs from the optimizer's assumptions** (missing or insufficient histograms)
- When **bind variables throw off the cardinality estimate** (the Bind Peeking issue)
- When a **complex join has so many possible combinations** that the optimizer gives up

In those cases, a hint lets you **pin the execution plan**.

## 7.2.2 Hint syntax

```sql
SELECT /*+ hint_name(options) */ columns FROM table ...
```

- Written in the `/*+ ... */` form, **immediately after SELECT/INSERT/UPDATE/DELETE**
- A typo or invalid hint **doesn't raise an error — it's simply ignored** (it fails silently) → **verification matters**

## 7.2.3 Commonly used hints (Oracle)

**① Controlling the access path**

| Hint | Meaning |
|---|---|
| `FULL(t)` | Force a Full Scan of table t |
| `INDEX(t idx)` | Use index idx on table t |
| `INDEX_DESC(t idx)` | Scan the index in descending order |
| `NO_INDEX(t idx)` | Don't use a specific index |

**② Controlling the join method**

| Hint | Meaning |
|---|---|
| `USE_NL(t)` | NL join with t as the inner (driven) table |
| `USE_HASH(t)` | Hash join with t as the inner (driven) table |
| `USE_MERGE(t)` | Sort merge join |

**③ Controlling the join order**

| Hint | Meaning |
|---|---|
| `LEADING(t1 t2 t3)` | Fix the join order as t1 → t2 → t3 |
| `ORDERED` | Join in FROM-clause order (old-school) |

**④ Controlling query transformation**

| Hint | Meaning |
|---|---|
| `UNNEST` / `NO_UNNEST` | Allow/block subquery Unnesting |
| `MERGE` / `NO_MERGE` | Allow/block view merging |
| `PUSH_PRED` | Push a predicate down into the view |

**⑤ Others**

| Hint | Meaning |
|---|---|
| `APPEND` | Direct Path INSERT |
| `PARALLEL(t, 4)` | Parallel processing (DOP = 4) |
| `GATHER_PLAN_STATISTICS` | Collect actual runtime statistics during execution |

## 7.2.4 Hints in MySQL

MySQL's hints are simpler than Oracle's, but the core idea is the same.

```sql
-- Forcing an index
SELECT * FROM emp USE INDEX (idx_dept) WHERE dept_id = 10;
SELECT * FROM emp FORCE INDEX (idx_dept) WHERE dept_id = 10;
SELECT * FROM emp IGNORE INDEX (idx_dept) WHERE dept_id = 10;

-- Optimizer hints (MySQL 5.7+)
SELECT /*+ INDEX(emp idx_dept) */ * FROM emp WHERE dept_id = 10;
SELECT /*+ NO_INDEX_MERGE(emp) */ * FROM emp WHERE ...;

-- Join order
SELECT /*+ JOIN_ORDER(a, b) */ * FROM a, b WHERE ...;
```

## 7.2.5 When you should NOT use hints

> 💬 Hints are a **"last resort."** Work through this order first.

1. **Refresh the statistics first** — `DBMS_STATS.GATHER_TABLE_STATS` / MySQL's `ANALYZE TABLE`
2. **Rewrite the query** — reshape subqueries/joins so the optimizer can solve them well
3. **Redesign the indexes** — the index you truly need might simply not exist
4. **If none of that works, then a hint**

## 7.2.6 The dangers of hints

- **When the data distribution changes, the hint becomes the wrong choice** — the hint is frozen, but the data keeps moving
- **It blocks future optimizer improvements** — even after a DB version upgrade, you're stuck with the old plan
- **The "ghost hint" problem** — a typo gets silently ignored with no error → always verify with the execution plan

## 7.2.7 How to verify a hint was applied

```sql
-- Oracle
EXPLAIN PLAN FOR SELECT /*+ ... */ ...;
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);

-- MySQL
EXPLAIN SELECT /*+ ... */ ...;
EXPLAIN FORMAT=JSON SELECT /*+ ... */ ...;
```

> Once you've added a hint, **always confirm it took effect via the execution plan**. It may have been silently ignored.

## 🔑 Key points from this part

- A hint = a comment that tells the optimizer **"follow my judgment instead"**
- Fix the statistics/query/indexes first, and reach for a hint **only if that fails**
- Typos are ignored without errors → **always verify with the execution plan**
- The hint is frozen, the data changes → over the long run it can become technical debt

---

### 📝 One-line takeaway

> **"A hint is a last resort, not a first move — fix the statistics, the query, and the indexes first, and if you do pin the plan, verify it in the execution plan and remember that frozen hints age into technical debt."**
