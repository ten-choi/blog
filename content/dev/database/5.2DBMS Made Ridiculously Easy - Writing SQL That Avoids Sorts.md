# 5.2 Writing SQL That Avoids Sorts

In [Part 5.1](<./5.1DBMS Made Ridiculously Easy - How Sorting Works and Memory vs Disk Sorts.md>) we saw that **a sort is fundamentally a heavy operation**. This part is about techniques for **eliminating sorts — or making them lighter — at the SQL level**.

---

## 5.2.1 Union vs Union All

```sql
-- Union       → sorts internally to remove duplicates
-- Union All   → simple concatenation, no sort
```

- **Union**
  - The optimizer performs a sort to **remove duplicates** between the top and bottom sets
  - With lots of data, it can drop straight into a disk sort
- **Union All**
  - A **simple concatenation** with no duplicate checking
  - If the two sets are **guaranteed to be mutually exclusive**, Union All is the right answer

> 💡 If you wrote it with UNION but "the two sets can never overlap," then **just switching to UNION ALL makes the sort disappear**.

---

## 5.2.2 Distinct vs Exists

```sql
-- Distinct — reads all the data, then removes duplicates
SELECT DISTINCT order_id FROM orders WHERE ...;

-- Exists — only checks whether something exists
SELECT order_id FROM orders WHERE EXISTS (...);
```

- **DISTINCT**
  - Reads **every row** matching the condition, then removes duplicates
  - Needs an internal sort (or hash) → a burden on both I/O and sorting
- **EXISTS**
  - Partial range processing that returns **true as soon as it finds one match**
  - No sort needed + minimal I/O

> 💡 If your duplicate removal is really just an **existence check**, first ask whether it can be rewritten with EXISTS.

## 5.2.3 GROUP BY and hash grouping

Older optimizers always resolved `GROUP BY` with a **Sort Group By** — **sort by the group key first**, then bundle equal values together — so a **sort cost was unavoidable**.

Modern optimizers support **Hash Group By** — they aggregate by piling the group keys into a **hash table**, so **no sort is needed**.

```
Example Oracle execution plans:
  HASH GROUP BY          ← no sort (fast)
  SORT GROUP BY          ← sort happens
```

### When does Hash Group By get chosen?

- When **GROUP BY + ORDER BY** are **not on the same columns** (i.e., a sorted result isn't required)
- When the number of groups is small (the hash table fits in memory)
- When you haven't blocked it with a hint like `NO_USE_HASH_AGGREGATION`

### MySQL 8.0+

```
If EXPLAIN shows "Using temporary", grouping is done via a temporary table
Control with hints: /*+ GROUP_INDEX(...) */, /*+ SET_VAR(optimizer_switch='hash_aggregation=on') */
```

## 5.2.4 When window functions can skip the sort

Window functions (`ROW_NUMBER()`, `RANK()`, `SUM() OVER(...)`, etc.) need an internal sort depending on their `PARTITION BY` and `ORDER BY`.

### Cases where the sort can be avoided

1. **An index exists that matches the window clause's sort key** → the optimizer uses the index order as-is

   That index-matching case is exactly the mechanism of Part 5.3.

2. **PARTITION BY only, no ORDER BY** + **an order-insensitive function (COUNT, SUM)** → the sort can be skipped
3. **Multiple window functions all share the same PARTITION BY / ORDER BY** → the sort is performed only once

### Anti-pattern

```sql
-- A different PARTITION BY for every window function
SELECT
  ROW_NUMBER() OVER (PARTITION BY dept ORDER BY sal),
  RANK()       OVER (PARTITION BY job  ORDER BY hiredate),
  ...
```
→ **The sort happens twice**. If you can, unify your window specs.

## 5.2.5 Writing SQL that uses less Sort Area

If a sort is **unavoidable**, at least steer it so it **finishes as an in-memory sort**. The key is **"shrink the size of the data being sorted."**

### Technique 1 — Defer transformations with a subquery

```sql
-- ❌ Bad: sorts the transformed result — post-transformation strings pile up in the Sort Area
SELECT UPPER(name) || '-' || dept AS label
FROM   emp
ORDER BY UPPER(name) || '-' || dept;

-- ✅ Good: sort first, transform at output time
SELECT UPPER(name) || '-' || dept AS label
FROM (
  SELECT name, dept FROM emp ORDER BY name, dept
);
```

- The inner subquery sorts the **untransformed originals** → **less Sort Area used**
- The transformation is applied only at the final output stage

### Technique 2 — SELECT only the columns you need

```sql
-- ❌ Bad
SELECT * FROM emp ORDER BY sal;

-- ✅ Good
SELECT empno, name, sal FROM emp ORDER BY sal;
```

- When sorting, **every SELECT column gets stored in the Sort Area**, so `*` burns a lot of Sort Area
- **Naming only the columns you need** eases the Sort Area load

### Technique 3 — Apply filters first

```sql
-- ❌ Bad: sorts all 100,000 rows, then keeps only the top 10
SELECT * FROM (SELECT * FROM logs ORDER BY created_at DESC) WHERE ROWNUM <= 10;

-- ✅ Good: use the index to read just the 10 most recent rows and stop
SELECT /*+ INDEX_DESC(logs idx_created) */ *
FROM   logs
WHERE  ROWNUM <= 10
ORDER BY created_at DESC;
```

→ Skipping the sort with an index is covered in detail in [Part 5.3](<./5.3DBMS Made Ridiculously Easy - Skipping Sorts with Indexes.md>).

## 🔑 Key points from this part

| Situation | Prescription |
|---|---|
| Union with no duplicates | **UNION ALL** |
| Only need an existence check | DISTINCT → **EXISTS** |
| GROUP BY that doesn't need a sorted result | **HASH GROUP BY** (leave it to the optimizer, or hint) |
| Multiple window functions | **Unify the window specs** to minimize the number of sorts |
| Sort is unavoidable | **Fewer columns + filter first + defer transformations** |

---

### 📝 One-line takeaway

> **"Before tuning a sort, ask whether the SQL even needs one — UNION ALL, EXISTS, hash grouping, and shared window specs can make the sort vanish entirely."**
