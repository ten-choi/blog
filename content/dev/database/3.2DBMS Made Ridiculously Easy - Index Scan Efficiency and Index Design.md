# 3.2 Index Scan Efficiency and Index Design

## 3.2.1 Making index scans efficient

### Shrinking the scan range = reading fewer leaf blocks

The cost of an index range scan ultimately boils down to **"how many leaf blocks do we have to sweep through?"**
Even for the exact same result, performance splits on **how tightly you narrowed the start and end points of the index scan**.

We met access vs. filter conditions briefly in Part 2.2 — from here they become the main tool.

### (1) Access conditions vs. filter conditions — the most important distinction

| Type | Role | Example |
|---|---|---|
| **Access condition (Access Predicate)** | **Determines the start/end points** of the index scan | `WHERE dept = 'A' AND hire_date >= '2020-01-01'` |
| **Filter condition (Filter Predicate)** | **Only checks** whether each row matches during the scan | `WHERE name LIKE 'Kim%'` (a non-index column) |

> 🔑 Even for the same result, **a condition working as an access condition shrinks the scan range** — a filter condition cannot shrink it at all.

### (2) Column order in a composite index

With an index on `(A, B, C)`, the scan range changes depending on the conditions.

```sql
-- ✅ A, B, C are all access conditions → the narrowest range
WHERE A = 10 AND B = 20 AND C = 30

-- ⚠️ A and B are access conditions, C becomes a filter (when B is a range condition)
WHERE A = 10 AND B >= 20 AND C = 30

-- ❌ Only A is an access condition, B/C become filters (when A is a range condition)
WHERE A >= 10 AND B = 20 AND C = 30
```

> **Principle**: put the **`=` condition columns up front**, and the **range condition columns (`>=`, `BETWEEN`, `LIKE`) at the back**.

### (3) IN-lists and index scans

An `IN` is internally decomposed into several `=` conditions — it's the same as **hitting the index multiple times**.

```sql
WHERE dept IN ('A', 'B', 'C')
-- = dept='A' OR dept='B' OR dept='C'
-- → 3 index scans
```

When the leading column is an `IN`, that leading column can be used like an `=` — so the trailing columns can still serve as access conditions.

### (4) Between vs. Like, and pushing range conditions back

The further back you push a range condition, the more of the front columns get used as access conditions.

```sql
-- ❌ Range condition in the middle
WHERE dept = 'A' AND hire_date BETWEEN '...' AND '...' AND title = 'Manager'
→ with index (dept, hire_date, title), title becomes a filter condition

-- ✅ Change the index order to (dept, title, hire_date) and all 3 become access conditions
```

## 3.2.2 Index design

### Indexes aren't free

The more indexes you have, **the faster reads get — but the slower DML (Insert/Update/Delete) gets.**
→ Every added index increases the cost of inserts, updates, and deletes linearly.

### (1) Design principles in a nutshell

1. **Design around the queries that run most often** — a query that runs a million times a day beats a batch job that runs once a month.
2. Put **`=` condition columns at the front**.
3. Put **range condition columns at the back**.
4. **Fold in the sort (ORDER BY) columns** so the Sort Order By operation can be skipped.
5. **Keep the number of indexes to a minimum** — review duplicate indexes and indexes sharing the same leading column for consolidation.

### (2) One composite index beats several single-column indexes

```
Instead of creating separate (A), (B), (C) indexes
→ consolidate into a single (A, B, C) index and it covers most queries
```

### (3) Index Merge vs. composite index

The optimizer can also combine two single-column indexes on the fly (Index Merge), but
**one well-designed composite index is faster in most cases.**

### (4) NULL handling in index columns

- An Oracle B-Tree index **does not store NULL values in the index**
  → `WHERE col IS NULL` can't use the index.
- For columns with lots of NULLs, consider a function-based index (`NVL`) or leveraging `IS NOT NULL`.

---

## 🔑 Key points from this part

- The cost of an index scan = **the number of leaf blocks read** → shrinking the scan range is the whole game.
- **Access condition ≫ filter condition** — the same `WHERE` clause can play very different roles.
- Composite index design: order columns **`=` → range → sort**.
- An index is a trade-off between **read optimization ⇆ DML penalty** — don't just pile them on.

---

### 📝 One-line takeaway

> **"The cost of an index scan is the number of leaf blocks it reads — order columns `=` first, range last, and build few, well-chosen composite indexes."**
