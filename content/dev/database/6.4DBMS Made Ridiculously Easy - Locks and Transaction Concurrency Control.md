# 6.4 Locks and Transaction Concurrency Control

- The **lock mechanism and transaction concurrency control** of the database you use is a must-learn topic!

Before diving in, recall the MVCC and read consistency model from Part 6.1: thanks to MVCC, readers don't block writers and writers don't block readers. That means everything in this part is about **writer-vs-writer conflicts** — what happens when two transactions try to *change* the same data at the same time.

## 6.4.1 Lock types

- Oracle lock types

  1. **DML locks**
     - **The most important kind of lock** from an application-development perspective
     - They protect the **integrity of user data** accessed by multiple concurrent transactions
     - DML locks come in two flavors: **table locks** and **row locks**
  2. **DDL locks**
  3. **Latches**
     - Used to protect the various shared data structures in the SGA
  4. **Buffer locks**
     - Used to **serialize** access to buffer blocks
  5. **Plan cache (execution plan cache) locks / pins**
     - Used to protect the **SQL cursors and PL/SQL programs** shared in the plan cache

## 6.4.2 Row locks vs table locks

- **DML row locks**

  - They prevent two concurrent transactions from **modifying the same row**
  - When UPDATE / DELETE / INSERT hits the same row:
    - **UPDATE, DELETE**: a row with an in-flight (not-yet-committed) change **cannot be modified by another transaction**
    - **INSERT**: with a unique index in place, trying to insert the same value causes **blocking**
      1. The trailing transaction waits until the leading transaction commits
      2. If the leading transaction commits, the trailing one fails; if it rolls back, the trailing one succeeds
  - To avoid performance degradation from DML row locks, **manage your commit timing so locks aren't held too long**

- **DML table locks (= TM locks)**

  - To stop other transactions from changing the structure of a table the current transaction is modifying, a **table lock is acquired first, before the row lock**

  - Row locks use only **one mode (exclusive)**, whereas table locks come in **several modes (RS, RX, S, SRX, X)**

  - The name "table lock" makes it easy to assume "the whole table gets locked," but in reality it's closer to **meta-information registered with the DBMS declaring what kind of work the transaction is doing on that table**. Other transactions compare their own work mode against the registered mode and decide: **compatible → proceed concurrently; conflicting → wait or give up**.

    - You can choose to wait until the lock is released / wait only for a set time then give up / give up immediately without waiting

  - Example) A DDL statement wants to alter the table's structure

    - The transaction trying to change the table structure **first checks whether a TM lock is held** on that table
    - If even one transaction holds an **RX-mode** lock, the DDL stops
    - Conversely, if the DDL got there first, **the transaction trying to run DML waits**

## 6.4.3 Blocking and deadlocks

- **Blocking vs deadlock**

  - **Blocking**: a trailing transaction is **stuck waiting** because of a lock held by a leading transaction
  - **Deadlock**: two transactions each hold a lock on a resource, and **each tries to lock the resource the other one holds** — so neither can make progress
    - When Oracle detects a deadlock, **the transaction that notices it first performs a statement-level rollback and then throws an error**

## 6.4.4 Pessimistic vs optimistic concurrency control

- **Transaction concurrency control** splits into **pessimistic concurrency control** and **optimistic concurrency control**

  1. **Pessimistic concurrency control**
     - **Assumes** "users *will* modify the same data at the same time," so it locks the data at read time and holds the lock until the read/update finishes
     - You take a pessimistic lock with `select ... for update`
     - It risks hurting concurrency badly, but the `for update wait ...` and `for update nowait` options can **claw some of that concurrency back**
  2. **Optimistic concurrency control**
     - **Assumes** "users *won't* modify the same data at the same time," so no lock is taken at read time. Instead, **you must check at update time whether the data has changed**.
     - Two ways to do it: **compare every column for changes**, or keep a dedicated **last-modified timestamp column** and check whether the timestamp moved

- **To get data quality *and* concurrency**

  - **Don't be afraid** of `for update`
  - When the situation calls for `for update`, use it precisely — and even if it's tedious, **handle the exceptions carefully with the wait / nowait options**
  - Don't hold locks longer than necessary; **commit as early as you can** within the bounds of transaction atomicity

## 6.4.5 Number-allocation strategies

- **Number-allocation strategies**

  - **Number allocation**: the process of **preventing PK duplication** when inserting new data

  - The options

    1. **A dedicated numbering table**

       - Manage a separate table used purely for handing out numbers
       - Read the numbering record, **update it to the value +1**, and use that value as the new record's PK
       - It **completely eliminates the possibility of two transactions allocating a duplicate value**
       - **Pros**
         - Highly **versatile**
         - No need to code defensively against duplicate records
         - Can **prevent gaps** in the sequence during INSERT
         - **Works even when the PK is a composite key**
       - **Cons**
         - **Row-lock contention** on the numbering record hurts performance (so it's hard to use under very heavy concurrent INSERT load)
    2. **A sequence object**

       - Put simply, it's **a numbering table that Oracle manages internally for you**

       - **Pros**
         - **Fast**
         - No need to code defensively against duplicate records

       - **Cons**
         - There's the overhead of **creating and managing a sequence object** per table
         - Sequence allocation has its own lock-related performance issues (though **setting an appropriate cache size** keeps it fast)
         - Usable **only when the PK is a single column**
         - **Gaps can appear** in the sequence
    3. **MAX + 1 lookup**
       - Example: use the value of `select max(transaction_no) + 1 from transactions` as the PK of the row being inserted
       - **Pros**
         - **No sequence or numbering table to manage**
         - **Excellent performance** when concurrent-transaction collisions are rare
         - **Works even with a composite PK**
       - **Cons**
         - Requires **careful exception handling** for duplicate records
         - Under heavy concurrent allocation, it **can end up much slower than a sequence**

---

### 📝 One-line takeaway

> **"Locks aren't the enemy — locks held too long are. Understand row locks vs table locks, pick pessimistic or optimistic control deliberately, and commit as early as atomicity allows."**
