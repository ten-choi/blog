# 7.1 Optimizer Statistics and How Cost Is Calculated

## 7.1.1 Selectivity and Cardinality

**Selectivity** is the **ratio of records selected by a condition** out of all the records.

When you search with an `=` condition, it's calculated like this.

`Selectivity = 1 / NDV`

**NDV**: the number of distinct values in the column (for gender, male/female → 2)

**Cardinality** is the **number of records selected by a condition** out of all the records.

`Cardinality = total rows × selectivity = total rows / NDV`

> 💡 The optimizer **calculates cost from cardinality**, and uses that cost to **decide which execution plan to run**. Which means the **accuracy of the selectivity value underneath cardinality is the heart of tuning**.

## 7.1.2 Statistics

### Object statistics

#### Table statistics

Querying table statistics
```sql
select 
       num_rows -- total record count
     ,blocks -- number of table blocks = total blocks belonging to 'used' extents
     ,avg_row_len -- average length per record
     ,sample_size -- number of sampled records
     ,last_analyzed -- when the statistics were gathered
from all_tables
where owner='SCOTT'
and table_name = 'EMP'
;
```

#### Index statistics

Querying index statistics
```sql
select blevel -- branch level: number of blocks read from the index root until just before reaching a leaf block
     ,leaf_blocks  -- total number of index leaf blocks
     ,num_rows -- number of records stored in the index
     ,distinct_keys -- number of distinct values formed by the index key combination. c1(3) * c2(4) = 12. Used for selectivity calculation.
     ,avg_leaf_blocks_per_key -- number of leaf blocks read when querying with '=' conditions on all index keys
     ,avg_data_blocks_per_key -- number of table blocks read when querying with '=' conditions on all index keys
     ,clustering_factor -- how clustered the table data is relative to the index key order. A precomputed figure for how many table blocks will be read while scanning the index and fetching table records
     ,sample_size
     ,last_analyzed
from all_indexes
where owner = 'SCOTT'
and table_name = 'EMP'
and index_name = 'EMP_X01'
;
    
    
```

#### Column statistics

Querying column statistics

```sql
select num_distinct -- number of distinct column values (NDV)
     , density -- selectivity for an '=' condition. 1/NDV
     , avg_col_len -- average column length (bytes)
     , low_value -- minimum value
     , high_value -- maximum value
     , num_nulls -- number of records that are null
     , last_analyzed
     , sample_size
from all_tab_columns
where owner = 'SCOTT'
and table_name = 'EMP'
and column_name = 'DEPTNO'
;
```

**Column histograms**

For an `=` condition, selectivity usually comes from `1/NDV` or the `Density` value.

But **when the data distribution is not uniform**, those values are hard to use as-is. In that case the optimizer reaches beyond plain statistics and uses a **histogram**.

**Histogram**: statistics that **precompute the proportion or frequency of data for each column value**. It's calculated by sampling the actual data.

- Histogram types
  - **Frequency**: stores the frequency count for each value
  - **Height-Balanced**: manages the data distribution so every bucket has the same height
  - **Top-Frequency**: stores frequency counts for the top n values that hold the most records
  - **Hybrid**: combines the characteristics of Frequency and Height-Balanced

Querying histograms

```sql
select endpoint_value, endpoint_number
from ALL_TAB_HISTOGRAMS
where owner = 'SCOTT'
and table_name = 'EMP'
and column_name = 'DEPTNO'
order by endpoint_value
;
```

### System statistics

**System statistics** are **measurements of the application's and hardware's performance characteristics**.

- CPU speed
- Average Single Block I/O speed
- Average Multiblock I/O speed
- Average Multiblock I/O count
- Maximum throughput of the I/O subsystem
- Average throughput of a parallel slave

## 7.1.3 How Cost Is Calculated

The formulas below show the I/O portion of the cost — the CPU component estimated from system statistics (see Part 1.2) is layered on top.

Let's look at how cost is calculated when accessing a single table through an index.

**Searching with `=` conditions**

``` 
Cost = BLEVEL                     -- index Vertical Traversal cost
      + AVG_LEAF_BLOCKS_PER_KEY  -- index Horizontal Traversal cost
      + AVG_DATA_BLOCKS_PER_KEY  -- table random access cost
```      

- blevel: branch level — the number of blocks read from the index root until just before reaching a leaf block
- avg_leaf_blocks_per_key: the number of leaf blocks read when querying with `=` conditions on all index keys
- avg_data_blocks_per_key: the number of table blocks read when querying with `=` conditions on all index keys

**When the conditions aren't all `=` (column statistics come into play too)**

```   
 Cost = BLEVEL                                          -- index Vertical Traversal cost
      + LEAF_BLOCKS       * effective index selectivity  -- index Horizontal Traversal cost
      + CLUSTERING_FACTOR * effective table selectivity  -- table random access cost
```

- leaf_blocks: total number of index leaf blocks
- clustering_factor: how clustered the table data is relative to the index key order — a precomputed figure for how many table blocks will be read while scanning the index and fetching table records
- effective index selectivity: the fraction of all index records expected to be selected by the access conditions
- effective table selectivity: the fraction of all index records expected to be selected by all conditions on the index columns

## 7.1.4 Gathering and Managing Statistics

Every cost calculation the optimizer does runs on the **assumption that the statistics are accurate**. If the statistics are stale or missing, even sound principles will inevitably produce a **wrong execution plan**.

### Manual gathering commands

**Oracle — the `DBMS_STATS` package**

```sql
-- Gather statistics for a specific table
BEGIN
  DBMS_STATS.GATHER_TABLE_STATS(
    ownname          => 'SCOTT',
    tabname          => 'EMP',
    estimate_percent => DBMS_STATS.AUTO_SAMPLE_SIZE,  -- automatic sample size
    method_opt       => 'FOR ALL COLUMNS SIZE AUTO',  -- automatic histograms
    cascade          => TRUE                          -- gather statistics for related indexes too
  );
END;
/

-- Entire schema
BEGIN
  DBMS_STATS.GATHER_SCHEMA_STATS(ownname => 'SCOTT');
END;
/
```

**MySQL**

```sql
ANALYZE TABLE emp;               -- refresh table statistics
ANALYZE TABLE emp, dept;         -- multiple tables at once

-- Histograms (8.0+)
ANALYZE TABLE emp UPDATE HISTOGRAM ON sal WITH 32 BUCKETS;
ANALYZE TABLE emp DROP HISTOGRAM ON sal;
```

### Automatic gathering schedules

**Oracle**

- By default, an `auto optimizer stats collection` automated job runs **10 PM to 2 AM on weekdays, and all day on weekends**
- Internally, it picks out only the tables whose **statistics have gone stale** and runs `DBMS_STATS` on them
- To check:
  ```sql
  SELECT client_name, status FROM dba_autotask_client;
  ```

**MySQL (InnoDB)**

- With `innodb_stats_auto_recalc = ON` (the default), statistics are automatically recalculated whenever **more than 10% of a table's data changes**
- With `innodb_stats_persistent = ON` (the default), statistics are persisted to disk (they survive a restart)

### Stale Statistics — the danger of "old numbers"

```
Problem scenario:
1. As of yesterday, the table has 10K rows — and the statistics say 10K rows
2. This morning's batch inserts 10 million rows
3. A query runs — the optimizer still calculates against a "10K-row table"
4. It's actually a big table, but the optimizer picks an NL join → disaster
```

- **"Statistics look at the past; data lives in the present"** — this gap is the #1 cause of execution plan errors
- When you should refresh manually:
  - Right after a bulk INSERT/UPDATE/DELETE
  - Right after adding/dropping a partition
  - Right after creating/dropping an index
  - When a query that always ran fine suddenly gets slow — **suspect the statistics first**

### Dynamic Sampling — the fallback when there are no statistics

When a query hits a table whose statistics were never gathered or are far too stale, Oracle can perform **Dynamic Sampling (= Dynamic Statistics)**.

- Right before building the execution plan, it **samples a few blocks of data matching the query's conditions** and builds temporary statistics
- Upside: even without statistics, the optimizer **won't build a completely wrong plan**
- Downside: **extra I/O happens at parse time** → parsing gets more expensive
- Parameter: `OPTIMIZER_DYNAMIC_SAMPLING` (levels 0–11)

### 💡 Real-world checklist

- [ ] Did you run a statistics-gathering command **right after** the bulk batch?
- [ ] Check for **staleness** (`USER_TAB_STATISTICS.STALE_STATS = 'YES'`)
- [ ] Are **histograms gathered** on the columns that need them (heavily skewed distributions)?
- [ ] Is the gathering itself scheduled so it **doesn't add load during service hours**?
- [ ] If it's a partitioned table, are you gathering **both global and partition-level statistics**?
