> The easiest SQL Tuning primer in the world — for junior developers.

> The NL join works **"one row at a time,"** the sort merge **"sorts both sides,"** and the hash join **"loads one side into a hash table and sweeps the other"** — the modern answer for joining large data sets.

# 4.3 Hash Join, the Answer for Large Data Sets

## 4.3.1 How the hash join works

It runs in two phases.

**① Build phase**

- Pick the **smaller set (the Build Input)** of the two, run its join keys through a hash function,
- and build a hash table **in memory (the Hash Area in the PGA)**.

**② Probe phase**

- Sweep the larger set (the Probe Input) **one row at a time**,
- run each row's join key through the same hash function → check the hash table for a match

```
Build (smaller side)     Probe (larger side)
[dept]                   [emp]
 ↓ build hash table       ↓ scan row by row, probing the hash table
[h(10) → row]            for each row:
[h(20) → row]              bucket = h(row.dept_id)
[h(30) → row]              if bucket in hash table → join
```

## 4.3.2 Why is it fast?

- **A hash table lookup is O(1)** — cheaper than the NL join's index traversal
- **No random I/O** — each table only needs **one Full Scan** and you're done
- **No index required** — for large joins it doesn't depend on whether an index exists

## 4.3.3 When the hash join wins

- When **both sides have lots of data** and an NL join's cost would explode
- When **the driven table has no index**
- When **one side is small enough to fit in memory (the Hash Area)**

## 4.3.4 Limits of the hash join

- **Only supports equality joins (equi-joins)** — any condition that isn't `=` can't be used
- **If the Hash Area runs out, it spills to disk** (this is the distinction between a Grace Hash Join and an In-Memory Hash Join)
  → at that point, much of the hash join's advantage evaporates
- **If the Build input is too big**, the hash table itself becomes a burden

## 4.3.5 NL vs Hash vs Sort Merge — at a glance

| Criterion | NL join | Sort merge | Hash join |
|---|---|---|---|
| **Small joins** | ✅ Best | ❌ Overkill | ❌ Overkill |
| **Large joins** | ❌ Slow | ⚠️ Sorting burden | ✅ Strong |
| **No index on driven table** | ❌ Slow | ✅ OK | ✅ OK |
| **Non-equi joins** | ✅ Possible | ✅ Possible | ❌ Not possible |
| **Response time (first row)** | ✅ Immediate | ❌ After full sort | ❌ After Build |

## 4.3.6 Hash joins in MySQL

- **MySQL supports hash joins starting with 8.0.18**
- From 8.0.20 onward, there are more and more cases where it picks the hash join over the NL join by default
- [MySQL official docs — Hash Join](https://dev.mysql.com/doc/refman/8.0/en/hash-joins.html)

---

### 📝 One-line takeaway

> **"Hash join = hash table on the small side → Probe with the big side."**

- The standard answer for the **large join + no index** situation.
- Caveats: **equality joins only**, and it **falls to disk when the Hash Area runs out**.
- Available in MySQL 8.0.18+ — always check your version.
