# 5.1 How Sorting Works

A **Sort** is a **heavy operation that burns a lot of CPU and memory**. When a sort-related issue shows up in SQL tuning, you usually end up suspecting one of three things — **"why did a sort appear,"** **"can we get rid of it,"** and **"if we can't, how do we make it cheap."**

In this part, let's look at the **very bottom layer of the mechanics** — where sorting happens, and how it actually runs.

---

## 5.1.1 When a sort happens

When the optimizer meets conditions like these, it puts a **Sort operator** into the execution plan:

- `ORDER BY`
- `GROUP BY` (when hash-based grouping is impossible or inefficient)
- `DISTINCT`
- `UNION` (for duplicate elimination)
- The sort phase of a **Sort Merge Join**
- A **Window function's** `PARTITION BY` / `ORDER BY`
- An **Index Build** (when creating an index, rows are sorted by key)

---

## 5.1.2 Where a sort happens — the Sort Area in the PGA

Sorting is fundamentally performed in the **Sort Area**, which is allocated inside the **PGA (Program Global Area)**.

- **The PGA is per-session private memory** — other sessions can't see it
- When a session needs to sort, the Sort Area is **allocated at a certain size** for it to use
- Once the sort finishes, the Sort Area is released

### 💡 Sidebar: shared memory vs. private memory

"Private memory" deserves a moment, because the split between the two kinds of database memory comes down to **"who uses it"** and **"what goes into it."**

- **Shared memory** is used by **every session together** — allocated once at instance startup. What lives here are things that **pay off when referenced in common**: data blocks read from disk (the Buffer Pool), the execution plan cache, the metadata cache. If session A reads the `members` table into the Buffer Pool, session B gets it from memory for free.
- **Private memory (the PGA)** belongs to **one session alone**. What lives here is **that session's own working data**: rows mid-sort, a hash join's hash table, cursors, session variables — data no other session needs to see, and shouldn't.

An easy analogy: **shared memory is the library's bookshelves** — everyone reads the same books; **private memory is your personal reading desk** — where you take a book to scribble notes, and which gets cleared when you leave.

Trace `SELECT * FROM orders ORDER BY amount DESC` and both show up: the `orders` blocks are read into **shared memory (the Buffer Pool)**, then sorting them by `amount` happens in **your session's private memory (the Sort Area)**. Why the split? If everything were shared, sessions would trample each other and **lock contention would explode**; if everything were private, every session would re-read the same data and **disk I/O would explode**.

| Item | Shared memory | Private memory |
|------|-------------|-------------|
| Who uses it | Shared by all sessions | Exclusive to each session |
| What's in it | Data blocks, execution plans, metadata | Sort/hash working data, cursors, session variables |
| Lifecycle | Instance start to shutdown | Session start to disconnect |
| Core benefit | Fewer disk I/Os (caching) | Isolated per-session work |

So the sort story of this part runs entirely on the right-hand column: **the data being sorted was read via shared memory, but the sorting itself happens in your private Sort Area** — which is exactly why its size decides everything that follows.

### Sort Area–related parameters

**Oracle (automatic PGA management)**

```
PGA_AGGREGATE_TARGET     -- target total PGA size for the whole instance
WORKAREA_SIZE_POLICY     -- AUTO (recommended) / MANUAL
```

- In `AUTO` mode, Oracle automatically distributes as much Sort Area as each session needs (typically 5% of `PGA_AGGREGATE_TARGET`)
- In `MANUAL` mode, you set the legacy parameter `SORT_AREA_SIZE` yourself (rarely used these days)

**MySQL**

```
sort_buffer_size         -- per-session sort memory size (default 256KB)
tmp_table_size           -- memory size for temporary tables
max_heap_table_size      -- max size of in-memory temporary tables
```

- When a session starts sorting, MySQL **allocates the entire `sort_buffer_size` at once, up front**. Set it too large and you consume **concurrent sessions × sort_buffer_size** of memory — an OOM risk.

## 5.1.3 Memory sort vs disk sort

### Memory sort (In-Memory Sort)

When the data to be sorted **fits entirely inside the Sort Area**.

- The internal algorithm is usually in the **Quicksort / Timsort** family
- Uses only CPU, no disk I/O → very fast

### Disk sort (External Sort)

When the data to be sorted **exceeds the size of the Sort Area**. Since it can't all fit in memory at once, it's handled like this:

1. Split the input into **chunks the size of the Sort Area** and sort each chunk in memory
2. Write each sorted chunk to the **Temp tablespace** (disk) as a temporary file
3. Repeat steps 1–2 until the entire input is processed
4. Combine the sorted chunks piled up on disk with **Merge Passes** to produce the final sorted result

This is the **External Merge Sort** algorithm. Performance degrades in proportion to how many times you read from and write to disk.

### The performance gap at the crossover

| Aspect | Memory sort | Disk sort |
|---|---|---|
| Space | PGA Sort Area | PGA + Temp tablespace |
| I/O | None | Disk writes + re-reads |
| Speed | Fast | **Tens to hundreds of times slower** |
| Trigger | Default | Sort Area exceeded |

### How to spot it in the execution plan

**Oracle**

```
Operation           Name        Sorts(Memory)  Sorts(Disk)
SORT ORDER BY                   1              1
```

- If `Sorts(Disk) > 0`, **a disk sort happened** → that's a tuning target

**MySQL**

```
In the Extra column of EXPLAIN output:
  Using filesort           → a sort occurred
  Using filesort; Using temporary  → a Temp table was used (possible disk sort)
```

- ⚠️ Despite the name `filesort`, **if the sort finishes in memory, no file is ever created**. Don't be fooled by the name.
- **If Performance Schema's `sort_merge_passes` value is large**, that's a signal of disk spills

## 🔑 Key points from this part

- Sorting is performed in the **PGA's Sort Area**
- If it fits inside the Sort Area, it's a **memory sort (fast)**; if it overflows, it's a **disk sort (slow)**
- So the two directions for tuning are crystal clear:
  1. **Eliminate the sort — or shrink it until it fits in the Sort Area** → [Part 5.2](<./5.2DBMS Made Ridiculously Easy - Writing SQL That Avoids Sorts.md>)
  2. **Skip the sort using an index** → [Part 5.3](<./5.3DBMS Made Ridiculously Easy - Skipping Sorts with Indexes.md>)

---

### 📝 One-line takeaway

> **"A sort that fits in the Sort Area is fast; one that spills to disk is tens to hundreds of times slower — so either eliminate the sort, shrink it, or let an index do it for you."**
