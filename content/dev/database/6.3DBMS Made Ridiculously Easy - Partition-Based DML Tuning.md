# 6.3 Partition-Based DML Tuning


### What is a partition?
- It's splitting a single table or index **by a partition key and storing each piece in its own segment**.
- Logically it still looks like one table, but **physically you get the effect of spreading the data across several tables**.

### Why partitions are needed
- **Management side**: work done on one partition **doesn't affect the other partitions** of the same table → better availability
- **Performance side**: less contention, better load distribution

## 6.3.1 Table partitions

### (1) How partitioned tables improve performance
* The core mechanism is **partition pruning**. At SQL parse or execution time, the optimizer analyzes the WHERE clause and **excludes irrelevant partitions from access entirely**.
* For example, with a non-partitioned table holding 10 million rows, the condition has to be **filtered against all 10 million rows**.
* With partitioning, only the **partitions matching the condition get scanned**, and filtering happens inside them — a big performance win.

### (2) Range partitioning
* Partitioning based on **ranges of values**, like a date column
* Very effective when management differs by **retention policy** (e.g., a log table where you keep one year of data and archive the rest)

### (3) Hash partitioning
* The user only chooses the **number of partitions**; the data-distribution algorithm is decided by **Oracle's internal hash function**
* Because of how hashing works, partition pruning only kicks in for **equality (=) or In-List conditions**

### (4) List partitioning

* If hash partitioning is "automatic splitting," list partitioning splits data **according to logical groups the user defines**
* For example, with a region column as the partition key, you partition by **logical criteria** like 'Seoul', 'Gyeonggi', 'Busan'

## 6.3.2 Index partitions

### (1) Local partitioned indexes
* Index partitions that map **1:1 to each table partition**
* For example, if the table is partitioned by month, each partition gets its own corresponding index
* The index partitions **inherit the table partitions' attributes as-is**, so `table partition key == index partition key`
* When a partitioned table changes, Oracle **automatically adjusts the local partitioned index to match**

> Quiz
>
> **Can a local partitioned index exist on a non-partitioned table?**

> ✅ **Answer: it can't.**
>
> By definition, a local partitioned index is **"an index partition that maps 1:1 to each table partition."**
> If the table isn't partitioned, **there's no partition to map to**, so the very concept of a local partitioned index doesn't hold.
> The only thing you can create in that case is a **non-partitioned (regular) index**.

### (2) Global partitioned indexes

* An index whose partitioning is **configured differently from the table's**. If it isn't a local index, **it's a global partitioned index** — that's the rule of thumb.
* This covers cases where the partition type differs, the partition key differs, or the partition boundary definitions differ.
* When the table's partition layout changes, the index becomes **Unusable** and **must be rebuilt**.

### (3) Non-partitioned indexes

* A regular index with no partitioning
* When a non-partitioned index is combined with a partitioned table, **any change to the table means the index has to be rebuilt**.

## 6.3.3 Bulk UPDATE tuning with partitions

Say a table holds 1 billion rows and you need to change **5% of them (50 million rows)**.

### 1) Just UPDATE the 50 million rows
→ You pay for the select/update on 50 million rows **plus the burden of maintaining the indexes**.

### 2) Drop the indexes, then UPDATE the 50 million rows
→ The update itself gets faster, but now you're stuck with **rebuilding indexes over 1 billion rows**.

### 3) Use partition exchange
* Available when **the table is partitioned and the indexes are local partitioned indexes**
```sql
(1) Create a temporary table
(2) Insert the post-update data into the temporary table
(3) Build indexes on the temporary table
(4) Exchange the existing table partition with the temporary table
(5) Drop the temporary table
```

## 6.3.4 Bulk DELETE tuning with partitions

For UPDATE you only need to **rebuild the indexes that contain the changed columns**, but DELETE requires **rebuilding every index**, so the index-rebuild cost is far bigger.

### 1) Bulk delete via partition DROP

* If the table is partitioned on the delete condition's column and the indexes are local, deletion becomes trivially simple
* For example, when the table is partitioned by month and you want to drop the January partition wholesale:
```sql
alter table transactions drop partition p201412;
```

### 2) Bulk delete via partition TRUNCATE
* The approach for when you're not deleting cleanly along the partitioning boundary but have **an additional delete condition**
* If most of the data needs to go, it's faster to **"wipe everything and re-insert only what you're keeping"** than to **"delete the rows to be removed."**
```sql
(1) Create a temporary table and insert only the rows to keep
(2) Truncate the target table partition
(3) Insert the copied data back into the original table (using INSERT ... SELECT)
(4) Drop the temporary table
```

## 6.3.5 Bulk INSERT tuning with partitions

### 1) With a non-partitioned table
* For bulk inserts, **marking the indexes Unusable first and rebuilding them afterward** can be the faster route.

### 2) With a partitioned table
* If the table is partitioned and the indexes are local, you can **rebuild indexes partition by partition** → you avoid the cost of a full rebuild.


---

### 📝 One-line takeaway

> **"On huge tables, stop deleting and updating row by row — partition the table so you can DROP, TRUNCATE, and EXCHANGE whole slabs of data at once."**
