# 5.3 Skipping Sorts with Indexes

**An index is an already-sorted data structure.** Read it as-is and you get a sorted result **with no extra sort**. This part covers the tuning techniques that actively exploit that property.

---

## 5.3.1 Why does "skipping the sort" matter?

Think about the patterns constantly requested in an OLTP environment:

- The 20 most recent orders
- The top 10 by view count
- The last 5 login records

If you run a sort every time for these queries, you end up **reading all 10 million rows, sorting them, then returning just the first 10**. Ridiculously inefficient.

But **with the right index**, the optimizer can do **partial range processing** — **"read just the first N rows in index order and stop."** Whether the table holds 10 million rows or 100 million, performance stays nearly constant.

---

## 5.3.2 Conditions for skipping Sort Order By

For the optimizer to skip the `ORDER BY`, **the sort-key order must match the index-key order**.

### The basic case

```sql
-- index: (created_at)
SELECT * FROM logs ORDER BY created_at;
```

→ Just **read the index leaf blocks in order** and the result is already sorted. **No SORT ORDER BY operator.**

### The composite-index case

```sql
-- index: (dept, sal)
SELECT * FROM emp WHERE dept = 10 ORDER BY sal;  -- ✅ sort can be skipped
SELECT * FROM emp WHERE dept = 10 ORDER BY name; -- ❌ not an index key → sort required
SELECT * FROM emp ORDER BY sal;                   -- ❌ no condition on the leading column
```

**The rules**:
- The **combined order** of the `WHERE` clause's equality columns and the `ORDER BY` columns must match the index order
- If the `ORDER BY` mixes in a column that isn't in the index, the sort can't be skipped

---

## 5.3.3 ORDER BY + LIMIT / ROWNUM — the truly powerful pattern

We met this pattern in Part 3.1 from the access side — here's why it works from the sort side.

```sql
-- index: (created_at DESC), or scan (created_at) descending
-- the 20 most recent log rows
SELECT * FROM logs ORDER BY created_at DESC LIMIT 20;           -- MySQL / PostgreSQL
SELECT * FROM logs WHERE ROWNUM <= 20 ORDER BY created_at DESC; -- Oracle (wrong — see below)
SELECT * FROM logs ORDER BY created_at DESC FETCH FIRST 20 ROWS ONLY; -- Oracle 12c+
```

**What the optimizer does:**
1. Scans the leaf blocks in reverse index order (Index Range Scan Descending)
2. The moment it has collected the first 20 rows, it **stops the scan**
3. Only 20 rows get random access to the table

→ **Constant performance regardless of the total row count.** That's the power of partial range processing.

### ⚠️ Oracle's ROWNUM trap

```sql
-- ❌ Wrong: this doesn't read just 20 rows — it grabs 20 rows first, then sorts them
SELECT * FROM logs WHERE ROWNUM <= 20 ORDER BY created_at DESC;
```

- `WHERE ROWNUM` is applied **before ORDER BY**
- So you end up **fetching an arbitrary 20 rows and then sorting those** (a wrong result)

**The right way**:

```sql
-- Wrap in an inline view so ORDER BY is applied first
SELECT * FROM (
  SELECT * FROM logs ORDER BY created_at DESC
) WHERE ROWNUM <= 20;

-- Or 12c+'s FETCH FIRST
SELECT * FROM logs ORDER BY created_at DESC FETCH FIRST 20 ROWS ONLY;
```

## 5.3.4 DESC sorting and indexes

```sql
-- index: (created_at ASC)
SELECT * FROM logs ORDER BY created_at DESC;
```

The optimizer can use an **Index Range Scan Descending** to **read an ascending index in reverse**, returning a DESC result with no sort.

### Composite sorts

```sql
-- index: (created_at, user_id)
SELECT * FROM logs ORDER BY created_at DESC, user_id DESC; -- ✅ solved by a reverse scan
SELECT * FROM logs ORDER BY created_at DESC, user_id ASC;  -- ❌ mixed directions → sort required
```

- If **all sort columns share the same direction**, the sort can be skipped
- Mixed directions mean a separate sort → **consider a Descending Index** (Oracle / MySQL 8.0+)

## 5.3.5 MIN / MAX optimization

```sql
-- index: (created_at)
SELECT MIN(created_at) FROM logs;  -- reads just 1 row from the index's 'first leaf'
SELECT MAX(created_at) FROM logs;  -- reads just 1 row from the index's 'last leaf'
```

**Execution plan**:
```
INDEX FULL SCAN (MIN/MAX)
  -- or
FIRST ROW / LAST ROW optimization
```

- Reads **only the first or last leaf block of the index and returns immediately**
- The table isn't touched at all → performance on the order of **O(1)**

### ⚠️ Wrap it in a function and it breaks

```sql
SELECT MIN(YEAR(created_at)) FROM logs;  -- ❌ the function forces a Full Scan
SELECT YEAR(MIN(created_at)) FROM logs;  -- ✅ MIN first → apply the function to the result
```

## 5.3.6 Pagination tuning — the OFFSET anti-pattern

Part 3.1 already introduced this one from the access side; here's the sort-side view of why it works.

```sql
-- ❌ Anti-pattern: OFFSET 100000 LIMIT 20
SELECT * FROM logs ORDER BY created_at DESC LIMIT 20 OFFSET 100000;
```

- OFFSET 100,000 means **reading and discarding the first 100,000 rows**, then returning the next 20
- The deeper the page, the **worse the performance — linearly**

### ✅ Cursor-based paging (Keyset Pagination)

```sql
-- first page
SELECT * FROM logs ORDER BY created_at DESC LIMIT 20;

-- next page: use the last created_at value as a condition
SELECT * FROM logs
WHERE  created_at < :last_created_at
ORDER BY created_at DESC
LIMIT 20;
```

- Every page performs **the same regardless of how many rows precede it**
- Downside: **you can't jump to an arbitrary page N** (sequential movement only)
- The best-fitting pattern for infinite scroll and feeds

---

## 5.3.7 A caution for 3-tier environments

- In a modern server architecture of **client - WAS - DB**, countless clients share the server's resources
- So you must avoid situations where one client **holds a DB connection for a long time**
- **Pulling a giant result set in full and sorting it on the client** is the worst case — a cause of connection pool exhaustion
- **Finish the sort in the DB and send only the top N rows.** This is exactly where **index-based sort skipping + LIMIT** shines

---

## 🔑 Key points from this part

- An index is an **already-sorted data structure** → the `SORT ORDER BY` operator can be eliminated
- Condition for skipping the sort: **WHERE equality columns + ORDER BY columns** must **exactly match the index order**
- **ORDER BY + LIMIT** is the flagship pattern of partial range processing — constant performance regardless of total row count
- **MIN/MAX** reads only the blocks at either end of the index — O(1)-level performance
- **OFFSET paging** is an anti-pattern. Replace it with **cursor-based paging**
- Oracle's **ROWNUM + ORDER BY** demands care about ordering (use an inline view or `FETCH FIRST`)

---

### 📝 One-line takeaway

> **"Match your WHERE equality columns and ORDER BY columns to the index order, and the database hands you sorted results for free — stopping after the first N rows."**
