> The first walls you hit with a bulk INSERT/UPDATE/DELETE are **buffer cache contention** and the **Redo/Undo logging overhead** — Direct Path I/O is the standard bulk-processing technique that dodges both at once.

# 6.2 Direct Path I/O: Optimizing Bulk Data Loads

## 6.2.1 Conventional I/O vs Direct Path I/O

**Conventional I/O (Conventional Path)**

```
User SQL → buffer cache → (when needed) disk
  - Buffer cache contention occurs
  - Redo logging performed
  - Undo logging performed
  - Free List search (hunting for empty blocks)
```

**Direct Path I/O**

```
User SQL → write directly to disk (bypassing the buffer cache)
  - Skips the buffer cache
  - Redo logging minimized or skipped
  - Appends new blocks directly above the table's High Water Mark (HWM)
```

## 6.2.2 When do you use it?

- **Bulk batch INSERTs** of millions to hundreds of millions of rows
- **CTAS** (`CREATE TABLE AS SELECT`)
- **SQL*Loader Direct Path** mode
- **Parallel DML**
- When a sort result exceeds the PGA and spills into the **Temp tablespace**

## 6.2.3 How to enable it (Oracle)

```sql
-- Run an INSERT ... SELECT as Direct Path
INSERT /*+ APPEND */ INTO target_table
SELECT * FROM source_table;

-- To turn off Redo logging too (changes a table attribute)
ALTER TABLE target_table NOLOGGING;
```

## 6.2.4 The "cost" of Direct Path

It's not free — there's a price.

| What you gain | What you lose |
|---|---|
| Avoids buffer cache contention | **The session can't read the same table** (until commit) |
| Redo/Undo overhead plummets | **No media recovery** (with nologging) |
| Fast thanks to appending above the HWM | **Free space inside blocks isn't reused** → the table balloons in size |
| Plays well with parallel processing | **FKs/Triggers make Direct Path refuse to run** |

## 6.2.5 Things to watch out for

- **After a Direct Path INSERT you must COMMIT** before that table can be queried again
- **NOLOGGING carries an unrecoverable-data risk** — take a **backup** right after the batch
- **Indexes still cost you** — before a bulk load, consider the strategy of **DROP the indexes → load → rebuild**
- MySQL has no feature named Direct Path I/O, but for the same purpose you can use **`LOAD DATA INFILE`**, **`DISABLE KEYS` with `INSERT ... SELECT`**, and the like

## 6.2.6 Checklist

Ask yourself these before a bulk load.

- Is the row count **1 million or more**? (Below that, a normal INSERT is plenty)
- Does the target table have **FKs/Triggers**? → Direct Path won't work
- Does **another session need to query** the same table during the load?
- Does your **recovery policy allow NOLOGGING**?
- Can the indexes be **taken down temporarily** without affecting the service?

---

## 🔑 Key points from this part

- Direct Path = **bypass the buffer cache + minimize Redo/Undo**
- The standard answer for bulk batches, but it comes with **recovery and concurrency constraints**
- `/*+ APPEND */` + `NOLOGGING` + index drop/rebuild is the classic recipe
- In MySQL, bulk-loading tools like `LOAD DATA INFILE` get you a similar effect

---

### 📝 One-line takeaway

> **"For bulk loads, skip the buffer cache and the logging — but remember: what you save in speed, you pay for in recoverability and concurrency."**
