# 2.1 Principles of Network Applications

At the core of network application development is writing **programs that run on different end systems and communicate with each other over the network**.

For example, a Web application consists of two distinct programs that communicate with each other: a `server` (the Web server program)  
and a `client` (the browser program running on the user's host).

The important point is that **we don't need to write software that runs on network-core devices such as routers or link-layer switches**.  
(Even if we wanted to, we couldn't, because network-core devices don't function at the application layer.)

<br/>
<br/>
<br/>

# 2.1.1 Network Application Architectures

The application architecture is distinctly different from the network architecture.

From the application developer's perspective, the network architecture is fixed and provides a specific set of services to the application.

The application architecture, on the other hand, is designed by the application developer and dictates how the application is structured across the various end systems.

<br/>
<br/>

## Two well-known application architectures

<p align="center"><img width="700" alt="Application architectures" src="https://user-images.githubusercontent.com/76640167/210484607-f2096b44-08ec-4e8d-b75d-4e3df863f35d.png">

<br/>
<br/>

### Client-server architecture

- **There is an always-on server that services requests from many other hosts, called clients.**
- Clients do not communicate directly with each other.
- The server has a fixed, well-known IP address.
- When a single server can't keep up with all the requests,  
  a data center housing a large number of hosts is used to create a powerful virtual server. A typical data center has around 100,000 servers.

<br/>

### P2P architecture

- It relies minimally (or not at all) on always-on infrastructure servers.
- Instead, the application **exploits direct communication between pairs of intermittently connected hosts**, called `peers`.
- Peers are typically client devices (personal desktops, laptops, etc.).
- It's self-scalable. For example, in a file-sharing application, each peer generates workload by requesting files,  
  but each peer also adds service capacity to the system by distributing files to other peers.
- It's cost-effective, since it doesn't need things like data centers.

<br/>
<br/>
<br/>

# 2.1.2 Processes Communicating

> It's not programs that actually communicate, but processes, which are programs in execution.

Processes on two different end systems communicate with each other by exchanging messages across the computer network.

The sending process creates and sends messages, and the receiving process receives them and may respond by sending messages back.

<br/>
<br/>

## Client and server processes

A network application consists of pairs of processes that send messages to each other over a network.

<br/>

We define client and server processes as follows:

> 💡 In the context of a communication session between a pair of processes,  
> **the process that initiates the communication (initiates contact with the other process at the beginning of the session)** is the `client`,  
> and **the process that waits to be contacted to begin the session** is the `server`.

<br/>

Simply put, the process sending the request is usually called the client, and the one receiving it is called the server.

Of course, as we saw with the P2P architecture, a client can also act as a server process, and a server can also act as a client process.

<br/>
<br/>

## The interface between the process and the computer network

> A process sends messages into, and receives messages from, the network through a `socket`.

If a process is a house on the network, a socket is like its door.

<br/>

<p align="center"><img width="700" alt="Socket" src="https://user-images.githubusercontent.com/76640167/210484602-4feb26bd-c1bf-43dd-aa19-14fcac26b146.png">

<br/>
<br/>

As shown in the figure above, **a socket is the interface between the application layer and the transport layer within a host.**

Since it's the programming interface with which network applications are built on the Internet, it's also called **the API between the application and the network**.

<br/>

The application developer has full control over everything on the application-layer side of the socket, but has very little control over the transport-layer side.

The application developer's control over the transport layer is limited to:

1. Choosing the transport protocol
2. Setting a few parameters, such as the maximum buffer size and maximum segment size

<br/>
<br/>

## Addressing processes

For a process to send packets to a process running on another host, the receiving process needs to have an address.

Identifying the receiving process requires two pieces of information:

1. The address of the host, i.e., its **IP address**.
2. An identifier specifying the receiving process within that host, i.e., its **port number**. We'll cover this in more detail in Chapter 3.

<br/>
<br/>
<br/>

# 2.1.3 Transport Services Available to Applications

> The application on the sending side pushes messages through the socket,  
> and the transport protocol is responsible for moving those messages across the network to the socket of the receiving process.

<br/>

Many networks, including the Internet, provide more than one transport protocol.

Let's look at **the four services a transport protocol can offer to the applications that use it**:

- Reliable data transfer (data integrity)
- Throughput
- Timing
- Security

<br/>
<br/>

### Reliable data transfer (data integrity)

As we saw in Chapter 1, packets can get lost within a computer network.

This kind of data loss can have serious consequences.

<br/>

If **a protocol provides a guaranteed data delivery service**, it's said to provide `reliable data transfer`.

When a transport protocol provides this service, the sending process can just pass its data into the socket and be confident that the data will arrive at the receiving process without errors.

<br/>

When a transport protocol doesn't provide this service, some of the data sent by the sending process may never arrive.

Applications that can tolerate this are called loss-tolerant applications (real-time video/audio applications being the typical examples).

<br/>

### Throughput

Because other sessions share the bandwidth along the network path, and because these sessions come and go, the available throughput can fluctuate over time.

A transport protocol can provide **guaranteed available throughput** at some specified rate.

<br/>

Applications with throughput requirements are called `bandwidth-sensitive applications`, and many current multimedia applications are bandwidth-sensitive.  
(If the throughput is too low, services like telephony become impossible.)

Applications without such requirements, on the other hand, are called `elastic applications`.

<br/>

### Timing

A transport protocol can also provide timing guarantees.

For example, it might guarantee that every bit the sender pushes into the socket arrives at the receiver's socket within 100 ms.

This is mainly used for real-time applications.

<br/>

### Security

On the sending host, the transport protocol can encrypt all the data, and on the receiving host, the transport protocol can decrypt it all.

Typically, **TCP is enhanced at the application layer with TLS to provide security services.** (Covered in more detail in Chapter 8.)

<br/>
<br/>
<br/>

# 2.1.4 Transport Services Provided by the Internet

<br/>

## 1️⃣ TCP services

The TCP transport protocol provides the following three services.

<br/>

### Connection-oriented service

**Before application-layer messages start flowing, TCP has the client and server exchange transport-layer control information with each other.**

This `handshaking procedure` alerts the client and server, letting them prepare for an onslaught of packets.

<br/>

After the handshaking phase, a TCP connection is said to exist between the sockets of the two processes.

The connection is called a `full-duplex connection` because the two processes can send messages to each other over it at the same time. (More on this in Chapter 3.)

<br/>

### Reliable data transfer service

The communicating processes rely on TCP **to deliver all data sent without error and in the proper order**.

When one side of the application passes a stream of bytes into a socket, TCP delivers that same stream of bytes to the receiving socket, with no missing or duplicate bytes.

<br/>

### Congestion-control mechanism

A mechanism that throttles a sending process when the network becomes congested. (Also covered in detail in Chapter 3.)

<br/>
<br/>

## 2️⃣ UDP services

UDP is a no-frills, lightweight transport protocol with a minimal service model.

UDP is **connectionless**, so there's no handshaking, and it provides an **unreliable data transfer service**, meaning there's no guarantee the data will be delivered.

<br/>

UDP also **doesn't include a congestion-control mechanism**, so a process can pump data into the network without being throttled.

However, the end-to-end throughput can actually end up lower due to congestion.

<br/>
<br/>

## Services not provided by Internet transport protocols

TCP and UDP don't provide any throughput or timing guarantees.

Time-sensitive applications are designed to cope with this lack of throughput and timing guarantees as well as possible.

However, since there's no guarantee for when delays become excessive, there are limits to how well they can cope.

# 2.1.5 Application-Layer Protocols

> 💡 An application-layer protocol defines **how an application's processes, running on different end systems, pass messages to each other.**

<br/>

Specifically, it defines:

- The types of messages exchanged
- The `syntax` of the various message types
- The meaning of the fields, i.e., the `semantics` of the information in them
- Rules for determining when and how a process sends messages and responds to them

<br/>

Many application-layer protocols are specified in RFCs and are therefore in the public domain.

For example, if a browser developer follows the rules of the HTTP RFC, the browser can retrieve Web pages from any Web server that also follows those rules.

Many other application-layer protocols are proprietary and not available in the public domain.

<br/>

An application-layer protocol is only **one piece** of a network application.

For example, a Web application consists of many components, including a standard for document formats, Web browsers, Web servers, and an application-layer protocol (HTTP).
