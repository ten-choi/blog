# 3.7 TCP Congestion Control

The `IP layer` **provides no explicit feedback to the end systems** about network congestion.

<br/>

## 3.7.1 Classic TCP Congestion Control

> Each sender limits the rate at which it sends traffic into its connection **as a function of perceived network congestion**.

1. The TCP sender perceives little congestion on the path between itself and the destination → it increases its sending rate.
2. The TCP sender perceives congestion along the path → it reduces its sending rate.

<br/>

### 1. How does a TCP sender limit the rate at which it sends traffic into its connection?

> 💡 The TCP congestion-control mechanism running at the sender
> keeps track of an additional variable, the `congestion window`.

- Denoted `cwnd`
- Imposes a constraint on **the rate at which a TCP sender can send traffic into the network**.

<br/>

The amount of unacknowledged data at the sender
may not exceed the minimum of `cwnd` and `rwnd (the receive window = spare room in the buffer)`.

> LastByteSent - LastByteAcked **≤ min{cwnd, rwnd}**

→ So **by adjusting the value of cwnd**, the sender can adjust the rate at which it sends data into its connection.

<br/>

### 2. How does a TCP sender perceive that there is congestion on the path between itself and the destination?

> 1️⃣ When a loss event occurs

When there is excessive congestion,

1. one or more router buffers along the path overflow,
2. causing a datagram to be dropped.
3. **The dropped datagram results in a loss event at the sender.**

   (e.g., a timeout or the receipt of three duplicate ACKs)

This tells the sender that there is congestion on the path between the sender and the receiver.

<br/>

> 2️⃣ When no loss event occurs

> 💡 `Self-clocking`  
> TCP uses **acknowledgments** as a trigger (or clock) to increase its congestion window size.

- If acknowledgments arrive at a slow rate → the congestion window grows at a relatively slow rate
- If acknowledgments arrive at a high rate → the congestion window grows more quickly

<br/>

### 3. What algorithm should the sender use to change its sending rate?

*What mechanism adjusts the cwnd value that controls the sending rate?*

- If TCP senders send too fast → congestion collapse can occur.
- If TCP senders send too slowly → they underutilize the bandwidth in the network.

<br/>

TCP decides the rate at which to send based on the following three guiding principles.

<br/>

> 1️⃣ A lost segment implies congestion, so the TCP sending rate should be decreased when a segment is lost.

`A lost segment` = **congestion**

The events that trigger a retransmission of a lost segment are:

- A timeout event
- Receipt of four acknowledgments (one original ACK + three duplicate ACKs)

<br/>

> 2️⃣ The sender's rate can be increased when an ACK arrives for a previously unacknowledged segment.

`The arrival of an acknowledgment` = the network successfully delivered the sender's segment to the receiver.

In other words, it's taken as an implicit indication that the network isn't congested.

<br/>

> 3️⃣ Bandwidth probing

Given `ACKs` indicating a congestion-free source-to-destination path and `loss events` indicating a congested path,

1. the TCP sender **increases its transmission rate as ACKs arrive**, until a loss event occurs.
2. **At the point a loss event occurs, it decreases the transmission rate.**

<br/>

So

1. the TCP sender increases its transmission rate up to the point where congestion sets in,
2. backs off from that point,
3. and then starts probing again to see whether the onset of congestion has changed.

<br/>

## The TCP Congestion-Control Algorithm

Three components

1. `slow start`


2. `congestion avoidance`


3. `fast recovery` → recommended, but not required.

<br/>

## Slow Start

1. When a TCP connection begins, `cwnd` is typically initialized to 1 MSS.  
   → The initial sending rate is roughly `MSS/RTT`.


2. Since the bandwidth available to the TCP sender may be much larger than MSS/RTT, the TCP sender wants to find the amount of available bandwidth quickly.

<br/>

> In the slow-start state, `cwnd` starts at 1 MSS and  
> **increases by 1 MSS** **every time a transmitted segment is first acknowledged.**

<br/>

As shown below, this makes the TCP sending rate grow exponentially.

<p align="center"><img width="380" alt="TCP slow start" src="https://user-images.githubusercontent.com/86337233/211625835-f36ebe84-04de-4091-86a2-fcedfb50fe4f.png">

<br/>
<br/>

### When slow start ends

When does this exponential growth end?

There are three cases.

<br/>

> 1️⃣  When there is a loss event (congestion) indicated by a **timeout**

1. The TCP sender sets `cwnd` to **1** MSS
2. and begins **a new slow start**.

<br/>

> 2️⃣ When cwnd equals **ssthresh**

1. **Slow start ends**
2. and TCP transitions into `congestion avoidance mode`.

<br/>

- `ssthresh (slow start threshold)` is a second state variable, set to `cwnd/2`.  
  (= half the value of the congestion window when congestion was detected)


- In `congestion avoidance mode`, TCP increases `cwnd` more cautiously.

<br/>

> 3️⃣ When **duplicate ACKs** are detected

- TCP performs a fast retransmit and enters the fast recovery state.

<br/>

## Congestion Avoidance

On entering the congestion-avoidance state, `cwnd` is roughly **half its value when congestion was last encountered**.

> In the `congestion-avoidance state`, TCP typically increases `cwnd` by just one MSS every RTT.

That is, each time a new acknowledgment arrives, `cwnd` is increased by <b>MSS·(MSS/cwnd) bytes</b>.

<br/>

### When congestion avoidance ends

When should congestion avoidance's linear increase (1 MSS per RTT) end?

<br/>

When a **timeout** occurs, TCP's congestion-avoidance algorithm behaves the same as in slow start:

> `cwnd` is set to **1 MSS**,
> and `ssthresh` is set to **half the value of cwnd when the loss event occurred**.

<br/>

However, a loss event can also be triggered by a triple duplicate ACK event,  
*in which case the network is still delivering segments from the sender to the receiver.*

<br/>

So for this type of loss event, TCP

1. halves the value of `cwnd` at the point the three duplicate ACKs are received,
2. records `ssthresh` as `half the value of cwnd`,
3. and then enters the `fast-recovery state`.

<br/>

## Fast Recovery

> In the `fast-recovery state`, `cwnd` is increased by `1 MSS`
> for every duplicate ACK **received for the missing segment**.

Here, the missing segment is the one that caused TCP to enter the fast-recovery state.

<br/>

1. **When an ACK arrives for the missing segment**, TCP enters the congestion-avoidance state (after deflating `cwnd`).


2. If a timeout event occurs, fast recovery performs the same actions as in slow start and congestion avoidance, then transitions to slow start.
   > That is, `cwnd` is set to **1 MSS**, and `ssthresh` is set to **half the value of cwnd when the loss event occurred**.

<br/>

Fast recovery is a recommended, but not required, component.

- `TCP Tahoe (an early version of TCP)`  
  : whenever a loss occurs — whether indicated by a timeout or by three duplicate ACKs —
    1. it unconditionally cuts its congestion window to 1 MSS
    2. and enters the **slow-start phase**.


- `TCP Reno (a newer version of TCP)` incorporated **fast recovery**.

<br/>

The graph below shows how TCP's congestion window evolves for Reno and Tahoe.

<br/>

<p align="center"><img width="500" alt="Evolution of TCP's congestion window" src="https://user-images.githubusercontent.com/86337233/211625839-e0b75f39-a78a-4265-aad1-b9382257e8de.png">

<br/>

When a loss event occurs,

- `TCP Reno`
    1. sets the congestion window to 9•MSS
    2. and then **grows it linearly.**


- `TCP Tahoe`
    1. sets the congestion window to **1 MSS**,
    2. **grows it exponentially until it reaches ssthresh**,
    3. and grows it linearly after that.

<br/>

## TCP Congestion Control: Retrospective

- Ignoring the initial slow-start period when a connection begins,
- and assuming that losses are indicated by triple duplicate ACKs rather than timeouts,

> 💡 TCP's congestion control consists of  
> a **linear (additive) increase in cwnd** of 1 MSS per RTT  
> and <b>a halving (multiplicative decrease) of cwnd</b> on a triple duplicate-ACK event.

→ For this reason, TCP congestion control is often referred to as an `additive-increase, multiplicative-decrease (AIMD)` form of congestion control.

<br/>

1. TCP **linearly increases its congestion window size (and hence its transmission rate)** until a triple duplicate-ACK event occurs.
2. It then **decreases** its congestion window size,
3. but then again begins **increasing it linearly**, `probing` to see if there's additional available bandwidth.

<br/>

<p align="center"><img width="500" alt="AIMD congestion control" src="https://user-images.githubusercontent.com/86337233/211625842-798c4c59-a967-4847-b29f-4e4a3ebfcc32.png">

<br/>

### TCP CUBIC

> If the state of the congested link where packet loss occurred hasn't changed much,  
> it's better to **ramp the sending rate up more quickly to get close to the pre-loss sending rate**, and only then probe cautiously for bandwidth.

<br/>

It increases the congestion window only on ACK receipt, and its slow-start and fast-recovery phases are the same as TCP Reno's,  
but the congestion-avoidance phase is modified as follows.

<br/>

> ✅ A few tunable CUBIC parameters determine how quickly (`K`) the protocol's congestion window size reaches `Wmax`.

- `Wmax`: the size of TCP's congestion window when loss was last detected
- Time `K`: **the future point in time when TCP CUBIC's window size will again reach Wmax**, assuming no losses

<br/>

> ✅ CUBIC **increases the congestion window as a function of the cube** of the distance between the current time `t` and `K`.

→ **The congestion window grows much more when `t` is far from `K`** than when it's close.

<br/>

In other words,

1. CUBIC quickly ramps up TCP's sending rate to get close to `Wmax`, the pre-loss rate,
2. and **then probes cautiously for bandwidth as it approaches** `Wmax`.

<br/>

> ✅ If the congestion level of the link that caused the loss has changed significantly, CUBIC can find a new operating point more quickly.

- `When t is close to K`, CUBIC's congestion-window increase is small.  
  (This is good if the congestion level of the link that caused the loss hasn't changed much.)
- `As t greatly exceeds K`, **the congestion window grows rapidly.**

<br/>

<br/>

The slow-start phase ends at `t0`,  
and when congestion losses occur at `t1`, `t2`, and `t3`, CUBIC **ramps back up toward `Wmax` more quickly.**

→ As a result, TCP CUBIC enjoys higher overall throughput.

TCP CUBIC tries to keep the flow just below the congestion threshold for as long as possible.

## 3.7.2 Network-Assisted Explicit Congestion Notification and Delay-Based Congestion Control

Since slow start and congestion avoidance were first standardized in the late 1980s, TCP has implemented an `end-to-end form of congestion control`.

More recently, however, extensions to IP and TCP have been proposed, implemented, and deployed **that let the network explicitly signal congestion to the TCP sender and receiver** (`network-assisted congestion control`).

There have also been proposed variants of the TCP congestion-control protocol that infer congestion from measured packet delay.

<br/>

## Explicit Congestion Notification (ECN)

A form of `network-assisted congestion control` performed within the Internet.

<br/>

At the network layer, two bits in the **Type of Service field** of the IP datagram header are used for ECN.

> 💡 A **congestion indication bit is set** to notify the sender of the onset of congestion before loss occurs.

<br/>

<p align="center"><img width="600" alt="Explicit Congestion Notification" src="https://user-images.githubusercontent.com/86337233/211625847-eee59d74-7fa9-4570-adf2-2d007837b231.png">

<br/>
<br/>

### Setting the ECN bits

One setting of the ECN bits is used by a router **to indicate that it is experiencing congestion**.

→ This congestion indication is carried in the marked `IP datagram` to the destination host, which then informs the sending host, as shown in the figure above.

<br/>

The second setting of the ECN bits is used by the sending host to tell routers that

- the sender and receiver are ECN-capable,
- and are therefore able to take action in response to ECN-indicated network congestion.

<br/>

### How it works

> 💡 A router experiencing congestion
> can set a `congestion indication bit` to signal the onset of congestion to senders  
> **before** its buffers fill up and packets get dropped.

1. When TCP at the receiving host gets an `ECN congestion indication` **via a received datagram**,


2. TCP at the receiving host **informs TCP at the sending host of the congestion indication**  
   by setting the `ECE (Explicit Congestion Notification Echo) bit`  
   **in a receiver-to-sender TCP ACK segment**.


3. The TCP sender reacts to the ACK carrying the congestion indication by **halving its congestion window**,


4. and sets the `CWR (Congestion Window Reduced) bit` to **1** **in the header of the next transmitted TCP sender-to-receiver segment**.

<br/>

## Delay-Based Congestion Control

> Detects the onset of congestion **proactively**, before packet loss occurs

<br/>

> `TCP Vegas` operates on the principle that
> **a TCP sender should keep the pipe full, but no fuller**.

In other words, once the pipe is full, there's nothing to gain (and only harm) from letting large queues build up.

<br/>

- TCP Vegas measures the source-to-destination path's `RTT` for every acknowledged packet.


- RTTmin: the minimum of the RTT values measured at the sender

<br/>

- If the actual sender-measured throughput is close to `cwnd/RTTmin`,
    - the path isn't congested yet,
    - so the TCP sending rate can be increased.


- If the actual sender-measured throughput is **significantly less than the uncongested throughput**,
    - the path is congested,
    - and **the TCP Vegas sender decreases its sending rate.**

<br/>
<br/>

## 3.7.3 Fairness

Consider `K` TCP connections, each with a different end-to-end path, but all passing through a `bottleneck link` **with a transmission rate of** `R bps`.

<br/>

Assuming each connection is transferring a large file and there's no UDP traffic passing through the bottleneck link,

> a congestion-control mechanism is said to be **fair** if the average transmission rate of each connection is approximately `R/K`.  
> That is, each connection gets **an equal share** of the link bandwidth.

<br/>

Let's look at two TCP connections sharing a single link with transmission rate `R`, as shown below.

<br/>

<p align="center"><img width="570" alt="Bottleneck link" src="https://user-images.githubusercontent.com/86337233/211625853-ca717317-75e6-47ec-ac70-971a8f475fcf.png">

<br/>
<br/>

Assumptions

- The two connections have `the same MSS and RTT`.  
  **→ If they have the same congestion window size, they'll have the same throughput.**
- They have a large amount of data to send.
- We ignore TCP's slow-start behavior.
- The TCP connections always operate in `congestion-avoidance mode`.

<br/>

The throughput realized by TCP connections 1 and 2 can be plotted as follows.

<br/>

<p align="center"><img width="360" alt="Throughput" src="https://user-images.githubusercontent.com/86337233/211625855-65fb1a01-7341-46a3-85d6-1e38f5e0be51.png">

<br/>
<br/>

- If TCP shares the link bandwidth equally between the two connections,  
  the realized throughput should fall along the 45º arrow (equal bandwidth share) emanating from the origin.
- Ideally, the sum of the two throughputs should equal R.

<br/>

→ The goal: **achieve throughputs near the intersection of the equal-bandwidth-share line and the full-bandwidth-utilization line**

<br/>

---

<br/>

1️⃣ Suppose that at some point in time, the TCP window sizes are such that connections 1 and 2 realize the throughputs indicated by `point A`.

- Because the amount of link bandwidth jointly consumed by the two connections is less than R,  
  **no loss will occur.**


- Both connections will **increase their windows by 1 MSS per RTT** as a result of the `TCP congestion-avoidance algorithm`.

<br/>

So the joint throughput of the two connections proceeds along a 45º line starting from point A,

2️⃣ and eventually **the link bandwidth jointly consumed by the two connections will exceed R → packet loss occurs**.

(Suppose packet loss is experienced when they realize the throughputs indicated by `point B`.)

<br/>

So connections 1 and 2 **decrease their windows by half**.

<br/>

3️⃣ The resulting throughputs are at `point C`, halfway between B and the origin.

Since the joint bandwidth use is less than R at point C,  
the two connections again increase their throughputs along a 45º line starting from C.

<br/>

4️⃣ Eventually loss will occur again (`point D`), and the two connections again halve their window sizes.

<br/>

> In other words, the bandwidth realized by the two connections eventually **fluctuates along** the `equal bandwidth share line`,  
> and **converges** to it regardless of where they start in the two-dimensional space.


*→ This gives an intuitive feel for why TCP shares bandwidth equally among connections.*

<br/>

---

<br/>

Unlike the idealized scenario above,  
in practice client-server applications can obtain **very different portions of link bandwidth**.

<br/>

In particular, when multiple connections share a common bottleneck link,

- sessions with a smaller RTT can grab the available bandwidth at that link **more quickly as it becomes free**,
- and so they enjoy higher throughput than connections with larger RTTs.

<br/>

### Fairness and UDP

UDP doesn't have congestion control.

<br/>

From TCP's perspective, multimedia applications running over UDP aren't being fair.

**They don't cooperate with other connections, nor do they adjust their transmission rates appropriately.**

<br/>

Because TCP congestion control decreases its transmission rate in the face of increasing congestion (loss),  
**UDP sources, which don't have to, can crowd out TCP traffic.**

→ We need congestion-control mechanisms for the Internet that prevent UDP traffic from bringing it to a halt.

<br/>

### Fairness and parallel TCP connections

Even if UDP traffic could be forced to behave fairly,  
the fairness problem still wouldn't be completely solved, because there's nothing to stop `TCP-based applications from using multiple parallel connections`.

When an application uses multiple parallel connections, **it gets a larger share of the bandwidth on a congested link.**
