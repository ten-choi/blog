# 3.3 Connectionless Transport: UDP

> 💡 UDP does about as little as a transport-layer protocol can do.

- Multiplexing/demultiplexing
- Light error checking

Beyond that, it adds nothing to IP.

<br/>
<br/>

## How It Works

1. It takes a message from the application process and attaches  
   the `source port number field` and `destination port number field` needed for multiplexing/demultiplexing.


2. After adding the `source host IP address field` and `destination host IP address field`,  
   it passes the resulting transport-layer segment down to the network layer.


3. The network layer encapsulates the transport-layer segment into an IP datagram  
   and delivers the segment to the receiving host.


4. When the segment arrives at the receiving host,  
   UDP uses the `destination port number` to deliver the segment's data to the right application process.

<br/>

> 💡 UDP **does no handshaking** between the sending and receiving transport-layer entities before sending a segment.

→ `Connectionless`

<br/>

### DNS

DNS is a typical example of an application-layer protocol that uses UDP.

If the querying host doesn't get a reply, it either sends the query to another name server or tells the application that it couldn't get a response.

<br/>
<br/>

## Advantages of UDP

Many applications are a better fit for UDP for the following reasons.

<br/>

### Finer application-level control over what data is sent, and when

With UDP, **as soon as** an application process hands data to UDP,  
UDP packages it into a UDP segment and immediately passes the segment to the network layer.

> **Real-time** applications can use UDP and **implement whatever extra functionality they need on top of it.**

<br/>

↔︎ `TCP`

1. Has a **congestion-control mechanism**.  
   That is, it **throttles** the transport-layer TCP sender when one or more links between the source and destination hosts become excessively congested.


2. Keeps retransmitting a segment **until the destination acknowledges receipt**,  
   no matter how long reliable delivery takes.

<br/>

### No connection establishment

UDP just blasts away without any formal preliminaries like TCP's three-way handshake.

**So UDP introduces no delay to establish a connection.**

<br/>

#### No connection state

UDP doesn't maintain connection state and doesn't track any connection-state parameters.

As a result, a server devoted to a particular application can typically support  
many more active clients when the application runs over UDP.

<br/>

#### Small packet header overhead

TCP has 20 bytes of header overhead per segment, while UDP has only 8 bytes.

<br/>
<br/>

## Disadvantages of UDP

UDP doesn't do `congestion control`.

> 💡 `Congestion control` is essential to keep the network from falling into a congested state where it can't do any useful work.

<br/>

If everyone started streaming high-bit-rate video without any congestion control,

- Routers would see massive packet overflow  
  → only a few UDP packets would make it through the source-to-destination path.


- The high loss rates caused by uncontrolled UDP senders would make TCP senders slow down to reduce those losses  
  → TCP sessions would get congested.

<br/>
<br/>

## Reliable Data Transfer over UDP

UDP provides an unreliable service, but  
**if the application itself provides reliability**, reliable data transfer is possible while still using UDP.

<br/>

e.g., the `QUIC (Quick UDP Internet Connections) protocol` used in Google's Chrome browser

It uses UDP as its underlying transport protocol and implements reliability in an application-layer protocol on top of UDP.

<br/>
<br/>
<br/>

### Application data

Occupies the data field of the UDP datagram.

<br/>

### Port numbers

Let the destination host hand the application data to the correct process running on the destination end system (i.e., perform demultiplexing).

<br/>

### Checksum

Used by the receiving host to check whether errors have been introduced into the segment.

<br/>

### Length field

Specifies the length of the UDP segment, including the header, in bytes.

<br/>

# 3.3.2 UDP Checksum

> The `UDP checksum` provides error detection: it **checks whether bits within the UDP segment have been altered**  
> as the segment moved from source to destination.

<br/>

1. On the sender side, UDP **takes the 1s complement of the sum of all the 16-bit words** in the segment,  
   with any overflow during the sum wrapped around.


2. The result is put in the checksum field of the UDP segment.


3. At the receiver, **all 16-bit words, including the checksum, are added together.**


4. If the packet has no errors, the sum at the receiver will be `1111111111111111`;  
   if `any bit is 0`, an error has been introduced into the packet.

<br/>
<br/>

## Why Does UDP Provide a Checksum?

Because **there's no guarantee that every link between source and destination provides error checking.**

And even if segments are transferred correctly across a link, bit errors can be introduced while a segment is stored in a router's memory.

<br/>

> 💡 UDP provides error checking, but **does nothing to recover from an error.**

It either just discards the damaged segment or passes it to the application with a warning.  
_(How it's handled depends on the implementation.)_

<br/>

---

<br/>

Since neither link-by-link reliability nor in-memory error detection is guaranteed, if the end-to-end data transfer service is to provide error detection,  
**UDP must provide error detection at the transport layer, on an end-end basis.**

→ This is an example of the `end-end principle`.

<br/>

### The end-end principle

Functions placed at lower levels may be redundant or of little value compared to the cost of providing them at a higher level.
