# 4.2 What's Inside a Router?

<p align="center"><img width="500" alt="Router architecture" src="https://user-images.githubusercontent.com/76640167/212551546-16b6533b-58ec-421a-9863-e7d581e0cb41.png">

The figure above shows the architecture of a router.

- `Input ports`
  - The **leftmost and rightmost boxes of an input port terminate the incoming physical link at the router, performing physical-layer functions**.
  - An input port also **performs the link-layer functions needed to interoperate with the link layer on the other side of the incoming link**. These are shown as the middle boxes in the input and output ports.
  - The most important function is the **lookup**, performed at the rightmost part of the input port. Here the router **consults the forwarding table to determine the output port to which an arriving packet will be forwarded via the switching fabric**.
  - `Control packets`, which carry routing protocol information, are forwarded from the input port to the routing processor.
  - Note that "port" here is different from the (software) ports discussed earlier.
- `Switching fabric`
  - The switching fabric **connects the router's input ports to its output ports**.
  - It lives entirely inside the router.
- `Output ports`
  - An output port **stores packets received from the switching fabric and transmits them on the outgoing link, performing the necessary link-layer and physical-layer functions**.
  - When a link is bidirectional, the output port is typically paired with the input port for that same link.
- `Routing processor`
  - Performs **control-plane functions**.
  - In traditional routers, it runs the routing protocols, maintains routing tables and attached link state information, and computes the router's forwarding table.
  - In SDN routers, the routing processor communicates with the remote controller to receive forwarding table entries computed by that controller, and installs those entries in the router's input ports.
  - It also performs network management functions.

A router's input ports, output ports, and switching fabric are almost always implemented in hardware.

The control plane is usually implemented in software and runs on the routing processor (typically a conventional CPU).

<br/>

## 4.2.1 Input Port Processing and Destination-Based Forwarding

<p align="center"><img width="700" alt="Input port processing" src="https://user-images.githubusercontent.com/76640167/212552679-134bbf97-c8fd-452c-a6dc-283454e8d745.png">

The input port's functions are as described above.

The lookup performed at the input port is central to how a router works.

The router uses the forwarding table to look up the output port to which an arriving packet will be forwarded via the switching fabric.

The forwarding table is either computed and updated by the routing processor or received from a remote SDN controller.

As in the top figure, the forwarding table is copied from the routing processor to each line card. Because each line card uses its own copy, the router doesn't have to call the centralized routing processor on a per-packet basis, which avoids a bottleneck.

<br/>

### Forwarding Table by Destination Address Range

With 32-bit IP addresses, a naive forwarding table would need one entry for every possible destination address. That's more than 4 billion entries, which is simply not feasible.

Suppose a router has four links, numbered 0 through 3.

<p align="center"><img width="500" alt="Destination address ranges" src="https://user-images.githubusercontent.com/76640167/212553661-aa22e2b5-353c-4cba-95e6-66ae79c2968e.png">

If we build the forwarding table from destination address ranges, a table with just four entries is enough.

<br/>

### Prefix-Based Forwarding Table

<p align="center"><img width="500" alt="Prefixes" src="https://user-images.githubusercontent.com/76640167/212553874-8c0c057e-f9a2-4533-bf21-c2196fa6e4fc.png">

With this kind of forwarding table, the router matches a `prefix` of the packet's destination address against the entries in the table.

For example, if the packet's destination address is `11001000 00010111 00010110 10100001`, its first 21 bits match the first entry in the table, so the router forwards the packet to link interface 0.

When an address like `11001000 00010111 00011000 10101010` matches more than one entry (its first 24 bits match the second entry and its first 21 bits match the third), the router uses the `longest prefix matching rule`.

That is, it finds the longest matching entry in the table and forwards the packet to the link interface associated with it. (Section 4.3 explains why.)

<br/>

Beyond the table design, lookups must be performed in nanoseconds, so other techniques are needed too.

Memory access time needs special attention, which calls for designs combining embedded on-chip DRAM with faster SRAM. In practice, TCAMs (Ternary Content Addressable Memories) are also often used for lookup.

Once the lookup determines a packet's output port, the packet can be sent into the switching fabric. In some designs, a packet may be temporarily blocked from entering the switching fabric if packets from other input ports are currently using it.

We'll look at blocking, queuing, and scheduling of packets in more detail later.

<br/>

## 4.2.2 Switching

The switching fabric is the heart of a router, because it's the path through which packets are actually switched from input ports to output ports.

Here are several ways switching can be done.

<br/>

### Switching via Memory

<p align="center"><img width="400" alt="Memory" src="https://user-images.githubusercontent.com/76640167/212554598-53215480-9612-413e-8d8f-e628878e60d1.png">

The earliest routers were traditional computers in which switching between input and output ports was done under direct control of the routing processor. The input and output ports functioned like I/O devices.

How a packet is forwarded:
1. When a packet arrives, the input port signals the routing processor with an interrupt, and the packet is copied into processor memory.
2. The routing processor extracts the destination address from the header.
3. It looks up the appropriate output port in the forwarding table, then copies the packet into the output port's buffers.

If memory bandwidth allows at most B packets per second to be written into or read from memory, the overall forwarding throughput must be less than B/2. Also, two packets can't be forwarded at the same time, even if they have different destination ports, because only one memory read/write can be done at a time over the shared system bus.

Modern routers that switch via memory perform the destination lookup and the storing of the packet into the right memory location directly on the input line cards.

<br/>

### Switching via a Bus

<p align="center"><img width="400" alt="Bus" src="https://user-images.githubusercontent.com/76640167/212554625-96f849a2-311f-4df7-a994-e4877392fd18.png">

The input port transfers a packet directly to the output port over a shared bus, without intervention by the routing processor.

This is typically done by having the input port prepend a switch-internal label (header) to the packet that indicates the local output port, and then transmitting the packet onto the bus.

All output ports receive the packet, but only the port whose label matches keeps it.

The label is then removed at the output port, since it's only used to cross the bus.

If multiple packets arrive at different input ports at the same time, all but one must wait, because only one packet can cross the bus at a time.

Since every packet must cross the single bus, the router's switching speed is limited by the bus speed.

<br/>

### Switching via an Interconnection Network

<p align="center"><img width="400" alt="Interconnection network" src="https://user-images.githubusercontent.com/76640167/212554641-56fbdfcb-c50d-4b60-8b2e-b61e85bf0e5f.png">

A crossbar switch is an interconnection network made of 2N buses that connect N input ports to N output ports.

Each vertical bus intersects each horizontal bus at a crosspoint, which the switch fabric controller can open or close at any time.

Unlike the previous two approaches, this lets a crossbar switch forward multiple packets in parallel.

However, if two packets from two different input ports are headed to the same output port, one has to wait, because only one packet can be sent over a given bus at a time.

More sophisticated interconnection networks use multi-stage switch fabrics built from multiple stages of switching elements, so packets from different input ports can be forwarded to the same output port simultaneously.

<br/>

## 4.2.3 Output Port Processing

<p align="center"><img width="500" alt="Output port processing" src="https://user-images.githubusercontent.com/76640167/212600107-7721ba99-bd00-4f26-b815-cc9bb0324f23.png">

Output port processing, shown above, takes packets stored in the output port's memory and transmits them over the output link. This includes selecting and de-queuing packets for transmission, and performing the needed link-layer and physical-layer transmission functions.

<br/>

## Where Does Queuing Occur?

Packet queues can form at both input ports and output ports.

Where queues form and how large they get depends on the traffic load, the relative speed of the switching fabric, and the line speed.

As these queues grow, the router's memory can eventually be exhausted, and packet loss occurs when there's no memory left to store arriving packets.

<br/>

### Input Queuing

What happens if the switching fabric isn't fast enough to transfer every arriving packet through without delay?

In that case, packets have to wait their turn to be transferred through the switching fabric to the output port.

To see the consequences of this queuing, assume a crossbar switching fabric where:

1. All links run at the same speed.
2. One packet can be transferred from an input port to a given output port in the same amount of time it takes for a packet to be received on an input link.
3. Packets move from input queues to output queues in FCFS (First-Come-First-Served) order.

Multiple packets can be transferred in parallel as long as their output ports differ. But if they share the same output port, only one packet can be sent to it, and the others have to wait.

<p align="center"><img width="500" alt="HOL blocking at an input-queued switch" src="https://user-images.githubusercontent.com/76640167/212602449-2614d598-c84d-4b78-a5ff-0214177ef831.png">

In the figure above, suppose the packet at the front of the upper-left queue is sent first.

The packet at the front of the lower-left queue has the same output port, so it has to wait. The second packet in that queue also has to wait because of the packet in front of it, even though its output port is different.

This is called `HOL (Head-of-the-Line) blocking` in an input-queued switch.

<br/>

### Output Queuing

Suppose there are N input ports and N output ports, each with speed R, the switch is N times faster than R, and packets from every input port are headed to the same output port.

In that case, in the time it takes to send a single packet on the output link, N new packets arrive at the output port. Since the output port **can only transmit one packet per unit of time, the N arriving packets have to wait in the transmission queue for the output link**.

When there isn't enough queue space, i.e., **when memory runs out, the router must either drop the arriving packet or remove one or more already-queued packets to make room for the new one**.

<p align="center"><img width="500" alt="Output port queuing" src="https://user-images.githubusercontent.com/76640167/212603601-f01b85d9-bb51-4a28-a27c-8307944f57ef.png">

The figure above shows an example of output port queuing.

Because of this queuing, the output port's `packet scheduler` has to choose one of the queued packets for transmission and remove it from the queue. (Covered in the next section.)

<br/>

### How Much Buffering Is Required?

For many years, the rule of thumb for buffer sizing from RFCs was that the amount of buffering B should equal the average round-trip time (RTT) times the link capacity C.

In other words, you need `B = RTT × C` worth of buffering.

More recent theoretical and experimental work suggests that when a large number N of independent TCP flows pass through a link, the buffering needed is `B = RTT × C / √N`.

<br/>

Larger buffers let the router absorb bigger fluctuations in the packet arrival rate and reduce its packet loss rate, but you also have to account for the longer queuing delays that come with them.

For example, increasing per-hop buffering tenfold to reduce packet loss also increases end-to-end delay tenfold.

So **growing the buffer is a double-edged sword: it can lower the packet loss rate, but it can also increase end-to-end delay**.

<br/>

<p align="center"><img width="700" alt="Bufferbloat" src="https://user-images.githubusercontent.com/76640167/212605581-8462495b-98e5-4fe3-a101-380a9c2955aa.png">

Consider a router at the edge of the network.

(a) depicts a home router sending TCP segments to a remote game server. Assume it takes 10 ms to transmit a packet containing the gamer's TCP segment, and that queuing delay is negligible.

Separately, suppose delays elsewhere on the path to the game server make the RTT 200 ms.
(This RTT condition is a separate assumption from the transmission delay condition in Figure 4.10(a).)

As in (b), suppose a burst of 25 packets arrives at the queue at t = 0.

The queued packets are transmitted one every 10 ms, and at t = 200 ms the 21st packet is being transmitted. At this point the first ACK arrives, which causes the sender to send a new packet.

The next ACK arrives at t = 210 ms at the home router's outgoing link, so another TCP segment is sent by the gamer and added to the queue. From then on, each ACK that arrives causes a new packet to arrive at the queue.

With this ACK clocking, one new packet arrives at the queue each time a queued packet is sent, so the queue always holds 5 packets.

In other words, **the end-to-end pipe is full, but the queuing delay stays constant and persistent**.

As a result, the gamer can't understand why delays stay long even though there's no other traffic on the home network.

This excessively long delay caused by persistent buffering is called bufferbloat.

To combat it, the DOCSIS 3.1 standard for cable networks (covered in Chapter 6) added an AQM (Active Queue Management) mechanism that reduces delay while preserving bulk throughput performance.

<br/>

## 4.2.5 Packet Scheduling

### FIFO

<p align="center"><img width="500" alt="FIFO queuing abstraction" src="https://user-images.githubusercontent.com/76640167/212629160-ffa328ee-fe9d-424e-bbc5-4de9711f8ea2.png">

If the link is currently busy transmitting another packet, a packet arriving at the output link queue waits for transmission.

If there isn't enough buffer space to hold the arriving packet, the queue's packet-discarding policy decides whether the packet is dropped or whether other packets are removed from the queue to make room for it.


<p align="center"><img width="700" alt="FIFO queue in operation" src="https://user-images.githubusercontent.com/76640167/212629250-0ba3b79f-32d6-4cf4-b183-cb1f302fbce1.png">

The FIFO scheduling discipline selects packets for transmission on the output link in the same order in which they arrived at the output link queue.

The figure above shows a FIFO queue in operation.

<br/>

### Priority Queuing

<p align="center"><img width="500" alt="Priority queue model" src="https://user-images.githubusercontent.com/76640167/212632896-9184e337-91f4-4277-9b70-31d4ab83794d.png">

With priority queuing, packets arriving at the output link are classified into priority classes.

In practice, a network operator might configure the queue so that packets carrying network management information get priority over user traffic.

When choosing a packet to transmit, the scheduler sends a packet from the highest-priority class that has a non-empty queue.

Among packets of the same priority class, the choice is made in FIFO order.

<p align="center"><img width="700" alt="Priority queue in operation" src="https://user-images.githubusercontent.com/76640167/212632989-2c0b97aa-6ff9-4a51-b81a-a5af83ff29ff.png">

The figure above shows a queue with two priority classes.

Packets 1, 3, and 4 are high priority, so they're sent first.

Because this is `non-preemptive priority queuing`, once transmission of packet 2 has started, packet 4 doesn't preempt it even though it has higher priority; it's sent only after packet 2 finishes.

<br/>

### Round Robin and WFQ

Under the round robin queuing discipline, packets are sorted into classes as in priority queuing, but there's no strict service priority among classes. Instead, a round robin scheduler alternates service among the classes.

In the simplest form of round robin scheduling, the scheduler just takes turns sending a packet from each class.

A `work-conserving queuing` discipline never lets the link sit idle while there are packets queued for transmission.

That is, if a class has no packets, the scheduler immediately checks the next class in the sequence.

<p align="center"><img width="700" alt="Round robin in operation" src="https://user-images.githubusercontent.com/76640167/212637669-4db8f860-ae58-42b6-b341-5d83b3e93afb.png">

The figure above shows a round robin queue in operation.

<br/>

<p align="center"><img width="500" alt="WFQ" src="https://user-images.githubusercontent.com/76640167/212637698-f2ae0e82-3448-4012-b0af-cbe113979350.png">

A generalized form of round robin queuing that's widely implemented in routers is the so-called `WFQ (Weighted Fair Queuing) discipline`.

Arriving packets are classified and queued in the appropriate per-class waiting area.

The WFQ scheduler serves classes **in a circular manner, like round robin**.

It's also a **work-conserving queuing discipline**.

In WFQ, each class i is assigned a weight w(i).

While it has packets to send, class i is guaranteed a fraction `w(i) / ∑w(j)` of service time, where the sum in the denominator is taken over all classes that have packets queued for transmission.

So even in the worst case, when every queue has packets, class i is still guaranteed that share.

Therefore, on a link with transmission rate R, class i always achieves a throughput of at least `R × w(i) / ∑w(j)`.

This description assumes an idealized case where packets are treated as fluid units of data and transmitting one packet doesn't interfere with transmitting another.
