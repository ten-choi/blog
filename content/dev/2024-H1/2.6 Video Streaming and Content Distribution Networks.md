# 2.6 Video Streaming and Content Distribution Networks

<br/>

# 2.6.1 Internet Video

A video is a sequence of images, typically displayed at a constant rate of 24 to 30 images per second.

An uncompressed, digitally encoded image consists of an array of pixels, with each pixel encoded into a number of bits representing luminance and color.

<br/>

An important characteristic of video is that it can be compressed, trading off video quality against bit rate.

Today's off-the-shelf compression algorithms can compress a video to essentially any bit rate desired. (The higher the bit rate, the better the image quality.)

<br/>

From a networking perspective, the most salient characteristic of video is its high bit rate.

Internet video typically ranges from 100 kbps to over 4 Mbps for streaming high-definition video.

4K streaming is expected to need bit rates above 10 Mbps. This means high-end video requires an enormous amount of traffic and storage.

<br/>

To provide continuous playout, the network must provide the streaming application with an average throughput at least as large as the bit rate of the compressed video.

→ Compression can be used to create multiple versions of the same video at different quality levels.

<br/>
<br/>
<br/>

# 2.6.2 HTTP Streaming and DASH

> In HTTP streaming, a video is simply stored on an HTTP server as an ordinary file with a specific URL.

1. The client establishes a TCP connection with the server and issues an HTTP GET request for that URL.
2. The server sends the video file within an HTTP response message, as fast as the underlying network protocols and traffic conditions allow.
3. The received bytes are collected in an application buffer.
4. Once the number of bytes in the buffer exceeds a predetermined threshold, playback begins.

Specifically, the client periodically grabs video frames from the buffer, decompresses them, and displays them on the user's screen.

<br/>

### The Problem

Every client receives the same encoding of the video, even though the available bandwidth varies from client to client.

This problem led to the development of a new kind of HTTP-based streaming: `DASH (Dynamic Adaptive Streaming over HTTP)`.

<br/>
<br/>

## DASH

> The video is encoded into several different versions, each with a different bit rate and quality level.

The client dynamically requests chunks of video segments, each a few seconds long, from the different versions.

When the available bandwidth is high, it requests chunks from a high-bit-rate version; when bandwidth is low, it requests chunks from a low-bit-rate version.

In other words, the client requests the version that fits its current conditions.

<br/>

Each video version is stored on the HTTP server under a different URL.

The HTTP server has a `manifest file` that provides a URL for each version along with its bit rate.

The client first fetches this manifest file,  
then each time selects the chunk from the version it wants and requests it by specifying the URL and a byte range in an HTTP GET request message.

<br/>

Ultimately, DASH lets the client freely switch among different quality levels.

<br/>
<br/>

# 2.6.3 Content Distribution Networks (CDNs)

## The Simplest Way to Provide an Internet Video Streaming Service

> Build a single massive data center, store all the videos there, and stream them directly from the data center to users all over the world.

<br/>

### Problems

1. If a client is far from the data center, packets pass through many communication links and ISPs,  
   and if any one of those links has a transmission capacity lower than the video consumption rate, it becomes a bottleneck.
2. A popular video will likely be sent many times over the same communication links, so you end up paying repeatedly to send the same bytes.
3. A single failure can take down the entire service.

To solve these problems, most video streaming companies use `Content Distribution Networks (CDNs)`.

<br/>
<br/>

## CDN

> A CDN operates servers distributed across many locations and stores copies of videos and other web content on these distributed servers.

Each user is directed to the CDN location that will provide the best user experience.

A CDN can be a private CDN, like Google's, or the service can be delivered through a CDN operated by a third party.

<br/>

### Two Philosophies for CDN Server Placement

CDNs typically adopt one of two philosophies:

- Enter Deep
- Bring Home

<br/>

#### Enter Deep

> push CDN servers deep into many access networks

Pioneered by Akamai, this approach deploys server clusters in access networks all over the world, entering deep into ISPs' access networks.

The goal is to place servers as close to users as possible, reducing the number of links and routers between them and improving delay and throughput.

<br/>

#### Bring Home

> smaller number (10's) of larger clusters in POPs near (but not within) access networks

Adopted by Limelight and other companies, this approach builds large server clusters at a smaller number of key sites, bringing the ISPs home.

Instead of connecting to access ISPs, these CDNs typically place their clusters in `Internet Exchange Points (IXPs)`.

<br/>

As a result, throughput may be lower and delay higher than with Enter Deep, but from the company's point of view it's easier to maintain and costs less.

<br/>

A CDN stores copies of content in these clusters, but it doesn't keep a copy of everything everywhere.

Some videos are rarely watched, or are only popular in certain countries.

<br/>

In practice, CDNs use a `pull` strategy: when a user's request reaches a cluster that doesn't have the video, the cluster retrieves it from a central server or another cluster, serves it to the user, and stores a copy at the same time.

When storage fills up, videos that aren't requested often are removed.

<br/>
<br/>

### How a CDN Operates

1. The user requests a video by specifying a URL.
2. The CDN intercepts the request and selects the most suitable CDN cluster for that client.
3. It redirects the client's request to a server in that cluster.

To intercept requests, CDNs take advantage of DNS. This is called `DNS redirection`.

<br/>

<p align="center"><img width="450" alt="CDN DNS" src="https://user-images.githubusercontent.com/76640167/210764950-3e99de26-f101-486c-8e59-0269e7769373.png">

1. The user enters a URL.
2. The user's host sends a query for the URL's hostname to its local DNS server.
3. The local DNS server forwards the query to the authoritative DNS server for that hostname.  
   To hand the query off to the CDN, the authoritative DNS server returns the IP address of the CDN's authoritative DNS server.
4. The local DNS server sends a query to the CDN's authoritative DNS server, which responds to the local DNS server with the IP address of a CDN content server.  
   This is the point at which the server the client will receive content from is decided.
5. The local DNS server gives the user's host the IP address of the CDN server.
6. Using that IP address, the client fetches the video via HTTP or DASH.

<br/>

### Cluster Selection Strategies

When the CDN intercepts the request through DNS as described above, it learns the IP address of the client's local DNS server. It picks the best cluster based on this IP address.

<br/>

#### Geographically Closest

> Assign the client to the geographically closest cluster.

Using a commercial geo-location database, the CDN maps the IP address to a geographic location and picks the nearest cluster.

This works well most of the time, but it can fall short: the geographically closest cluster may not be the closest in terms of hops along the network path,  
and the client may not be using a local DNS server that's actually near it.

<br/>

#### Real-time Measurements

> Real-time measurement

The CDN performs **periodic real-time measurements of delay and loss performance** between its clusters and clients, and picks the best cluster based on current network conditions.

The problem is that many local DNS servers are configured not to respond to these probes.

<br/>

# 2.6.4 Case Studies: Netflix and YouTube

## Netflix

<p align="center"><img width="450" alt="Netflix" src="https://user-images.githubusercontent.com/76640167/210767665-e80ff1b4-fbc3-468b-ae73-00165867631d.png">

### What Netflix Uses the Amazon Cloud For

- Content ingestion: ingesting and processing movies. Netflix receives the studio master version of a movie and uploads it to hosts in the Amazon cloud.
- Content processing: machines in the Amazon cloud create many different formats of each movie to suit the wide variety of client players, such as desktop computers, smartphones, and game consoles connected to TVs.
  Using DASH, they create multiple versions at different bit rates for each format.
- Uploading versions to the CDN: once all the versions of a movie have been created, hosts in the Amazon cloud upload them to the CDN.

<br/>

To build its own CDN, Netflix installed server racks both in IXPs and within residential ISPs themselves.

It currently has server racks in over 200 IXP locations, as well as in hundreds of ISP locations that host its racks.

Each rack server has several 10 Gbps Ethernet ports and over 100 terabytes of storage.

<br/>

Netflix uses `push caching` to populate its IXP and ISP CDN servers.

For locations that can't hold the entire library, it pushes only the most popular videos, determined on a day-to-day basis.

<br/>

1. The user selects a movie to play.
2. Netflix software running in the Amazon cloud determines which CDN servers have a copy of the movie.
3. Among the servers that have the movie, it determines the best server for that client's request.
4. Typically, if the client's local ISP has a Netflix CDN server rack, that rack is used; otherwise, an IXP with a nearby CDN server is used.
5. It sends the client the IP address of the specific server, along with a manifest file containing URLs for the different versions of the requested movie.
6. The client and that CDN server then interact directly using a proprietary version of DASH.

<br/>

Because Netflix uses its own private CDN, it doesn't need `DNS redirection`.

Instead, the Netflix software running in the Amazon cloud tells the client directly which CDN server to use.

<br/>

Netflix's CDN also uses `push caching` rather than `pull caching`.

Content isn't pulled in dynamically on cache misses; it's pushed to the servers at scheduled times during off-peak hours.

<br/>
<br/>

## YouTube

Like Netflix, YouTube uses its own private CDN.

Google also uses DNS to connect users to a particular server cluster.

<br/>

In most cases, the cluster selection strategy is to pick the cluster with the lowest RTT between the client and the cluster.

Sometimes, for load balancing, it directs the client to a more distant CDN.

<br/>

YouTube adopted HTTP streaming and lets users choose the version manually.

To reduce wasted bandwidth and server resources caused by repositioning and early termination,  
YouTube uses the HTTP byte-range header to limit the flow of data sent after a target amount of video has been prefetched.
