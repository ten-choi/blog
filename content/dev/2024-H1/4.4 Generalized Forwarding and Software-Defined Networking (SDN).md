# 4.4 Generalized Forwarding and Software-Defined Networking (SDN)

Earlier we described destination-based forwarding as two steps: look up the destination IP address (`match`), then send the packet into the switching fabric to the specified output port (`action`).

Now consider a more general `match-plus-action` approach, where the `match` can be done over multiple header fields associated with different protocols at different layers of the protocol stack.

The `action` can include forwarding the packet to one or more output ports, load balancing packets across outgoing interfaces, rewriting header values, intentionally blocking/dropping a packet, and sending a packet to a special server for further processing.

In generalized forwarding, each packet switch contains a `match-plus-action table` that is computed and distributed by a remote controller.

### OpenFlow 1.0

Let's look at OpenFlow 1.0, which introduced SDN concepts and functionality in a clear and concise way.

Each entry in the `match-plus-action forwarding table`, known in OpenFlow as a flow table, includes:

- A set of header field values against which an incoming packet will be matched. Hardware-based matching is performed most rapidly in TCAM memory, which can hold more than a million destination address entries. A packet that doesn't match any flow table entry can be sent to the remote controller for further processing.
- A `set of counters` that are updated as packets are matched to flow table entries. These counters might include the number of packets that have matched the entry and the time since the entry was last updated.
- A set of actions to take when a packet matches a flow table entry. These actions include forwarding the packet to a given output port, dropping the packet, making copies of the packet and sending them to multiple output ports, and rewriting selected header fields.

<br/>

## 4.4.1 Match

<p align="center"><img width="700" alt="Match-plus-action match fields" src="https://user-images.githubusercontent.com/76640167/213117975-972cdf56-575f-4e0d-b9b2-662f3ea2278f.png">

The figure above shows the eleven packet header fields and the incoming port ID that can be matched in an OpenFlow 1.0 `match-plus-action` rule.

The ingress port refers to the input port on the packet switch on which a packet is received.

<br/>

Flow table entries can also contain wildcards. For example, an address of `128.119.*.*` in a flow table matches the corresponding address field of any datagram whose first 16 bits are 128.119.

Each flow table entry also has a priority. If a packet matches multiple flow table entries, the selected match and its corresponding action are those of the highest-priority entry.

<br/>

Not every field in the IP header can be matched.

For example, OpenFlow doesn't allow matching based on the TTL field or the datagram length field.


<br/>

## 4.4.2 Action

Each flow table entry has a list of zero or more actions that determine how packets matching that entry are processed.

If there are multiple actions, they're performed in the order specified in the list.

The most important actions are:

- `Forwarding`
  - An incoming packet can be forwarded to a particular physical output port, broadcast over all ports, or multicast over a selected set of ports.
  - The packet can be encapsulated and sent to the remote controller.
  - The controller can then install a new flow table entry and take action on that packet, or return the packet to the device for forwarding under the updated flow table rules.
- `Dropping`
  - A flow table entry with no action indicates that a matched packet should be dropped.
- `Modify-field`
  - The values of ten packet header fields can be rewritten before the packet is forwarded to the chosen output port.

<br/>

### Third Example: Firewall

Consider a firewall scenario in which s2 wants to receive only traffic sent from hosts attached to s3.

<br/>

A `match-plus-action` flow table is a limited form of **programmability**.

It specifies how a router should forward and manipulate a datagram based on a match between the datagram's header values and the match conditions.

**So you can imagine even richer forms of programmability.**
