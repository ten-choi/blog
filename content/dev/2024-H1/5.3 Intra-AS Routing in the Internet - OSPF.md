# 5.3 Intra-AS Routing in the Internet: OSPF

Viewing the network as **a homogeneous set of routers all running the same routing algorithm** has two problems.

1. `Scale`

   As the number of routers grows, the overhead of communicating, computing, and storing routing information grows out of control.


2. `Administrative autonomy`

   An ISP generally wants to operate its network as it pleases (e.g., to run whatever routing algorithm it chooses),  
   or to hide aspects of its network's internal organization from the outside.

<br/>

### Autonomous systems

These problems can be solved by organizing routers into `autonomous systems (ASs)`.

- Each AS consists of a group of routers under the same administrative control.
- An autonomous system is identified by its globally unique `autonomous system number (ASN)`.
- Routers within the same AS all run the same routing algorithm and have information about each other.
- The routing algorithm running within an autonomous system is called an `intra-autonomous system routing protocol`.

<br/>
<br/>

## The Open Shortest Path First (OSPF) Protocol

`Open shortest path first (OSPF) routing` and `IS-IS (Intermediate System to Intermediate System)`  
are widely used for intra-AS routing in the Internet.

<br/>

OSPF is a **link-state protocol** that uses flooding of link-state information and Dijkstra's least-cost path algorithm.

- With OSPF, each router obtains <b>a complete topological map (graph) of the entire AS</b>.


- Each router then locally runs Dijkstra's shortest-path algorithm to determine a shortest-path tree to all subnets, with itself as the root node.


- A router running OSPF broadcasts routing information **to all other routers in the autonomous system**:
    - whenever there's a change in a link's state
    - periodically (at least once every 30 minutes), even if the link's state hasn't changed


- The state information in OSPF messages is carried directly by IP, with an upper-layer protocol number of `89` for OSPF.
    - So the OSPF protocol must itself implement functionality such as reliable message transfer and link-state broadcast.
    - The OSPF protocol must also check that links are operational,  
      and allow an OSPF router to obtain a neighboring router's database of network-wide link state.

<br/>

### Configuring OSPF link weights

When describing link-state routing, we implicitly assumed the following order:

1. link weights are set,
2. a routing algorithm such as OSPF is run, and
3. traffic flows according to the routing tables computed by the LS algorithm.

<br/>

In cause-and-effect terms:

- Cause: the link weights are given
- Effect: routing paths that minimize the overall cost are determined accordingly.

<br/>

In practice, the cause-and-effect relationship between link weights and routing paths may be reversed.

A network operator can set link weights in order to obtain routing paths that achieve certain traffic engineering goals.

That is, the desired paths for traffic flows are known, and OSPF link weights must be found such that the OSPF routing algorithm results in those paths.

<br/>

For example, an administrator can set all link costs to 1 to achieve minimum-hop routing,  
or set each link's weight inversely proportional to its capacity to discourage traffic from using low-bandwidth links.

<br/>

### Improvements built into OSPF

#### Security

Exchanges between OSPF routers (e.g., link-state updates) can be authenticated,  
and authentication ensures that only trusted routers can participate in the OSPF protocol within an AS.

By default, OSPF packets between routers are not authenticated and could be forged.

<br/>

Two types of authentication

- Simple authentication: the same password is configured on each router, and routers include the password in plaintext when they send OSPF packets, so it's not secure.
- MD5 authentication: based on shared secret keys configured in all the routers. *(covered in Chapter 8)*

<br/>

#### Multiple same-cost paths

When multiple paths to a destination have the same cost, OSPF allows multiple paths to be used.

In other words, when there are several paths with equal cost, **a single path doesn't need to be chosen for carrying all the traffic.**

<br/>

#### Integrated support for unicast and multicast routing

`MOSPF (multicast OSPF)` provides simple extensions to OSPF to provide multicast routing.

- Uses the existing OSPF link database
- Adds a new type of link-state advertisement to the existing OSPF link-state broadcast mechanism

<br/>

[Note]

- `MAC address`: the physical address assigned to each device so devices can be distinguished from each other on a network
- `Unicast`: a transmission method in which the frame carries both the sender's MAC address and the destination's MAC address (one-to-one communication)
- `Broadcast`: a method of sending a frame to every system connected to the local network  
  (a single sending node transmits data to every node on the network that can receive it)
- `Multicast`: a method of designating a specific group among the systems connected to the network and sending information to only that group's members at once  
  (only available if the routers support multicast)

<br/>

#### Support for hierarchy within a single AS

An OSPF autonomous system (AS) can be configured hierarchically into areas.

- Each area runs its own OSPF link-state routing algorithm.
- A router within an area broadcasts its link state **only to the other routers in that same area**.
- Within each area, one or more `area border routers` are **responsible for routing packets outside the area.**
- The primary role of the `backbone area` is to route traffic between the areas in the AS.

<br/>

For inter-area routing within the AS, a packet is

1. routed to an area border router (intra-area routing),
2. routed through the backbone to the area border router in the destination area,
3. and then routed to the final destination.
