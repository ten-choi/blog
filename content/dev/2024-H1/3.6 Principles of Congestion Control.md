# 3.6 Principles of Congestion Control

> 💡 The cause of network congestion: too many sources trying to send data at too high a rate

→ To deal with it, we need mechanisms that throttle the senders causing the congestion.

<br/>

## 3.6.1 The Causes and the Costs of Congestion

### Scenario 1: Two senders, a router with infinite buffers

- Two hosts, A and B, each have a connection that `shares a single hop` between source and destination.
- The applications on hosts A and B are sending data at an `average rate of λin bytes/sec`.
- Assume the router has an infinite amount of buffer space.

<br/>

<p align="center"><img width="700" alt="Congestion scenario 1" src="https://user-images.githubusercontent.com/86337233/211454689-76fb01a5-de4b-4556-a80b-fc908571ceda.png">

<br/>
<br/>

The graphs below show the performance of A's connection.

1. `Per-connection throughput`: the number of bytes per second at the receiver
    - Sending rate between 0 and R/2: the receiver's throughput equals the sender's sending rate.
    - Sending rate above R/2: the throughput is R/2.
    - In other words, no matter how high hosts A and B set their sending rates, **neither can get more than R/2 throughput.**

<br/>

<p align="center"><img width="280" alt="Congestion scenario 1 - throughput" src="https://user-images.githubusercontent.com/86337233/211454696-58c0e5d1-ece7-4eaf-ab49-12ca7b243f3e.png">

<br/>
<br/>

2. `Average delay`
    - As the sending rate approaches R/2: the average delay grows larger and larger.
    - When the sending rate exceeds R/2: **unbounded** (assuming infinite available buffering)

<p align="center"><img width="280" alt="Congestion scenario 1 - delay" src="https://user-images.githubusercontent.com/86337233/211454693-638ed740-069f-498a-9928-1da5aad7544b.png">

<br/>
<br/>


> As the packet arrival rate approaches the link capacity, **queuing delays grow large.**

<br/>

### Scenario 2: Two senders and a router with finite buffers

- Assume `the router's buffer space is finite`. → Packets arriving at an already-full buffer are dropped.
- Assume `each connection is reliable`. → If a packet is dropped at the router, it will eventually be retransmitted by the sender.
- The **rate** at which the application sends original data into the socket: `λin bytes/sec`
- The rate at which the transport layer sends segments into the network <b>(the offered load)</b>  
  : `λ'in bytes/sec` *= the rate of original transmissions plus retransmissions*

<br/>

<p align="center"><img width="700" alt="Congestion scenario 2" src="https://user-images.githubusercontent.com/86337233/211454697-900ad2b0-7639-4da4-8ea7-dc8007abdb0c.png">

<br/>
<br/>

<p align="center"><img width="780" alt="Congestion scenario 2 - graphs" src="https://user-images.githubusercontent.com/86337233/211454701-c4833238-04e5-4e71-930a-da27777bcec6.png">

<br/>
<br/>


a. When no loss occurs at all (the host sends a packet only when a buffer is free)

- The connection's throughput = λin
- The average host sending rate can't exceed R/2.

<br/>

b. When the sender retransmits only when it knows for certain that a packet has been lost

- When the `offered load λ'in` is **R/2**: the rate at which data is delivered is **R/3**
- Of the R/2 of data transmitted,
    - 0.333R bytes/sec is original data
    - 0.166R bytes/sec (on average) is retransmitted data

> The sender must perform retransmissions **to compensate for packets dropped due to buffer overflow**.

<br/>

c. When the sender times out prematurely and retransmits a packet that wasn't lost but was just delayed in the queue

- **Both** the original data packet and the retransmission reach the receiver.
- Assuming each packet is forwarded twice by the router, **the throughput is R/4 when the offered load is R/2.**

> **Unneeded retransmissions by the sender in the face of large delays** cause the router to use its link bandwidth to forward unneeded copies of packets.

<br/>

### Scenario 3: Four senders, routers with finite buffers, and multihop paths

- Four hosts transmit packets over overlapping `two-hop paths`.
- Each host uses a timeout/retransmission mechanism.
- All hosts have the same value of `λin`.
- All router links have a capacity of `R bytes/sec`.

<br/>

<p align="center"><img width="550" alt="Congestion scenario 3" src="https://user-images.githubusercontent.com/86337233/211454704-dbe234c3-f42c-4129-a971-03994afbfad0.png">

<br/>
<br/>

- Regardless of `λin`, **router R2** can see an **arrival rate of at most R**, the capacity of the link from R1 to R2.
- A–C traffic and B–D traffic must compete for buffer space at **router R2**.  
  → **The larger the offered load from B–D, the smaller the amount of A–C traffic** that successfully gets through R2.

> Under heavy traffic, the A–C end-to-end throughput drops to zero.

<br/>

So, as the graph below shows, there's a tradeoff between offered load and throughput.

<p align="center"><img width="320" alt="Congestion scenario 3 - graph" src="https://user-images.githubusercontent.com/86337233/211454705-89d22fd0-1433-4a11-ac8b-3f284d3e4dbb.png">

> When a packet is dropped along a path, **the transmission capacity used at each upstream router to forward that packet up to the point where it was dropped ends up wasted.**

<br/>
<br/>

## 3.6.2 Approaches to Congestion Control

### End-to-end congestion control

> The network layer provides no explicit support to the transport layer for congestion control purposes.

So the presence of congestion in the network must be **inferred by the end systems** based only on observed network behavior (packet loss and delay).

<br/>

This is the approach TCP takes to congestion control.

1. It treats **TCP segment loss** and **increasing round-trip delay values** as indications of network congestion.
2. TCP decreases its window size accordingly.

<br/>

### Network-assisted congestion control

> Routers provide explicit feedback to the sender, the receiver, or both, regarding the congestion state of the network.

- In `ATM ABR (Available Bit Rate) congestion control`,  
  a router can explicitly tell the sender the transmission rate it can support on its outgoing link.


- More recently, IP and TCP can optionally implement this approach as well.

<br/>

There are two ways congestion information is fed back from the network to the sender.

1. **Direct feedback**
    - Network router → sender
    - Form of notification: a `choke packet`


2. Marking/updating a field **in a packet** flowing from the sender to the receiver
    - When the receiver gets a marked packet, it notifies the sender of the congestion.
    - This takes a full round-trip time.
