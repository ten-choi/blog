# 2.3 Electronic Mail in the Internet

In this section, we'll look at the application-layer protocols at the heart of the Internet email architecture.

<br/>

The figure below shows a high-level view of the Internet mail system.

<p align="center"><img width="600" alt="Email system" src="https://user-images.githubusercontent.com/76640167/210542924-1107ca75-eee8-45f6-829a-df0d0df81c15.png">

<br/>
<br/>

Three major components of Electronic mail:

- `User agents`
- `Mail servers`
- `SMTP(Simple Mail Transfer Protocol)`

<br/>
<br/>

## User Agent (UA)

- a.k.a. "mail reader"
- A user agent lets users read, reply to, forward, save, and compose messages.
- Well-known examples include Microsoft Outlook and Apple Mail.

<br/>
<br/>

## Mail server

- It forms the core of the email infrastructure.
- Each recipient has a `mailbox` on a mail server.
    - The mailbox holds and manages the recipient's messages.
    - **A typical message starts its journey at the sender's user agent, travels to the sender's mail server, and then on to the recipient's mail server,**  
      where it's deposited in the recipient's mailbox.
    - To access the messages in a mailbox, the user must be authenticated by the mail server with a username and password.
- The sender's mail server also has to deal with failures at the other mail server.
    - If it can't deliver mail to the recipient's mail server, it holds the message in a `message queue` and tries to deliver it again later.
    - Retries happen roughly every 30 minutes; if delivery keeps failing, the server removes the message and notifies the sender.

<br/>
<br/>

## SMTP

> 💡 The principal application-layer protocol for Internet email.

- SMTP uses `TCP's reliable data transfer service` to transfer mail from the sender's mail server to the recipient's mail server.
- Like most application-layer protocols, SMTP has a `client` side and a `server` side.
- Both the client and server sides of SMTP run on every mail server; a mail server acts as a client when sending mail to another mail server and as a server when receiving mail.

<br/>
<br/>
<br/>

# 2.3.1 SMTP

> uses `TCP` **to reliably transfer email message** from client to server, `port 25`

> `direct transfer`: sending server to receiving server

<br/>

In SMTP, the body of every mail message must be simple `7-bit ASCII`.

This restriction limits what can be sent and causes problems when sending large attachments or video files.

<br/>

Three phases of transfer

1. handshaking (greeting)
2. transfer of messages (data exchange)
3. closure

<br/>

### Basic operation

<p align="center"><img width="700" alt="Message delivery process" src="https://user-images.githubusercontent.com/76640167/210545342-e280b01b-fff0-4ec7-b921-9bfcddb94999.png">

<br/>
<br/>

1. Alice invokes her `email user agent`, provides Bob's email address, and instructs it to send the message.


2. Alice's user agent sends the message to her `mail server`, where it's placed in a `message queue`.


3. The client side of SMTP, running on Alice's mail server, sees the message in the message queue.  
   **It opens a `TCP connection` to an SMTP server running on Bob's mail server.**


4. After some initial SMTP handshaking, the SMTP client sends Alice's message over the TCP connection.


5. At Bob's mail server host, the server side of SMTP receives the message. Bob's `mail server` then places the message in Bob's `mailbox`.


6. Bob invokes his `user agent` to read the message at his convenience.

<br/>

> SMTP **does not use intermediate mail servers**, even when the two mail servers are far apart.

In other words, if sending a message fails, the message isn't stored on some intermediate mail server; **it stays on the sender's mail server.**

<br/>
<br/>

### Basic operation in detail

1. The client SMTP establishes a `TCP connection` to `port 25` on the server SMTP. If the server is down, the client tries again later.


2. Once the connection is established, they perform `application-layer handshaking`.  
   During this phase, the SMTP client indicates the email address of the sender and the email address of the recipient.


3. The client then sends the message (relying on TCP's reliable data transfer service).


4. **If there are more messages to send, the client repeats this over the same TCP connection**; otherwise, it closes the TCP connection. (`persistent connection`)

<br/>
<br/>

## Example exchange between an SMTP client (C) and an SMTP server (S)

```
S:  220 hamburger.edu
C:  HELO crepes.fr
S:  250 Hello crepes.fr, pleased to meet you
C:  MAIL FROM: <alice@crepes.fr>
S:  250 alice@crepes.fr ... Sender ok
C:  RCPT TO: <bob@hamburger.edu>
S:  250 bob@hamburger.edu ... Recipient ok
C:  DATA
S:  354 Enter mail, end with ”.” on a line by itself
C:  Do you like ketchup?
C:  How about pickles?
C:  .
S:  250 Message accepted for delivery
C:  QUIT
S:  221 hamburger.edu closing connection
```

<br/>

<p align="center"><img width="830" alt="Example of message delivery" src="https://user-images.githubusercontent.com/86337233/232236656-a28366f7-e268-4cd4-a525-86b39c658069.png">

<br/>
<br/>

- The client issues five commands: `HELO`, `MAIL FROM`, `RCPT TO`, `DATA`, and `QUIT`.
- The client sends a line consisting of a single period (`.`), which **indicates the end of the message to the server.**
- The server replies to each command, and each reply has a reply code and an (optional) English-language explanation.

<br/>

**SMTP uses `persistent connections`.**

That is, if the sending mail server has several messages to send to the same receiving mail server, **it can send all of them over the same TCP connection.**

<br/>

Using the telnet command, you can have a dialogue like the one above directly with a remote mail server.

<br/>
<br/>

# 2.3.2 Mail Message Formats

When an email is sent, a `header` containing peripheral information precedes the `message body`.

- These headers are defined in RFC 5322, and the header and body are separated by a CRLF.
- Every header must have a `From:` header line and a `To:` header line. (The other headers are optional.)

<br/>

<p align="center"><img width="600" alt="Message format" src="https://user-images.githubusercontent.com/86337233/232237089-44b78dca-e43b-458c-9de0-f2756195c8a1.png">

<br/>
<br/>

A typical message header looks like this:

```
From: alice@crepes.fr
To: bob@hamburger.edu
Subject: Searching for the meaning of life.

Message
```

# 2.3.3 Mail Access Protocols

- `SMTP` : delivery / storage to receiver's server
- `Mail access protocol` : retrieval from server

<br/>

> The `mail server` manages the mailboxes and runs both the client and server sides of SMTP.

<br/>

If the mail server were on the user's local host, that host would have to stay always on and connected to the Internet to receive email, which could arrive at any time.

That's impractical for most Internet users.

<br/>

Instead, a typical user runs a user agent on the local host and **accesses their mailbox stored on an always-on shared mail server.**

The mail server is usually shared with other users.

<br/>

<p align="center"><img width="770" alt="Email protocols" src="https://user-images.githubusercontent.com/76640167/210550668-901b362b-a929-4d44-abe8-da7bf21ca857.png">

<br/>
<br/>

### From the sender's user agent to the recipient's mail server

> The sender's user agent doesn't talk directly to the recipient's mail server.

Instead, as shown in the figure, (1) the sender's user agent **sends the email message to the sender's mail server using `SMTP` or `HTTP`.**

(2) The sender's mail server then **relays the email message to the recipient's mail server using `SMTP`.**

<br/>

The main reason for this two-step procedure is that without relaying through the sender's mail server, there'd be nothing to handle retries when the recipient's mail server is down.

The sender's user agent first deposits the email in its own mail server, and the sender's mail server then keeps trying to send the message every 30 minutes until it reaches the recipient's mail server.

<br/>

### From the recipient's mail server to the recipient's user agent

How does the recipient retrieve messages sitting on a mail server inside their ISP?

SMTP is a `push` protocol, while retrieving messages is a `pull` operation, so a different protocol is needed.

<br/>

Two common approaches:

- `HTTP`
    - Used for Web-based email and smartphone apps.
    - Naturally, the mail server then needs both an SMTP interface and an HTTP interface.
- `IMAP`: the Internet Mail Access Protocol, defined in RFC 3501
