# 5.5 The Software-Defined Networking (SDN) Control Plane

In this section, we'll reuse the SDN terminology from Section 4.4 and refer to the network's forwarding devices as "`packet switches`" or simply "`switches`."

Forwarding decisions in these switches can be based not only on network-layer source/destination addresses and link-layer source/destination addresses,  
but on many other values in the transport-, network-, and link-layer packet headers.

<br/>

## Characteristics of the SDN Architecture

### Flow-based forwarding

> Packet forwarding in `SDN`-controlled switches **can be based on any values** in the transport-layer, network-layer, or link-layer headers.

This is in sharp contrast to the traditional router-based forwarding we looked at in earlier sections,  
where forwarding of an `IP datagram` is based solely on the datagram's destination address.

<br/>

> 💡 In SDN, computing, managing, and installing the flow table entries in all of the network's switches is entirely the job of the `SDN control plane`.

<br/>

### Separation of the data plane and the control plane

#### Data plane

- Made up of the network's `switches` (relatively simple but fast devices).
- Performs "match plus action" based on the contents of their flow tables.

<br/>

#### Control plane

- Made up of servers and the `software` that determines and manages the switches' flow tables.

<br/>

### Network control functions live outside the data-plane switches

The `SDN control plane` is implemented in software and runs on separate servers that are remote from the network switches.

<br/>

As the figure below shows, the control plane consists of two components:

1. The `SDN controller` (or network operating system)
2. A set of `SDN network-control applications`

<br/>

<p align="center"><img width="600" alt="SDN components" src="https://user-images.githubusercontent.com/86337233/213711658-f229ca35-e7a3-4818-b85f-ac2276e417e5.png">

<br/>
<br/>


The SDN controller

1. maintains accurate state information (e.g., the state of remote links, switches, and hosts),
2. provides this information to the network-control applications, and
3. provides the means for those applications to monitor, program, and control the underlying network devices.

<br/>

The controller in the figure is shown as a single central server, but in practice the controller is only **logically centralized**.

(It's typically implemented on several servers to provide coordination, scalability, and high availability.)

<br/>

### A programmable network

The network can be programmed through the network-control applications running in the control plane.

These applications use **the API provided by the SDN controller** to specify and control the data plane in the network devices.

e.g.,  
A routing network-control application might determine the end-to-end path between a source and destination by running Dijkstra's algorithm  
**based on the node-state and link-state information held by the SDN controller**.

<br/>
<br/>

## 5.5.1 The SDN Control Plane

: The SDN controller and SDN network-control applications

<br/>

### The SDN controller

The controller's functionality can be broadly organized into three layers:

1. `Interface to the network-control application layer`
2. `Network-wide state-management layer`
3. `Communication layer`

<br/>

<p align="center"><img width="580" alt="SDN controller components" src="https://user-images.githubusercontent.com/86337233/213711664-270bb750-0349-4109-aaca-cc97627caee1.png">

<br/>
<br/>

#### Communication layer: communication between the SDN controller and **the controlled network devices**

> 💡 Communicating with the controlled devices

- For an SDN controller to control the operation of a remote SDN-enabled device, a protocol is needed to transfer information between the controller and that device.
- A device must also report locally observed events to the controller so that it has up-to-date information about the network state.

Communication between the controller and the controlled devices crosses what's known as the controller's "`southbound`" **interface**.

The concrete protocol that provides this communication is `OpenFlow`, which is implemented in most (though not all) SDN controllers.

<br/>

#### Network-wide state-management layer

> 💡 Network-wide distributed, robust state management

To make the SDN control plane's ultimate control decisions,  
the controller needs up-to-date information about the network's hosts, links, switches, and other SDN-controlled devices.

Since the ultimate purpose of the control plane is to determine the flow tables of the various controlled devices, the controller also needs to maintain copies of those tables.

These pieces of information, such as the counters in a switch's flow table, are all examples of the <b>network-wide "state"</b> maintained by the SDN controller.

<br/>

#### Interface to the network-control application layer

> 💡 Interfaces and abstractions for network-control applications

The controller interacts with network-control applications through its `"northbound" interface`.

This API lets network-control applications read and write the network state information and flow tables within the state-management layer.

<br/>

---

<br/>

From the outside, an SDN controller can look like a single, well-organized, *"logically centralized"* service,

but these services and the databases that hold the state information  
are actually implemented on a **distributed** set of servers for fault tolerance, high availability, or other performance reasons.

<br/>

Modern controllers use a controller platform architecture that is logically centralized but physically distributed.

This architecture gives the controlled devices and the network-control applications a service that scales with the growing number of devices and offers high availability.

<br/>
<br/>

## 5.5.2 The OpenFlow Protocol

- The OpenFlow protocol operates between an SDN controller and an SDN-controlled switch, or any other device implementing the OpenFlow API.
- The OpenFlow protocol runs over TCP, with a default port number of `6653`.

<br/>

The important messages **flowing from the controller to the controlled switch** are:

- `Configuration`: Lets the controller query and set a switch's configuration parameters.

- `Modify-State`: Used by the controller to add/delete or modify entries in the switch's flow table, and to set switch port properties.
- `Read-State`: Used by the controller to collect statistics and counter values from the switch's flow table and ports.
- `Send-Packet`: Used by the controller to send a specific packet out of a specified port at the controlled switch.  
  The message itself carries the packet to be sent in its payload.

<br/>

The main messages **flowing from the SDN-controlled switch to the controller** are:

- `Flow-Removed`: Informs the controller that a flow table entry has been removed, either because it timed out or as the result of a received **Modify-State** message.
- `Port-status`: Used by a switch to inform the controller of a change in port status.
- `Packet-in`
    - Recall from Section 4.4 that a packet arriving at a switch port that doesn't match any flow table entry is sent to the controller for processing.
    - Some packets that do match an entry may also be sent to the controller so it can take action on them.  
      This message is used to send such packets to the controller.

<br/>
<br/>

## 5.5.3 Data and Control Plane Interaction: An Example

The figure below illustrates the interaction between SDN-controlled switches and the SDN controller.

- Here, Dijkstra's algorithm is used to determine shortest paths,  
  and it runs as a separate application **outside the packet switches**.

- The packet switches send **link updates** **to the SDN controller** rather than to each other.

<br/>

<p align="center"><img width="500" alt="SDN controller scenario" src="https://user-images.githubusercontent.com/86337233/213711666-386f50a2-908c-4aad-b862-92b868626000.png">

<br/>
<br/>

- A shortest-path algorithm is in use.
- Suppose that `the link between switches s1 and s2 goes down`.
    - Assume that, as a result, the flow forwarding rules into and out of s1, s3, and s4 change, but s2's operation is unchanged.
- OpenFlow is used as the communication-layer protocol.
- The control plane performs no function other than link-state routing.

<br/>

1. **Switch s1, having detected the link failure to s2,** notifies the SDN controller of the link-state change using an OpenFlow `port-status message`.


2. The `SDN controller` receives the OpenFlow message indicating the link-state change and notifies the link-state manager,  
   which updates the link-state database.


3. The `network-control application` responsible for Dijkstra link-state routing had previously registered to be notified when link state changes.  
   That application now receives notification of the link-state change.


4. The `link-state routing application` asks the link-state manager for the **updated link state**.
    - This may also require help from other components in the state-management layer.
    - **It then computes the new least-cost paths.**


5. The link-state routing application then contacts the flow table manager, which determines the flow tables to be updated.


6. The `flow table manager` uses the OpenFlow protocol to **update the flow tables of the switches affected by the link-state change**.
    - In this example, those are s1, s2, and s4.
    - s1: will now forward packets destined for s2 to s4.
    - s2: will now receive packets from s1 via the intermediate switch s4.
    - s4: must now forward packets from s1 to s2.

<br/>

> 💡 Because the controller can change flow tables however it wants,  
> any form of forwarding can be implemented simply by changing the application control software.

## 5.5.4 SDN: Past and Future

### Past

Although the intense interest in SDN is a relatively recent phenomenon,  
SDN's technical roots, and especially the idea of separating the data and control planes, go back quite a while.

<br/>

- In 2004, [Feamster 2004, Lakshman 2004, RFC 3746] all argued for **separating the network's data and control planes**.


- The `Ethane project [Casado 2007]` pioneered  
  (1) a simple flow-based Ethernet switch with "match plus action" flow tables,  
  (2) a centralized controller that managed flow admission and routing,  
  (3) and the **idea of forwarding packets from the switch to the controller** when they don't match any flow table entry.

   <br/>

    - A network of more than 300 Ethane switches was in operation in 2007.
    - Ethane quickly evolved into the OpenFlow project.

<br/>

### Future

The SDN revolution is replacing "monolithic switches and routers that integrate everything (both data and control planes)"  
with "`simple commodity switching hardware and a sophisticated software control plane`."

A **generalization of SDN** known as `network functions virtualization (NFV)` aims to disruptively replace complex middleboxes  
(those with dedicated hardware and proprietary software for media caching/service) with simple commodity servers, switching, and storage.

<br/>

A second important area of research is **extending SDN concepts** from the intra-AS setting **to the inter-AS setting**.

<br/>
<br/>

## SDN Controller Case Studies: The OpenDaylight and ONOS Controllers

Some SDN controllers are proprietary products built for a specific company.

Many more, however, are open source and implemented in a variety of programming languages.

<br/>

Most recently, the `OpenDaylight controller` and the `ONOS controller` have gained considerable industry support.

Both are open source and are being developed in partnership with the Linux Foundation.

<br/>

### The OpenDaylight controller

The figure below shows a simplified view of the `ODL (OpenDaylight) controller platform [OpenDaylight 2020, Eckel 2017]`.

<br/>

<p align="center"><img width="620" alt="OpenDaylight controller" src="https://user-images.githubusercontent.com/86337233/213711668-cf0281bd-cc01-444e-a547-425e81297c10.png">

<br/>
<br/>

- ODL's basic network service functions sit at the core of the controller.


- `Service Abstraction Layer (SAL)`
    - Lets controller components and applications invoke each other's services and subscribe to the events they generate.
    - Provides a **uniform abstract interface** to the protocols between the ODL controller and the controlled devices,  
      such as OpenFlow, SNMP (Simple Network Management Protocol), and NETCONF (Network Configuration).


- `OVSDB (Open vSwitch Database Management Protocol)` is used to manage **data center switching**.  
  *(Data center networking is covered in Chapter 6.)*

<br/>

The `network orchestrations and applications` part at the very top  
**determines how services** such as data-plane forwarding, firewalling, and load balancing **are carried out in the controlled devices**.

<br/>

### The ONOS controller

The figure below shows a simplified view of the `ONOS controller [ONOS 2020]`.

<br/>

<p align="center"><img width="620" alt="ONOS controller" src="https://user-images.githubusercontent.com/86337233/213711671-83b1df03-db2f-409b-8870-f750a34af119.png">

<br/>
<br/>

As with the standard controller, we can identify three layers:

1. `Northbound` abstractions and protocols
    - ONOS is an intent framework.
        - This lets an application request a high-level service (e.g., set up a connection between host A and host B)  
          without needing to know how that service is actually implemented.
    - State information is provided to network-control applications across the northbound API  
      either synchronously (via direct queries) or asynchronously (e.g., via notifications when network state changes).


2. `Distributed core`
    - The state of the network's links, hosts, and devices is maintained in ONOS's distributed core.
    - By providing service replication and coordination mechanisms among instances, the ONOS core  
      gives the applications above and the network devices below the abstraction of logically centralized core services.


3. `Southbound` abstractions and protocols
    - The southbound abstractions hide the heterogeneity of the underlying hosts, links, switches, and protocols.
    - This lets the distributed core operate regardless of the device or protocol type.
    - Because of this abstraction, the southbound interface below the distributed core sits logically higher than in the standard controller or the ODL controller.
