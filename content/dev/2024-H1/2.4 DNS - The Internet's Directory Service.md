# 2.4 DNS: The Internet's Directory Service

<br/>

### Hostname

One of the identifiers for an Internet host is its `hostname`, such as `www.facebook.com` or `www.google.com`.

<br/>

However, a hostname tells you almost nothing about where the host is located on the Internet.

On top of that, hostnames are variable-length alphanumeric strings, which makes them hard for routers to process.

<br/>

For these reasons, hosts are also identified by what we usually call an `IP address`.

<br/>
<br/>

### IP Address

An IP address is made up of 4 bytes and **has a hierarchical structure.**

- It looks like `121.7.106.83`: each byte is written as a decimal number from 0 to 255, separated by dots.
- **Because it's hierarchical, scanning it from left to right gives you more and more specific information about where the host sits on the Internet.**  
  (Covered in more detail in Chapter 4.)

<br/>
<br/>
<br/>

# 2.4.1 Services Provided by DNS (Domain Name System)

People prefer hostnames, but routers prefer fixed-length, hierarchical IP addresses.

> To reconcile the two, we need a directory service that **translates hostnames into IP addresses**.

That's the main job of the Internet's `DNS (Domain Name System)`. (`hostname translations, address resolutions`)

<br/>

## DNS (Domain Name System)

1. A **distributed** database implemented as a **hierarchy** of DNS servers.  
   implemented in hierarchy of many name servers


2. An **application-layer protocol** that lets hosts query that distributed database.

<br/>

DNS servers are typically UNIX machines running BIND (Berkeley Internet Name Domain) software.

The DNS protocol runs over `UDP` and uses `port 53`.

<br/>
<br/>

### [Note] Why DNS Uses UDP

#### 1️⃣ Speed

TCP goes through a 3-way handshake before any data is sent, while UDP has no connection setup cost.

> For DNS, **speed matters more than reliability**, so UDP is a better fit than TCP.

UDP (for classic DNS) only carries packets up to 512 bytes and has little overhead, so it's fast, and since DNS packets are very small, UDP works in its favor.

That said, DNS didn't pick UDP simply because its packets are small.  
**It's because the packets are small enough that guaranteed reliability isn't needed.** (If a response is lost, just send the query again.)

<br/>

#### 2️⃣ No Need to Maintain Connection State

TCP keeps track of the connection state between hosts.

TCP packets carry a lot of that state information, whereas UDP records nothing and has nothing to maintain.

> Because it doesn't keep connection state and keeps bookkeeping to a minimum, a DNS server running over UDP can handle far more clients than it could over TCP, which is why UDP was chosen.

<br/>
<br/>

## What Happens When a Browser on the User's Host Requests a URL

1. The user's machine runs the client side of the DNS application.


2. The browser extracts the hostname from the URL and passes it to the DNS client.


3. The DNS client sends a query containing the hostname to a DNS server. (client queries to DNS server)


4. Eventually, the DNS client receives the IP address for that hostname.


5. Once the browser has the IP address from DNS,  
   it initiates a TCP connection to the HTTP server process at port 80 on that IP address.

<br/>

As the example shows, DNS adds extra delay,  
but because results are often `cached` in a nearby DNS server, caching reduces both the average DNS delay and the amount of DNS network traffic.

<br/>
<br/>

## Services Beyond Translating Hostnames to IP Addresses

### Host Aliasing

A host with a complicated hostname can have one or more aliases.

A hostname like `relay1.west-coast.enterprise.com` might have an alias like `enterprise.com`.

In that case, `relay1.west-coast.enterprise.com` is called the `canonical hostname`.

> DNS can be used not only to get a host's IP address but also **to get the canonical hostname for a given alias hostname**.

<br/>

### Mail Server Aliasing

Email addresses are simple, but the hostname of the mail server behind them is usually much more complicated.

<br/>

### Load Distribution

> load balancing among the servers

<br/>

**Popular sites are replicated across multiple servers, with each server running on a different end system and having a different IP address.**

In this case, multiple IP addresses are associated with a single canonical hostname, and the DNS database holds this set of IP addresses.

**When a client makes a DNS query for a hostname mapped to a set of addresses, the server responds with the entire set of IP addresses.**

<br/>

**The addresses in each response are rotated.**

Since a client typically sends its HTTP request to the first IP address in the set, **DNS rotation has the effect of distributing traffic.**

<br/>

[[Note] What is DNS Load Balancing?](https://www.nginx.com/resources/glossary/dns-load-balancing/)

<br/>
<br/>
<br/>

# 2.4.2 Overview of How DNS Works

Suppose some application running on the user's host wants to translate a hostname into an IP address.

The process goes like this:

1. The application invokes the DNS client, specifying the hostname.


2. DNS on the user's host sends a query message into the network.  
   All query and reply messages are sent as `UDP datagrams on port 53`.


3. The reply message is handed back to the application.

<br/>

DNS looks simple, but it's actually quite complex: it consists of many DNS servers distributed around the world,  
plus an application-layer protocol that specifies how DNS servers and querying hosts communicate.

<br/>
<br/>

## What If DNS Were a Centralized Database?

> why not centralize DNS?

If DNS used a simple design with a single Internet name server holding every mapping, it would cause the following problems given the huge number of hosts today:

- Single point of failure: if this name server crashes, the entire Internet stops working. (`single point of failure`)
- Traffic volume: a single DNS server would have to handle every query.
- Distant centralized database: a single DNS server can't be "close" to every querying client. The farther away it is, the slower every query gets.
- Maintenance
    - A single name server would have to keep records for every Internet host.
    - It would need constant updates to reflect every new host, and there would be authentication issues around letting users register hosts.

<br/>

In short, a centralized database **doesn't scale at all**, which is why DNS is designed to be distributed.

<br/>
<br/>

## A Distributed, Hierarchical Database

<p align="center"><img width="600" alt="Distributed hierarchical database" src="https://user-images.githubusercontent.com/76640167/210617280-e684c1b7-4f6c-4224-af7e-2e88334bdea2.png">

<br/>
<br/>

DNS uses a large number of servers, organizes them in a hierarchy, and distributes them around the world.

<br/>

### Types of Servers in the DNS Hierarchy

#### Root DNS Servers

- More than 1,000 root server instances are spread across the world.
- Root name servers provide the IP addresses of TLD servers.
- They're coordinated by `ICANN (Internet Corporation for Assigned Names and Numbers)`.

<br/>

#### TLD (Top-Level Domain) DNS Servers

- Top-Level Domain, TLD
- There are TLD servers for top-level domains like `com`, `org`, and `net`, as well as for every country's top-level domain, such as `kr` and `uk`.
- They provide the IP addresses of authoritative DNS servers.

<br/>

#### Authoritative DNS Servers

- Every organization with publicly accessible hosts on the Internet must provide publicly accessible DNS records that map those hostnames to IP addresses.
    - An organization's authoritative DNS server holds these DNS records.
- An organization can choose to run its own authoritative DNS server, or pay a service provider to store these records on one of its authoritative DNS servers.

<br/>

#### Local DNS Servers

- A local DNS server doesn't strictly belong to the server hierarchy, but it's central to the DNS architecture.
- Each ISP has a local DNS server, which provides IP addresses to hosts.
- It's usually close to the host, so latency is low.

<br/>
<br/>

### Example

<p align="center"><img width="400" alt="DNS example" src="https://user-images.githubusercontent.com/76640167/210620114-71bda09c-0995-410a-b8e1-70ee1c5b76bd.png">

<br/>
<br/>

In the figure above, suppose `cse.nyu.edu` wants the IP address of `gaia.cs.umass.edu`.

1. It sends a query to its local DNS server, including the hostname it wants translated.
2. The local DNS server forwards the query to a root DNS server.
3. The root DNS server sees `edu` and returns to the local DNS server a list of IP addresses for TLD servers responsible for `edu`.
4. The local DNS server sends the query to a TLD server.
5. The TLD server sees `umass.edu` and responds with the IP address of the authoritative DNS server, named `dns.umass.edu`.
6. The local DNS server sends the query directly to the authoritative DNS server.
7. The authoritative server responds with the IP address of `gaia.cs.umass.edu`.
8. The local DNS server returns the final IP address to the host.

<br/>

A total of 8 DNS messages were sent here.

In practice, a TLD server usually doesn't know the authoritative DNS server directly as in this example; it knows an intermediate DNS server that in turn knows the authoritative server.

Including that extra round, a total of 10 messages are sent.

<br/>

This example uses both `recursive queries` and `iterative queries`.

The query from `cse.nyu.edu` to `dns.nyu.edu` is recursive, since it asks `dns.nyu.edu` to obtain the mapping on its behalf,  
while the rest are iterative.

<br/>
<br/>

The figure below shows a chain of DNS queries where every query is recursive.

<p align="center"><img width="400" alt="Recursive queries" src="https://user-images.githubusercontent.com/76640167/210622856-0c967585-6ce3-45c7-97bd-c1ed6e3143fc.png">

<br/>
<br/>

> In practice, typical queries follow the iterative pattern.

- With recursive queries, DNS servers higher in the hierarchy take on a lot of responsibility.
    - puts burden of name resolutions on contacted name server
    - heavy load at upper levels of hierarchy
- Protecting critical infrastructure matters much more, so it's better for the default name server to do the work rather than the critical root name servers.

<br/>
<br/>

## DNS Caching

In practice, DNS uses `caching` to improve latency and reduce the number of DNS messages on the network.

> In a query chain, **when a DNS server receives a DNS reply, it can store the information from the reply in its local memory.**

<br/>

If a hostname/IP address pair is cached in a DNS server and another query for the same hostname arrives at that server,  
the DNS server can provide the address even if it isn't authoritative for that hostname.

Because mappings between hostnames and IP addresses aren't permanent, cached information is discarded after a certain period (`TTL, Time to Live`).

Besides specific IP addresses, a local DNS server can also cache the IP addresses of TLD servers, allowing it to bypass the root DNS servers.

<br/>
<br/>
<br/>

# 2.4.3 DNS Records and Messages

Each DNS server replies with a message that **carries one or more resource records**.

<br/>

## DNS Resource Records

DNS servers store `Resource Records (RRs)` that map hostnames to IP addresses.

A resource record is a 4-tuple containing the following fields:

```
(Name, Value, Type, TTL)
```

`TTL (Time to Live)` is the lifetime of the resource record.

Name and Value depend on Type. In other words, **depending on the Type**, the semantics of Name and Value change.

<br/>

### Type = `A`

> **A**ddress  
> A Type A record provides the standard hostname-to-IP-address mapping.

- Name: hostname
- Value: the IP address for the hostname

<br/>

### Type = `NS`

> **N**ame **S**erver

- Name: domain
- Value: the hostname of an authoritative DNS server that knows how to obtain the IP addresses of hosts in the domain

<br/>

### Type = `CNAME`

> **C**anonical **NAME**

- Name: an alias name for a canonical hostname
- Value: the canonical hostname for the alias hostname Name

<br/>

### Type = `MX`

> **M**ail e**X**change

- Value: the canonical name of a mail server that has the alias hostname Name
- MX records allow the hostnames of mail servers to have simple aliases.

<br/>

To get the canonical name of a mail server, you query for the MX record; to get the canonical name of other servers, you query for the CNAME record.

<br/>

If a DNS server is authoritative for a particular hostname, it contains a Type A record for that hostname.

If a server isn't authoritative for a hostname, it contains a Type NS record for the domain that includes the hostname, along with a Type A record that provides the IP address of the DNS server responsible for that hostname.

<br/>
<br/>
<br/>

## DNS Messages

DNS query and reply messages share the same format, shown in the figure below.

<p align="center"><img width="600" alt="DNS message" src="https://user-images.githubusercontent.com/76640167/210725479-3cc2dfe9-5ffd-49f8-9385-5cc244b7c2e6.png">

<br/>
<br/>

### Header

`The header section is the first 12 bytes` and contains several fields.

- The first field is a 16-bit number that identifies the query.  
  This identifier is copied into the reply message, so the client can match replies it receives with the queries it sent.


- The `flags field` contains several flags.
    - A 1-bit `query/reply flag` indicates whether the message is a query or a reply.
    - A 1-bit `authoritative flag` is set in a reply when the DNS server is authoritative for the queried name.
    - A 1-bit `recursion-desired flag` is set when the client wants the DNS server to perform recursion if it doesn't have the record.
    - A 1-bit `recursion-available field` is set in a reply if the DNS server supports recursion.


- The remaining four `"number-of" fields` indicate how many of each of the four types of data sections follow the header.

### Payload

- `Question section`
    - Contains information about the query being made.
    - It has a name field containing the name being queried and a type field indicating the type of question being asked about that name (A, NS, etc.).
- `Answer section`
    - Contains the resource records for the name that was originally queried (value, TTL).
    - **It can carry multiple resource records, because a single hostname can have multiple IP addresses (replicated web servers).**
- `Authority section`
    - Contains records of other authoritative servers.
- `Additional section`
    - Contains other helpful records.
    - For example, in a reply to an MX query, the answer section contains a resource record giving the canonical hostname of the mail server,  
      and the additional section contains a Type A record giving the IP address of that canonical hostname.

<br/>
<br/>

## Inserting Records into the DNS Database

Suppose you're registering the domain name `networkutopia.com` with a `DNS registrar`.

> A `DNS registrar` is a commercial entity that verifies the uniqueness of a domain name,  
> enters it into the DNS database, and charges a fee for that service.

In the past a single small registrar had a monopoly, but now many registrars compete, and ICANN accredits them.

<br/>

When you register a domain name with a registrar, you must give it the names and IP addresses of your primary and secondary authoritative DNS servers.

- Primary authoritative server: `dns1.networkutopia.com` / IP: 212.2.212.1
- Secondary authoritative server: `dns2.networkutopia.com` / IP: 212.2.212.2

Let's assume the values above.

<br/>

For each of these two authoritative DNS servers, the registrar makes sure that a `Type NS` and a `Type A` record are **entered into the TLD com servers.**

Specifically, for the primary authoritative server, the following two resource records are inserted into the DNS system:

```
(networkutopia.com, dns1.networkutopia.com, NS)
(dns1.networkutopia.com, 212.2.212.1, A)
```

<br/>

You also need to make sure that a `Type A` resource record for your web server and a `Type MX` resource record for your mail server are **entered into your authoritative DNS server.**

Once all of these steps are done, people can visit your website and send email to your domain.

<br/>
<br/>

## DNS Vulnerabilities

### DDoS Bandwidth-Flooding Attacks

An attacker tries to flood the DNS root servers with packets so that other DNS queries go unanswered.

This has actually happened, but many root servers were protected by packet filters configured to block the ICMP ping messages the attackers sent toward them,  
and most local DNS servers cache the IP addresses of the top-level domain servers, so there was very little damage.

<br/>

A more effective attack is to target the top-level domain servers instead, and this actually happened to the top-level domain service provider Dyn.

It ended up causing widespread disruption to many popular applications.

<br/>

### DNS Poisoning Attacks

An attacker sends forged replies to a DNS server, tricking it into accepting bogus records into its cache.

Attacks like this can be used to redirect web users to the attacker's website.

To prevent such attacks, the DNS Security Extensions (DNSSEC) protocol was developed and is now in use.
