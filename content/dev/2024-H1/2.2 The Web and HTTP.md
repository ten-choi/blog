# 2.2 The Web and HTTP

The Web operates `on demand`: **users receive what they want, when they want it.**

Individuals can also find a wealth of information and interact with each other on the Web.

<br/>
<br/>
<br/>

# 2.2.1 Overview of HTTP

The `Web's application-layer protocol` is at the heart of the Web.

It's defined in RFC 1945, RFC 7230, and RFC 7540.

`HTTP` defines **the structure of messages** and **how the client and server exchange them**.

Before getting into the details, let's go over some Web terminology.

<br/>
<br/>

## Web page

> A Web page consists of objects.

An object is simply a file (an HTML file, a JPEG image, a JavaScript file, etc.) that is addressable by a single URL.

<br/>

Most Web pages consist of a base HTML file and several referenced objects.

For example, if a Web page contains HTML text and five JPEG images, the page has six objects.

<br/>

The base HTML file references the other objects in the page by their `URLs`.

A URL has the hostname of the server that houses the object and the object's path name.

e.g.,

```
http://www.school.edu/picture.gif 
```

- Hostname: `www.school.edu`
- Path name: `picture.gif`

<br/>
<br/>

## Web browsers and clients

Because a `Web browser` implements the client side of HTTP, in the context of the Web the terms browser and `client` are used interchangeably.

The browser displays the requested Web page and provides a number of navigational and configuration features.

<br/>

A `Web server` houses Web objects, each addressable by a URL.

In general, when a user requests a Web page,  
(1) the browser sends HTTP request messages for the objects in the page to the server, and  
(2) the server receives the requests and responds with HTTP response messages containing the objects.

<p align="center"><img width="450" alt="Web server and browsers" src="https://user-images.githubusercontent.com/76640167/210488592-53e2960a-2ec3-4ecf-8408-8d51a3ebb968.png">

<br/>
<br/>
<br/>

## HTTP and TCP

> HTTP uses `TCP` as its underlying transport protocol.

<br/>

1. The HTTP client first initiates a TCP connection with the server.


2. Once the connection is established, the browser and server processes access TCP through their socket interfaces.


3. The client sends `HTTP request messages` into its socket interface and receives `HTTP response messages` from it.  
   Likewise, the HTTP server receives request messages from its socket interface and sends response messages into it.

<br/>

When messages are sent over TCP this way, **because TCP provides a reliable data transfer service,**  
**every HTTP request message eventually arrives at the server.** (The same goes for messages sent by the server.)

This is where the advantage of a layered architecture shows: HTTP **doesn't have to worry at all** about how TCP recovers lost data or reorders data into the correct order.

<br/>
<br/>

## Stateless protocol

Even if a particular client asks for the same object twice within a few seconds, the server doesn't say it just sent it; it simply sends the object again.

Because an HTTP server maintains no information about its clients, HTTP is called a `stateless protocol`.

<br/>
<br/>
<br/>

# 2.2.2 Non-Persistent and Persistent Connections

## Non-persistent connections

> 💡 When client-server interaction takes place over TCP, **each request/response pair is sent over a separate TCP connection.**

<br>

Let's walk through the steps of transferring a Web page from the server to the client.

Suppose the page consists of **a base HTML file and 10 images**, and all 11 objects reside on the same server.

<br>

Here's how it goes:

1. The HTTP client initiates a `TCP connection` to the server on `port 80, HTTP's default port`. Associated with the TCP connection, there's a socket at the client and a socket at the server.


2. The HTTP client sends an HTTP request message to the server via its TCP connection socket. The request includes the path of the object.


3. The HTTP server receives the request message via its TCP connection socket and retrieves the object at that path from its storage.  
   It encapsulates the object in an HTTP response message and sends it to the client via the socket.


4. The HTTP server tells TCP to close the connection. (But TCP doesn't actually terminate it until it knows for sure the client has received the response message intact.)


5. When the HTTP client receives the response message, the TCP connection terminates. The message indicates that the encapsulated object is an HTML file.  
   The client extracts the file from the response message, examines the HTML file, and finds references to the 10 JPEG objects.


6. **Steps 1–4 are then repeated for each of the referenced JPEG objects.**

<br/>

As the browser receives the Web page, it displays the page to the user. Different browsers may interpret and display a Web page in different ways.

> HTTP only defines the communication protocol; it has nothing to do with how a Web page is interpreted.

<br/>

Users can configure their browsers to control the degree of parallelism, i.e., whether the steps above happen in parallel or one after another.

The browser can **open multiple TCP connections and request different parts of the Web page over those connections.**

HTTP 1.0 supports non-persistent connections.

<br/>
<br/>

Let's estimate the time from when a client requests the HTML file until the whole file is received by the client.

For that we need the RTT,  
where the `RTT (round-trip time)` is **the time it takes for a small packet to travel from the client to the server and then back to the client**.

The RTT includes packet-propagation delays, queuing delays, and processing delays. (Discussed in Chapter 1.)

<br/>

<p align="center"><img width="600" alt="Calculating the time to request an HTML file" src="https://user-images.githubusercontent.com/76640167/210491569-3638ca03-2d17-4eea-8a5f-d984bb831d00.png">

<br/>
<br/>

When a user clicks on a hyperlink, the browser initiates a TCP connection with the Web server. This involves a `3-way handshake`.

> That is, the client sends a small TCP segment to the server, the server acknowledges with a small segment, and finally the client acknowledges back to the server.

<br/>

Once the server responds with its small segment, one RTT has elapsed. At this point, **the client sends the HTTP request message over the TCP connection, combined with the third part of the handshake.**

Once the request message arrives, the server sends the HTML file over the TCP connection, and this request/response takes another RTT.

> So the total response time is roughly 2 RTTs plus the time it takes the server to transmit the HTML file.

<br/>
<br/>

### Drawbacks of non-persistent connections

1. **A brand-new connection must be established and maintained for each requested object.**
    - TCP buffers must be allocated and TCP variables kept on both the client and the server,  
      which places a significant burden on a Web server that may be serving requests from hundreds of clients simultaneously.


2. Each object takes 2 RTTs.

<br/>
<br/>
<br/>

## Persistent connections

With HTTP/1.1 persistent connections, the server leaves the TCP connection open after sending a response. (Non-persistent connections are also supported.)

**Subsequent requests and responses between the same client and server are sent over the same connection.**

In other words, multiple Web pages residing on the same server can be sent over a single persistent TCP connection.

<br/>

Requests for these objects can be made back-to-back, without waiting for replies to pending requests (pipelining).

Typically, the HTTP server closes a connection when it hasn't been used for a certain period of time.

HTTP's default mode uses persistent connections with pipelining.

<br/>
<br/>

## HTTP message format

The HTTP message formats are defined in the RFCs.

### HTTP request message

<p align="center"><img width="600" alt="Request message format" src="https://user-images.githubusercontent.com/76640167/210494014-891426d1-0c27-47dc-8271-c6f5bab316e9.png"></p>

<br/>
<br/>

Here's a typical HTTP request message:

```
GET /somedir/page.html HTTP/1.1
Host: www.someschool.edu
Connection: close
User-agent: Mozilla/5.0
Accept-language: fr
```

<br/>

#### Characteristics

1. It's written in ordinary ASCII text, so humans can read it.
2. The message consists of five lines, and **each line is terminated by a CR (carriage return) and an LF (line feed).** The last line is followed by an additional CR and LF.

The first line of an HTTP request message is called the `request line`, and the lines that follow are called `header lines`.

<br/>

### Request line

The request line has three fields: the `method` field, the `URL field`, and the `HTTP version field`.

The method field can take several values, including `GET`, `POST`, `HEAD`, `PUT`, and `DELETE`.

<br/>
<br/>

### Header lines

1. Host
    - Specifies the host on which the object resides.
    - You might think it's unnecessary since there's already a TCP connection to that host, but it's required by Web proxy caches, covered in Section 2.2.5.
2. Connection: By including this header line, the browser tells the server whether it wants to use a persistent or a non-persistent connection.
3. User-agent: Specifies the type of browser making the request to the server.
4. Accept-language: Indicates which language version of the object the user prefers.

<br/>
<br/>

## Entity body

It's empty with GET and used with `POST`.

With a POST message, the user is still requesting a Web page from the server, but the specific contents of the page depend on what the user entered into the form fields.

A request generated by a form doesn't have to be a POST. The input data can also be sent in the requested URL using the GET method.

<br/>

The `HEAD` method is similar to GET.

**When a server receives a request with the HEAD method, it responds with an HTTP message but leaves out the requested object.** It's often used for debugging.

<br/>

The `PUT` method is used by applications that need to upload objects to a Web server.

The `DELETE` method allows a user or an application to delete an object on a Web server.

<br/>
<br/>

---

<br/>

### HTTP response message

<p align="center"><img width="600" alt="Response message" src="https://user-images.githubusercontent.com/76640167/210497215-8265b94b-c82f-4ea8-9374-5f41fc6eaed1.png">

<br/>
<br/>

Here's a typical HTTP response message:

```
HTTP/1.1 200 OK
Connection: close
Date: Tue, 18 Aug 2015 15:44:04 GMT
Server: Apache/2.2.3 (CentOS)
Last-Modified: Tue, 18 Aug 2015 15:11:03 GMT
Content-Length: 6821
Content-Type: text/html
(data data data data data ...)
```

<br/>

### Status line and status codes

The `status line` contains the protocol version field, a status code, and a corresponding status message.

Status codes and messages:

- 200 OK: The request succeeded and the information is returned in the response.
- 301 Moved Permanently: The requested object has been permanently moved. The new URL is given in the Location header of the response message.
- 400 Bad Request: The server couldn't understand the request.
- 404 Not Found: The requested document doesn't exist on this server.
- 505 HTTP Version Not Supported: The server doesn't support the requested HTTP protocol version.

<br/>

### Header lines

1. Connection: Tells the client whether the server is going to close the TCP connection after sending the message.
2. Date: Indicates the date and time when the HTTP response was created and sent by the server.
3. Server: Indicates which Web server generated the message.
4. Last-Modified: Indicates the date and time when the object was created or last modified.
5. Content-Length: Indicates the number of bytes in the object being sent.
6. Content-Type: Indicates the type of the object in the entity body.

<br/>

The HTTP specification defines many more header lines; the ones above are just a few of them.

Browsers generate header lines dynamically based on the browser type, various settings, whether caching is involved, and so on, and Web servers do the same.

<br/>
<br/>

# 2.2.4 User-Server Interaction: Cookies

An HTTP server is stateless.

However, it's often desirable for a server to identify users, either because it wants to restrict user access or because it wants to serve content based on the user's identity.  
**For this purpose, HTTP uses `cookies`.**

> over stateless HTTP, `cookie` provides a **state related service layer**

<br/>

<p align="center"><img width="700" alt="Keeping state with cookies" src="https://user-images.githubusercontent.com/76640167/210499304-190c6dc5-ab64-4864-9f25-bb27fc63f460.png">

<br/>
<br/>

## How cookies work

1. The browser sends an HTTP request message to the Web server.
2. The Web server creates a unique identification number and creates an entry in its back-end database indexed by that number.
3. It sends back **an HTTP response message** that includes a `Set-cookie: <identification number>` header.
4. The browser sees the header and appends that line to the special cookie file it manages.
5. The next time it **sends a request to the same Web server**,  
   the browser consults its cookie file, extracts the identification number for that site, and sends a `Cookie: <identification number>` header along with the request.

This is how the Web server can identify the user.

<br/>
<br/>
<br/>

# 2.2.5 Web Caching

> A `Web cache` (also called a `proxy server`) is a network entity that satisfies HTTP requests on behalf of an origin Web server.

> Goal: satisfy client request **without involving origin server**

A Web cache has its own disk storage and **keeps copies of recently requested objects.**

<br/>

<p align="center"><img width="450" alt="Web caching" src="https://user-images.githubusercontent.com/76640167/210502046-6dbbe817-240d-401d-8ec6-f3a73210e48d.png">

<br/>
<br/>

## How a proxy server works

1. The browser establishes a TCP connection to the Web cache and sends it an HTTP request for the object.
2. The Web cache checks whether it has a copy of the object stored locally. **If it does, it returns the object to the client browser in an HTTP response message.**
3. **If it doesn't, the Web cache opens a TCP connection to the origin server.**  
   The Web cache then sends an HTTP request for the object over that cache-to-server TCP connection, and the origin server sends the object to the Web cache in an HTTP response message.
4. When the Web cache receives the object, it stores a copy in its local storage and sends the object to the client browser in an HTTP response message (over the TCP connection that was already set up).

<br/>

> A cache is both a server and a client, since it both receives requests and sends them.

- `server` for original requesting client
- `client` to origin server

<br/>

Typically, a Web cache is purchased and installed by an ISP (a university, a company, or a residential ISP).

<br/>
<br/>

## Why use Web caching

1. **It can substantially reduce the response time for a client request.**  
   There's usually a high-speed connection between the client and the cache, so if the cache has the object, bottlenecks can be avoided.


2. A Web cache can substantially reduce traffic on an institution's access link to the Internet.


3. It substantially reduces Web traffic across the Internet as a whole, improving performance for all applications.

<br/>

### Performance without vs. with a Web cache

<p align="center"><img width="370" alt="Bottleneck" src="https://user-images.githubusercontent.com/76640167/210504713-f02f053c-e503-413f-8cbc-046c55082359.png">

<br/>
<br/>

- Suppose the average object size is `1 Mb`, and the average request rate from the institution's browsers to the origin servers is `15 requests per second`.
- Assume the HTTP request messages are negligibly small and thus create no traffic on the access link.
- Also assume that the **average time it takes from when the router on the Internet side of the access link forwards an HTTP request until it receives the response** is `2 seconds`.  
  This is commonly called the `Internet delay`.

> Total response time = LAN delay + access delay + Internet delay

<br/>

The traffic intensity on the LAN is:

```
(15 requests/sec) X (1 Mb/request) / 100 Mbps = 0.15
```

<br/>

The traffic intensity on the access link (between the two routers) is:

```
(15 requests/sec) X (1 Mb/request) / 15 Mbps = 1
```

<br/>

A traffic intensity of 0.15 on the LAN causes at most tens of milliseconds of delay, so the LAN delay can be ignored.  
But as the traffic intensity approaches 1, as discussed in Section 1.4, the delay on the link becomes very large and grows without bound.

**We could fix this by upgrading the access link to 100 Mbps, which would lower the traffic intensity to 0.15, but that's very expensive.**

<br/>

<p align="center"><img width="370" alt="Components of the Internet" src="https://user-images.githubusercontent.com/76640167/210506730-5cb70fea-a9ed-4817-afe0-4463bfd24a4a.png">

<br/>
<br/>

The `fraction of requests satisfied by a cache (hit rate)` typically ranges from 0.2 to 0.7. In this example, let's assume a `hit rate of 0.4`.

- Since the cache and the clients are connected by a high-speed LAN, 40% of the requests are satisfied almost immediately by the cache (within 10 ms).
- The remaining 60% of the requests still need to be satisfied by the origin servers, so the traffic intensity drops from 1.0 to 0.6.

In general, a traffic intensity below 0.8 corresponds to a small delay (negligible compared to the 2 seconds).

<br/>

Taking all this into account, the average delay is:

```
0.4 X 0.01 sec + 0.6 X 2.01 sec = 1.2....
```

<br/>

Many caches run on inexpensive PCs using public-domain software.

- Through Content Distribution Networks (CDNs), Web caches are playing an increasingly important role on the Internet.

- CDN companies install many geographically distributed caches throughout the Internet,  
  localizing much of the traffic. (Some companies use their own dedicated CDNs.)

## Conditional GET

> Web caching can reduce user-perceived response times, but it introduces a new problem: **the copy of an object in the cache may be stale.**

That's because the object on the Web server may have been modified since the copy was cached at the client.

<br/>

> 💡 HTTP has a mechanism that allows a cache to **verify that the objects it delivers to browsers are up to date**,  
> and it's called the `conditional GET`.

> Goal: don't send object if cache has **up-to-date cached version**

An HTTP request message is a conditional GET if (1) it uses the GET method and (2) it includes an `If-modified-since header`.

<br/>

### How conditional GET works

1. On behalf of a requesting browser, the proxy cache sends a request message to the Web server.

```
GET /fruit/kiwi.gif HTTP/1.1
Host: www.exotiquecuisine.com
```

<br/>

2. The Web server sends the cache a response message containing the object.

```
HTTP/1.1 200 OK
Date: Sat, 3 Oct 2015 15:39:29
Server: Apache/1.3.0 (Unix)
Last-Modified: Wed, 9 Sep 2015 09:23:24
Content-Type: image/gif
(data data data data data ...)
```

- The cache forwards the object to the requesting browser and also stores the object locally.
- The important part is that the cache **also stores the last-modified date along with the object.**

<br/>

3. One week later, another browser requests the same object via the cache, and the object is still in the cache.  
   Since the object may have been modified on the Web server in the meantime, the cache performs an up-to-date check by issuing a `conditional GET`.

```
GET /fruit/kiwi.gif HTTP/1.1
Host: www.exotiquecuisine.com
If-modified-since: Wed, 9 Sep 2015 09:23:24
```

- The value of `If-modified-since` exactly matches the Last-Modified value the server sent a week earlier.

- This conditional GET tells the server to **send the object only if it has been modified since the date specified in If-modified-since.**

<br/>

4. If it hasn't been modified,

```
HTTP/1.1 304 Not Modified
Date: Sat, 10 Oct 2015 15:39:29
Server: Apache/1.3.0 (Unix)
(empty entity body)
```

- the server sends a response like the one above.  
  Sending the object when nothing has changed would waste bandwidth and, especially for large objects, increase the user-perceived response time.
- This response message tells the client to go ahead and use its cached copy of the requested object.

<br/>
<br/>
<br/>

# 2.2.6 HTTP/2

As of 2020, 40% of the top 10 million websites support `HTTP/2`.

The main goal of HTTP/2 is to reduce perceived latency by multiplexing requests and responses over a single TCP connection,  
and it also provides request prioritization, server push, and efficient compression of HTTP header fields.

HTTP/2 changes how data is formatted and transported between the client and server.

<br/>
<br/>

## The existing HTTP/1.1

With persistent connections, having **only one TCP connection per Web page**  
reduces the number of sockets at the server and, as explained below, lets each Web page being transported get a fair share of the network bandwidth.

However, sending all the objects of a Web page over a single TCP connection can cause the `HOL (Head of Line) blocking problem`.

<br/><br/>

### The HOL blocking problem

Suppose a video clip needs to be sent along with many small objects, and there's a low- or medium-speed **bottleneck link** between the server and the client.

The video clip takes a long time to pass through the bottleneck link, while **the small objects are stuck waiting behind it.**

In other words, the video clip blocks the other objects.

<br/>

HTTP/1.1 has worked around this problem by opening **multiple parallel TCP connections**.

<br/>
<br/>

### TCP congestion control

TCP congestion control has each TCP connection share a bottleneck link fairly, **splitting the available bandwidth equally among them.**

If n TCP connections are operating over a bottleneck link, each connection gets roughly 1/n of the bandwidth.

<br/>

By opening multiple parallel TCP connections to transport a single Web page, the browser can "cheat" and grab a larger share of the link bandwidth.

Many HTTP/1.1 browsers open up to six parallel TCP connections, which not only prevents HOL blocking but also lets them use more bandwidth.

<br/>
<br/>

## HTTP/2 framing

> One of the main goals of HTTP/2 is to reduce or eliminate the number of parallel TCP connections needed to transport a single Web page.

This not only reduces the number of sockets that need to be opened and maintained at the server, but also lets TCP congestion control work as intended.

However, when only a single TCP connection is used to transport a Web page, HTTP/2 needs a carefully designed mechanism to avoid HOL blocking.

<br/>

> 💡 `HTTP/2 framing` means breaking each HTTP message into independent frames, interleaving them, and reassembling them on the other side.

For example, suppose a request comes in for a video clip and eight small objects, so the server receives nine concurrent requests to send nine objects.

The server (1) splits the video clip into 1,000 frames and (2) splits each small object into 2 frames, then sends one frame from the video clip.

After that, using frame interleaving, it sends the first frame of each small object, and by repeating this it avoids HOL blocking.

<br/>
<br/>

**Breaking HTTP messages into independent frames, interleaving them, and reassembling them on the other side is the single most important improvement in HTTP/2.**

Framing is done by the framing sublayer of the HTTP/2 protocol.

When a server wants to send an HTTP response, the response is processed by the framing sublayer and broken down into frames.

The response's header fields become one frame, and the message body is broken into one or more frames.

The response frames are then interleaved by the server's framing sublayer and sent over a single persistent TCP connection.

When the frames arrive at the client, they're reassembled into the original response messages by the framing sublayer and then processed by the browser. (The same applies to requests from the client to the server.)

<br/>

Besides breaking each HTTP message into independent frames, the framing sublayer also binary-encodes the frames.

Binary protocols are more efficient to parse, lead to slightly smaller frames, and are less error-prone.

<br/>

### Message prioritization

`Message prioritization` lets developers optimize application performance by customizing the relative priority of requests.

<br/>

When a client sends multiple concurrent requests to a single server, it can prioritize them by assigning each message a weight between 1 and 256.

> The higher the number, the higher the priority.

The server can then send the frames for the highest-priority requests first.

<br/>

The client can also express dependencies between messages by specifying the ID of the message each one depends on.

<br/>

### Server push

Another feature of HTTP/2 is that **a server can send multiple responses for a single client request.**

In addition to the response to the original request, the server can **push** additional objects to the client without the client having to request them.

This is possible because the base HTML page indicates the objects needed to fully render the Web page.

Instead of waiting for HTTP requests for these objects, the server can analyze the HTML, identify the objects needed,  
and send them to the client **before the requests for them even arrive.**

This eliminates the extra latency the server would otherwise spend waiting for those requests.

<br/>
<br/>

## HTTP/3

A new HTTP protocol designed to run on top of QUIC, a transport protocol (covered in Chapter 3). It isn't fully standardized yet.
