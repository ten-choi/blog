# 3.8 Evolution of Transport-Layer Functionality

Beyond the TCP variants mentioned so far, many more versions of TCP exist.

<br/>

The only features these TCP variants have in common are that they

1. use the **TCP segment format**,
2. and must **compete "fairly" with each other** in the face of network congestion.

<br/>

## QUIC: Quick UDP Internet Connections

The transport services an application needs may be such that

1. it needs more services than UDP provides,
2. but doesn't want all the particular features that come with TCP, or wants different services altogether.

<br/>

> 💡 Application designers can always "`roll their own protocol`" **at the application layer**.

<br/>

e.g., `QUIC (Quick UDP Internet Connections)`

- QUIC is an **application-layer protocol** designed from the ground up specifically **to improve the performance of transport-layer services** for secure HTTP.


- Today, more than 7% of Internet traffic is QUIC.


- **It uses many of the approaches for reliable data transfer, congestion control, and connection management that we've covered.**

<br/>

As the figure below shows, QUIC is an `application-layer protocol` that uses UDP as its underlying transport-layer protocol,  
and it's designed to interface above it with a version of `HTTP/2`.

<br/>

Left: the traditional secure HTTP protocol stack / Right: the secure QUIC-based HTTP/3 protocol stack

### Key features of QUIC

> ✅ Connection-oriented and secure

QUIC is a `connection-oriented protocol` between two endpoints.

- A `handshake` between the endpoints is required to set up **the QUIC connection state**
- Two pieces of the connection state: the source and destination connection IDs

<br/>

QUIC combines **the handshake needed to establish connection state** with **the handshakes needed for authentication and encryption**.

That gives it faster setup than the traditional secure HTTP protocol stack, which needs multiple RTTs to

1. first establish a TCP connection,
2. and then establish a TLS connection over that TCP connection.

<br/>

> ✅ Streams

- Multiple application-level "`streams`" can be multiplexed over a single QUIC connection.
- Once a QUIC connection is established, new streams can be added quickly.

<br/>

> ✅  Reliable, TCP-friendly, congestion-controlled data transfer

QUIC provides **reliable data transfer independently for each QUIC stream**.

You can see this in the figure below.

<br/>

#### (a) HTTP/1.1

A **single-connection client and server** using application-level TLS encryption  
on top of `TCP`'s RDT (reliable data transfer) and CC (congestion control)

<br/>

> Since TCP provides reliable, in-order byte delivery, multiple HTTP requests **must be delivered in order** at the destination HTTP server.

So if bytes from one HTTP request are lost,  
the remaining HTTP requests **can't be delivered until the lost bytes are retransmitted and correctly received by TCP at the HTTP server.**  
(= the `HOL blocking problem`)

<br/>

#### (b) HTTP/3

A **multi-stream client and server** using QUIC's encryption, reliable data transfer, and congestion control  
on top of `UDP`'s unreliable datagram service

<br/>

> Because QUIC provides reliable, in-order delivery **on a per-stream basis**,  
> **a lost UDP segment only affects the streams whose data was carried in that segment.**


In other words, HTTP messages on other streams can continue to be received and delivered to the application.

<br/>

QUIC provides reliable data transfer using an `acknowledgment mechanism` similar to TCP's.

QUIC's congestion control is based on `TCP NewReno`, a slight modification of the TCP Reno protocol.

<br/>

---

<br/>

> 💡 QUIC is an `application-layer protocol` that provides reliable, congestion-controlled data transfer between two endpoints.

<br/>

This means changes to QUIC can be made on "application-update timescales,"

which are much faster than TCP or UDP update timescales.
