# 4.3 The Internet Protocol (IP): IPv4, Addressing, IPv6, and More

## 4.3.1 IPv4 Datagram Format

A network-layer packet on the Internet is called a datagram.

### IPv4 Datagram Format

<p align="center"><img width="500" alt="Datagram" src="https://user-images.githubusercontent.com/76640167/212647972-acc5a773-a64c-4cd9-adb8-13f3f02876b9.png">

- `Version number`
    - These 4 bits specify the IP protocol version of the datagram.
    - By checking the version number, the router determines how to interpret the rest of the datagram.
    - Different versions of IP use different datagram formats.
- `Header length`
    - Because an IPv4 datagram can carry a variable number of options in its header, these four bits are needed to determine where in the datagram the actual payload begins.
    - Most IPv4 datagrams carry no options, so the typical IPv4 header is 20 bytes.
- `Type of service`
    - The type of service (TOS) bits in the IPv4 header let different types of IP datagrams be distinguished from each other. For example, they're useful for telling real-time datagrams apart from non-real-time traffic.
- `Datagram length`
    - The total length of the IP datagram in bytes. The field is 16 bits, so the theoretical maximum size of an IP datagram is 65,535 bytes, but datagrams are rarely larger than 1,500 bytes.
- `Identifier`, `flags`, `fragmentation offset`
    - These fields relate to IP fragmentation.
    - A large IP datagram is split into several smaller IP datagrams, which are forwarded independently to the destination, where they're reassembled before the payload is passed up to the transport layer of the final host.
- `TTL (time to live)`
    - This field keeps datagrams from circulating forever in the network (e.g., because of a routing loop). It's decremented each time a router processes the datagram, and the datagram is dropped when it reaches 0.
- `Protocol`
    - This field is typically used only when the IP datagram reaches its final destination. Its value indicates the specific transport-layer protocol (TCP, UDP) to which the data portion of the datagram should be passed.
    - In an IP datagram, this field plays a role similar to the port number field in a transport-layer segment.
- `Header checksum`
    - The header checksum helps a router detect bit errors in a received IP datagram.
    - The router discards datagrams in which an error is detected.
    - Because the TTL field (and possibly the options field) change, the checksum must be recomputed and stored again at each router.
    - Why error checking happens at both the transport and network layers:
        - At the IP layer, only the IP header is checksummed, whereas the TCP/UDP checksum is computed over the entire TCP/UDP segment.
        - TCP/UDP and IP don't have to belong to the same protocol stack. In principle, TCP can run on top of something other than IP.
- `Source and destination IP addresses`
    - When the source creates a datagram, it inserts its own IP address into the source IP address field and the destination's IP address into the destination IP address field.
- `Options`
    - Allow the IP header to be extended.
    - Header options are rarely used, which avoids the overhead of carrying option information in every datagram header.
    - They also complicate matters, because a variable-length header means the start of the data field can't be determined up front.
- `Data (payload)`
    - The last and most important field, and the reason the datagram exists in the first place. In most cases it contains the transport-layer segment to be delivered to the destination.

Most IP datagrams have a 20-byte header (assuming no options).

If the datagram carries a TCP segment, each non-fragmented datagram carries a total of 40 bytes of header (20 bytes of IP header plus 20 bytes of TCP header) along with the application-layer message.

<br/>

## 4.3.2 IPv4 Addressing

A host typically has a single link into the network.

When IP in the host wants to send a datagram, it sends it over this link.

The boundary between a host and its physical link is called an `interface`.

A router is connected to multiple links, and the boundary between the router and each link is also an `interface`, so a router has multiple `interfaces`.

Because every host and router can send and receive IP datagrams, IP requires each host and router interface to have its own IP address.

Each of these interfaces has a unique IP address.

So **technically, an IP address is associated with an `interface`, rather than with the host or router that contains that `interface`.**

<br/>

### Subnets and IP Addresses

Each IP address is **32 bits long**, so there are 2^32 possible addresses. Addresses are usually written in **dotted-decimal notation, where each byte of the address is written in decimal and separated from the other bytes by a period**.

An interface's IP address can't be chosen arbitrarily. Part of the IP address is determined by the `subnet` it's connected to.

<p align="center"><img width="500" alt="Subnets" src="https://user-images.githubusercontent.com/76640167/212662555-482eb213-def6-4066-b4ca-2b7e65714196.png">

The three hosts on the left and the router interface they connect to all have IP addresses of the form 223.1.1.xxx. These four interfaces are also connected to each other by a single network **with no router in between**.

This network could be interconnected by an Ethernet LAN, in which case the interfaces would be connected by an Ethernet hub, an Ethernet switch, or a wireless access point.

In IP terms, this network connecting three host interfaces and one router interface forms a `subnet`.

IP addressing assigns this subnet the address `223.1.1.0/24`. The `/24` is called the subnet mask, and it indicates that the leftmost 24 bits form the subnet address.

The figure above shows three subnets.

<br/>

<p align="center"><img width="500" alt="Six subnets" src="https://user-images.githubusercontent.com/76640167/212667479-eb056442-26a3-4e8f-8bf7-97a1e864981a.png">

The IP definition of a subnet isn't limited to Ethernet segments connecting multiple hosts to a router interface.

In the figure above, you can see that the three routers are also connected to each other by point-to-point links.

Here, subnets show up not only between hosts and routers, but also between routers.

In total, there are six subnets.

<br/>

**Definition of a subnet**

> 💡 To determine the subnets, detach each interface from its host or router, creating islands of isolated networks, with interfaces terminating the endpoints of the isolated networks. Each of these isolated networks is called a subnet.

By this definition, an organization with multiple Ethernet segments and point-to-point links will have multiple subnets, with all devices in a given subnet sharing the same subnet address.

Different subnets must have different addresses, but in practice their subnet addresses often have a lot in common.

<br/>

### CIDR

CIDR is one of the Internet's address assignment strategies.

CIDR generalizes the notion of subnet addressing.

In an address of the form a.b.c.d/x, x indicates the number of most significant bits that make up the network portion of the IP address.

These bits are called the address's `prefix`, or `network prefix`.

An organization is usually assigned a block of contiguous addresses (a range of addresses with a common prefix), and the IP addresses of the organization's devices share that common prefix.

When a router outside the organization forwards a datagram whose destination is inside the organization, it only needs to look at the leading x bits.

A single entry of the form a.b.c.d/x is enough to forward packets to any destination in the organization, which considerably reduces the size of the forwarding tables in those routers.

The remaining 32-x bits of the address distinguish among the devices inside the organization, all of which share the same network prefix.

These bits are used when forwarding packets at routers within the organization, and these lower-order bits may themselves have an additional subnet structure.

<br/>

### Classful Addressing

Before CIDR was adopted, the network portion of an IP address was restricted to 8, 16, or 24 bits, and subnets with those address lengths were known as class A, B, and C networks respectively. This scheme became known as `classful addressing`.

However, requiring the subnet portion to be exactly 1, 2, or 3 bytes became a problem for supporting the rapidly growing number of organizations with small and medium-sized networks.

For example, a class C (/24) subnet can only accommodate 254 hosts, far too few for many organizations, while a class B (/16) subnet supports 65,534 hosts, which is far too many.

<br/>

### Broadcast Address

Another kind of IP address is the broadcast address, 255.255.255.255.

When a host sends a datagram with destination address 255.255.255.255, the message is delivered to every host on the same subnet.

<br/>

Next, we'll look at how an organization obtains a block of addresses for its devices, and then how addresses from that block are assigned to individual devices.

<br/>

### Obtaining a Block of Addresses

To get a block of IP addresses for use within an organization's subnet, a network administrator first contacts its ISP, which provides addresses from a larger block it has already been allocated.

<p align="center"><img width="500" alt="IP address blocks" src="https://user-images.githubusercontent.com/76640167/212675085-61430550-15e6-4fb9-a909-1a7bb8bac116.png">

Suppose the ISP has been allocated the block shown above. The ISP can divide it into eight equal-sized smaller address blocks, as shown, and use them to support eight organizations.

ISPs, in turn, get their address blocks from `ICANN`, a nonprofit organization.

`ICANN`'s roles include **allocating IP addresses** and **managing the DNS root servers**.

<br/>

### Obtaining a Host Address: The Dynamic Host Configuration Protocol (DHCP)

Once an organization has obtained a block of addresses from its ISP, it assigns individual IP addresses to the host and router interfaces in the organization.

For router interface addresses, the system administrator manually configures the IP addresses into the router.

Host IP addresses can also be configured manually, but more commonly this is done with the `Dynamic Host Configuration Protocol (DHCP)`.

DHCP lets a host obtain an IP address automatically, along with additional information such as its subnet mask, the address of its first-hop router (default gateway), and the address of its local DNS server.

Because it can automatically connect a host to the network, DHCP is often called a plug-and-play or zero-configuration protocol.

<br/>

<p align="center"><img width="500" alt="DHCP client and server" src="https://user-images.githubusercontent.com/76640167/212679674-19caa44a-265c-43c1-84a6-ecdcdbcaec8e.png">

DHCP is a client-server protocol.

The client is typically a newly arriving host that wants to obtain network configuration information, including an IP address for itself.

Each subnet either has a DHCP server, or, if it doesn't, needs a DHCP relay agent (typically a router) that knows the address of a DHCP server for that network.

<br/>

<p align="center"><img width="400" alt="DHCP in operation" src="https://user-images.githubusercontent.com/76640167/212680264-a3e3a046-d66c-46d3-b09f-2961a5717062.png">

The figure above shows the four steps of the DHCP protocol when a new host arrives.

- `DHCP server discovery`
    - First, the newly arriving host has to find a DHCP server to interact with. It does this using a **DHCP discover message**, which the client sends as a UDP packet to port 67.
    - The DHCP client creates an IP datagram containing the **DHCP discover message**, with the destination IP address set to the broadcast address 255.255.255.255 and the source IP address set to 0.0.0.0.
    - The IP datagram is passed to the link layer, which broadcasts the frame to all nodes attached to the subnet.
- `DHCP server offer(s)`
    - A DHCP server that receives a DHCP discover message responds to the client with a DHCP offer message.
    - This message is also broadcast to all nodes on the subnet using the IP broadcast address.
    - Since there may be several DHCP servers on the subnet, the client may be in the position of choosing the best-located DHCP server among several offer messages.
    - Each server offer message contains the transaction ID of the received discover message, the IP address proposed for the client, the network mask, and an **IP address lease time**.
- `DHCP request`
    - The newly arriving client chooses from among one or more server offers and responds to the selected offer with a **DHCP request message**, echoing back the configuration parameters.
- `DHCP ACK`
    - The server responds to the DHCP request message with a **DHCP ACK message**, confirming the requested parameters.

Once the client receives the DHCP ACK, the interaction is complete, and the client can use the DHCP-allocated IP address for the duration of the lease.

<br/>

DHCP has a drawback: since a node gets a new IP address from DHCP every time it connects to a new subnet, a TCP connection to a remote application can't be maintained as a mobile node moves between subnets.

<br/>

## 4.3.3 Network Address Translation (NAT)

If every host is assigned an IP address from the subnet, a large block of addresses has to be allocated when the network grows significantly.

Problems can come up, such as the ISP having already allocated the adjacent portions of the address range. In cases like this, addresses can be handled with `Network Address Translation (NAT)`.

<p align="center"><img width="700" alt="NAT" src="https://user-images.githubusercontent.com/76640167/212688870-ba4c2f2c-522f-438d-9eb3-3a518e76a7a9.png">

A **NAT-enabled router** has an interface that is part of the home network, shown on the right side of the figure above.

All four interfaces in the home network have the same network address, `10.0.0.0/24`.

The address space `10.0.0.0/8` is one of three portions of the IP address space reserved by an RFC for a `private network`, or a `realm with private addresses`, such as the home network in the figure.

> 💡 A realm with private addresses is a network whose addresses only have meaning to devices within that network.

A realm with private addresses only has meaning inside the home network. In other words, those addresses can't be used to send to or receive from the global Internet.

<br/>

To the outside world, a NAT-enabled router behaves as **a single device with a single IP address**.

In the figure, all traffic leaving the home router for the Internet has the source IP address `138.76.29.7`, that is, **the IP address of the router's outward-facing (WAN-side) interface**.

Likewise, all traffic entering the home network must have `138.76.29.7` as its destination address.

In essence, the NAT-enabled router hides the details of the home network from the outside world.

<br/>

If every datagram arriving at the NAT router from the WAN has the same destination IP address, how does the router know which internal host to forward a given datagram to?

The NAT router uses a `NAT translation table`, which includes IP addresses and port numbers, to figure this out.

Walk through the steps in order using the **NAT translation table** in the figure above.

The web server, unaware of the internal host, replies with the router's WAN-side address as the destination IP, and the router uses the NAT translation table to deliver the reply to the right internal host.

<br/>

Port numbers are meant for addressing processes, not for addressing hosts.

Server processes wait for incoming requests at well-known port numbers, and peers in a P2P protocol need to accept incoming connections when acting as servers, so servers running on a home network can run into problems.

A technical solution to this problem is NAT traversal tools.

<br/>

## 4.3.4 IPv6

IPv6 addressing was developed because the IPv4 address space was rapidly running out.

<br/>

### IPv6 Datagram Format

Key changes in IPv6:

- Expanded addressing capabilities
    - IPv6 increases the size of the IP address from 32 bits to 128 bits, so running out of IP addresses should never happen.
    - In addition to unicast and multicast addresses, IPv6 introduces a new type of address, the anycast address. A datagram addressed to an anycast address can be delivered to any one of a group of hosts.
- A streamlined 40-byte header
    - The fixed-length 40-byte header lets routers process IP datagrams faster.
    - A new encoding of options allows for more flexible option processing.
- Flow labeling
    - IPv6 has an elusive definition of a flow. The RFC says it enables "labeling of packets belonging to particular flows for which the sender requests special handling, such as a non-default quality of service or real-time service." Its exact meaning still hasn't been pinned down, but it was built in anticipation of the flow differentiation that might be needed someday.

<br/>

<p align="center"><img width="500" alt="IPv6 datagram format" src="https://user-images.githubusercontent.com/76640167/212698226-9bf18f85-3111-4434-9202-f2ed45aabd28.png">

The IPv6 datagram format is shown in the figure.

- `Version`
    - This 4-bit field identifies the IP version number. For IPv6 it's 6.
- `Traffic class`
    - This 8-bit field, similar in spirit to the TOS field in IPv4, can be used to give priority to datagrams from certain applications (such as VoIP) over datagrams from other applications (such as SMTP email).
- `Flow label`
    - Used to identify a flow of datagrams.
- `Payload length`
    - This 16-bit value is an unsigned integer giving the number of bytes in the IPv6 datagram following the fixed-length 40-byte header.
- `Next header`
    - This field identifies the protocol to which the contents of the datagram will be delivered (TCP, UDP).
- `Hop limit`
    - Decremented by one by each router that forwards the datagram. When it reaches 0, the datagram is discarded by the router.
- `Source and destination addresses`
    - Hold the source and destination addresses.
- `Data`
    - The payload portion of the IPv6 datagram. When the datagram reaches its destination, the payload is removed from the IP datagram and passed on to the protocol specified in the next header field.

Fields in IPv4 that are gone in IPv6:

- `Fragmentation/reassembly`
    - In IPv6, fragmentation and reassembly are done only by the source and destination.
    - If a router receives an IPv6 datagram that's too large to forward over the outgoing link, it drops the datagram and sends a "Packet Too Big" ICMP error message back to the sender.
    - The sender then resends the data using a smaller IP datagram size.
    - Doing this in routers is time-consuming, so removing it from routers speeds up IP forwarding.
- `Header checksum`
    - Since transport-layer protocols and data link protocols already perform checksumming, the IP designers decided the network-layer checksum was redundant and could be dropped, so they removed it.
- `Options`
    - The field, which was rarely used even in IPv4, is gone, and the header now has a fixed length.
    - Instead, options can appear as one of the possible next headers in the IPv6 header.

<br/>

### Transitioning from IPv4 to IPv6

The problem is that while new IPv6-capable systems can be backward-compatible and send, route, and receive IPv4 datagrams, systems built on IPv4 can't handle IPv6 datagrams.

### Declaring a Flag Day

One option is to pick a date and time when every Internet machine is turned off and upgraded from IPv4 to IPv6. Over 40 years ago, the transition from NCP to TCP was actually done this way.

But a flag day involving hundreds of millions of devices would be completely impossible today.

<br/>

### Tunneling

<p align="center"><img width="700" alt="Tunneling" src="https://user-images.githubusercontent.com/76640167/212711125-cbde816b-a934-4a2e-a404-92665e9e93ea.png">

This is the approach widely used in practice.

Suppose two IPv6 nodes (B and E in the figure) want to interact using IPv6 datagrams.

But they're connected to each other through IPv4 routers. The set of IPv4 routers between the IPv6 nodes is called a `tunnel`.

How IPv6 datagrams are sent:

1. The IPv6 node on the sending side of the tunnel takes the IPv6 datagram and puts it in the data field of an IPv4 datagram.
2. It addresses the IPv4 datagram to the IPv6 node on the receiving side of the tunnel and sends it to the first node in the tunnel.
3. The IPv4 routers inside the tunnel process it like any other IPv4 datagram, unaware that it contains an IPv6 datagram.
4. The IPv6 node on the receiving side of the tunnel receives the IPv4 datagram and determines that it actually contains an IPv6 datagram.
5. It then forwards the IPv6 datagram to the next node.

Basic IPv6 adoption has happened, but there hasn't been much progress recently.
