# 2.5 Peer-to-Peer File Distribution

> A P2P architecture relies minimally on always-on infrastructure servers; instead, **pairs of intermittently connected hosts (peers) communicate directly with each other.**

- In client-server file distribution, sending a copy of the file to every client puts a huge load on the server and consumes a lot of server bandwidth.
- **In P2P file distribution, each peer can redistribute any portion of the file it has received to other peers, helping the server with the distribution process.**

<br/>

As of 2020, the most popular **P2P file distribution protocol** is `BitTorrent`.

<br/>
<br/>
<br/>

# Scalability of P2P Architectures

<p align="center"><img width="450" alt="File distribution example" src="https://user-images.githubusercontent.com/76640167/210734676-39d266cf-181b-4a33-9ed4-7f518a16ad19.png">

The server and the peers are connected to the Internet through access links.

- We denote the upload rate of the server's access link as `u(s)`, the upload rate of the i-th peer's access link as `u(i)`,  
  and the download rate of the i-th peer's access link as `d(i)`.
- We denote the size of the file being distributed as `F bits` and the number of peers that want the file as `N`.

<br/>

The `distribution time` is **the time it takes for all N peers to get a copy of the file**.

When analyzing distribution time, we make the following simplifying assumptions for both the client-server and P2P architectures:

- The Internet core has abundant bandwidth, so all bottlenecks are in the access links.
- The server and all peers aren't participating in any other network applications, so all of their upload and download access bandwidth goes to distributing this file.

<br/>
<br/>

### Distribution Time in the Client-Server Architecture

- **The server must transmit a copy of the file to each of the N peers.** So the server has to transmit `NF bits`.
    - That means the time for the server to distribute the file is at least `NF/u(s)`.
- Let d(min) denote the download rate of the peer with the lowest download rate.
    - The peer with the lowest rate can't receive all F bits of the file in less than F/d(min) seconds.
    - So the minimum distribution time is `F/d(min)`.

So, writing the distribution time as D(cs), we get:

```
D(cs) ≧ max{ NF/u(s) , F/d(min)} 
```

<br/>

From this expression, we can see that for sufficiently large N, the client-server distribution time is given by `NF/u(s)`. **In other words, it grows linearly with N.**

<br/>
<br/>

### Distribution Time in the P2P Architecture

Here, each peer can help the server distribute the file.

In particular, when a peer receives some of the file data, it can use its own upload capacity to redistribute that data to other peers.

<br/>

- When distribution begins, only the server has the file.
    - For the file to reach the peer community, the server must send each bit of the file into its access link at least once.
    - So the minimum distribution time is at least `F/u(s)`.  
      (A bit the server has sent once doesn't need to be sent by the server again, because **the peers can redistribute it among themselves.**)
- As with the client-server architecture, the peer with the lowest download rate can't get all F bits of the file in less than F/d(min) seconds.
    - So the minimum distribution time is at least `F/d(min)`.
- Finally, **the total upload capacity of the system** is the server's upload rate plus the upload rates of all the peers. Let's call this u(total).
    - The system must deliver F bits to each of the N peers, and it can't do that faster than u(total).
    - So the minimum distribution time is `NF/u(total)`.

<br/>

So, writing the distribution time as D(p2p), we get:

```
D(p2p) ≧ max {F/u(s) , F/d(min), NF/u(total)}
```

<br/>
<br/>

If we assume that in the client-server architecture the server schedules its transmissions optimally,  
and that in the P2P architecture each peer can redistribute a bit as soon as it receives it (in practice, chunks are redistributed),  
then the lower bounds in these expressions can be taken as the actual minimum distribution times.

<br/>

<p align="center"><img width="450" alt="Distribution time" src="https://user-images.githubusercontent.com/76640167/210739434-43b60eba-5646-4f4d-bfac-91605965f0f1.png">

<br/>
<br/>

The graph above shows that for any number of peers N, the P2P architecture takes less time than the client-server architecture.

So applications with a P2P architecture are **self-scaling**.

# BitTorrent

> `BitTorrent` is a popular **P2P protocol** for file distribution.

<br/>
<br/>

## Torrent

> In BitTorrent lingo, **the collection of all peers participating in the distribution of a particular file** is called a `torrent`.

<br/>

<p align="center"><img width="450" alt="BitTorrent" src="https://user-images.githubusercontent.com/76640167/210740090-9342a5c1-7bbc-4420-88cb-59fdefcf293c.png">

<br/>
<br/>

Peers in a torrent **download equal-size `chunks` from one another.** (typically 256 KB)

- A peer has no chunks when it first joins, but it accumulates more and more chunks over time.  
  (accumulate chunks over time from other peers)
- While a peer downloads chunks, it also uploads chunks to other peers.
- Once a peer has the entire file, it can leave the torrent, or stay and keep uploading chunks to other peers.

<br/>
<br/>

## Tracker

Each torrent has an **infrastructure node** called a `tracker`.

When a peer joins a torrent, it registers itself with the tracker and periodically informs the tracker that it's still in the torrent, so **the tracker can keep track of the peers in the torrent.**

<br/>

Let's use the figure above as an example.

When a new peer, Alice, joins the torrent,  
**the tracker randomly selects a subset of peers (specifically, 50) from the set of participating peers and sends the `IP addresses of those 50 peers` to Alice.**

With this list of peers in hand, Alice attempts to establish concurrent `TCP connections` with all the peers on the list,  
and the peers she successfully connects to are called her `neighbors`.

<br/>

> The peers fluctuate over time

`churn`: peers may come and go

Over time, some of these peers leave, other peers try to establish TCP connections with Alice, so a peer's set of neighbors changes over time.

<br/>
<br/>

## Rarest First

> requesting chunks: rarest first

<br/>

At any given time, Alice will have some subset of the chunks and will know which chunks her neighbors have.

Based on this information, Alice makes two decisions:

1. Which chunks should she request first from her neighbors?
2. Which of her neighbors should she send chunks to?

<br/>

For the first, she uses a technique called `rarest first`.

Among the chunks she doesn't have, **she determines which are the rarest among her neighbors and requests those first.**

This way, the rarest chunks get redistributed more quickly, so the number of copies of each chunk ends up roughly equal.

<br/>
<br/>

## Trading Smartly

> sending chunks: tit-for-tat

<br/>

When deciding which requests to respond to, Alice **gives priority to the neighbors currently supplying her data at the highest rate.**

- Specifically, she continuously measures the rate at which she receives bits, determines **the four peers sending to her the fastest**, and reciprocates by sending chunks to those four peers.
- She recalculates this every 10 seconds and updates the set.

In BitTorrent lingo, these four peers are said to be `unchoked`.

<br/>

Every 40 seconds, she also **sends chunks to one additional randomly chosen peer** outside those four.

In BitTorrent lingo, this peer is said to be `optimistically unchoked`.

- This way, Alice may become one of that random peer's top uploaders, in which case that peer may start sending chunks to Alice in return.
- Random selection means Alice doesn't just trade chunks with a fixed set of peers; she can trade with many different peers.

<br/>

All other neighboring peers outside these five are choked and don't trade any chunks. (`choked` by Alice = do not receive chunks from her)

<br/>
