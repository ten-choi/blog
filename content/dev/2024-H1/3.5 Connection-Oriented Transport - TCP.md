# 3.5 Connection-Oriented Transport: TCP

## 3.5.1 The TCP Connection

> 💡 TCP is `connection-oriented` because, before one application process can start sending data to another,  
> the two processes **must first "handshake" with each other**.

In other words, they have to send each other some preliminary segments to establish the parameters that will ensure the data transfer.

<br/>

A TCP `connection` is a logical one: **its state lives in the TCP running in the two communicating end systems**.

<br/>

A TCP connection provides a `full-duplex service`.

> If there is a TCP connection between a process on host A and a process on host B,  
> **application-layer data can flow from A to B at the same time as it flows from B to A.**

<br/>

A TCP connection is always `point-to-point`, between a single sender and a single receiver.

So "**multicasting**" — one sender transferring data to many receivers in a single send operation — is not possible with TCP.

<br/>

## How a TCP Connection Is Established

- `client process`: the process that initiates the connection


- `server process`

<br/>

### The three-way handshake

*(Covered in more detail in 3.5.6)*

<br/>

1. The client application process first **tells the client TCP** that it wants to establish a connection to a process on the server.


2. The client's transport layer then proceeds to establish a TCP connection with the TCP in the server.
   > That is, the client first sends a special `TCP segment`.


3. The server responds with a `second special TCP segment`.


4. Finally, the client responds again with a `third special segment`.

<br/>

- The first two segments carry no `payload (application-layer data)`.


- **The third segment may carry a payload.**

<br/>

### Once the TCP connection is established

Once a TCP connection is established, the two application processes can send data to each other.

1. The client process passes **a stream of data** through the `socket (the door of the process)`.


2. Once the data passes through the door, it is in the hands of the TCP running in the client.
    1. TCP directs the data to the connection's `send buffer`, one of the buffers set aside during the initial three-way handshake.
    2. From time to time, TCP grabs chunks of data from the send buffer and passes them to the network.
       (There's no fixed rule for when TCP should send buffered data.)

<br/>

### Maximum segment size (MSS)

> The maximum amount of data that can be grabbed and placed in a segment is limited by the `maximum segment size (MSS)`.

<br/>

What determines the MSS

- The length of the largest link-layer frame that can be sent by the local sending host  
  (the `maximum transmission unit, MTU`)


- It is set so that a TCP segment (when encapsulated in an IP datagram) plus the TCP/IP header length (typically 40 bytes) **fits into a single link-layer frame**.

<br/>

> 💡 The MSS is *not the maximum size of the TCP segment including headers,* but **the maximum amount of application-layer data in the segment**.

<br/>

### TCP segment

> TCP header + client data

1. Segments are passed down to the network layer, where they are **each encapsulated within a `network-layer IP datagram`**.


2. The `segments` are sent into the network.


3. When TCP receives a segment at the other end, the segment's data is placed in the TCP connection's `receive buffer`.  
   → The application reads the stream of data from this buffer.

<br/>

---

<br/>

> Each side of a TCP connection has its own `send buffer` and `receive buffer`.

<br/>

<p align="center"><img width="600" alt="TCP send and receive buffers" src="https://user-images.githubusercontent.com/86337233/211437579-b86e832e-cd39-4707-a212-9ee7c7d6869f.png">

<br/>
<br/>

> 💡 In short, a TCP connection consists of buffers, variables, and a socket connection to a process on one host,  
> and another set of buffers, variables, and a socket connection to a process on the other host.

<br/>
<br/>

## 3.5.2 TCP Segment Structure

### Structure

#### **Header fields**

- `source and destination port numbers`


- `checksum field`


- 32-bit `sequence number field`


- 32-bit `acknowledgment number field`


- 16-bit `receive window`: used for flow control.  
  (Indicates the number of bytes the receiver is willing to accept.)


- 4-bit `header length field`: specifies the length of the TCP header in 32-bit words.


- `options field`
    - This field is optional and variable-length.
    - Used when the sender and receiver negotiate the maximum segment size (MSS), or as a window scaling factor for high-speed networks.


- `flag field`: contains 6 bits.
    - `ACK` bit: indicates that the value in the acknowledgment field is valid.
    - `RST`, `SYN`, `FIN` bits: used for connection setup and teardown.
    - `PSH` bit: when set, indicates that the receiver should pass the data to the upper layer immediately.
    - `URG` bit
        - Indicates that this segment contains data that the sending-side upper-layer entity has marked as "urgent."
        - The location of the last byte of this urgent data is indicated by the 16-bit `urgent data pointer field`.

<br/>

#### **Data field**

Contains a chunk of application data.

<br/>

<p align="center"><img width="500" alt="TCP segment structure" src="https://user-images.githubusercontent.com/86337233/211437603-f0cab27b-5fc5-4dd3-a7e5-b6d4a23797e7.png">

<br/>
<br/>

### MSS

The MSS limits the size of a segment's data field.

- When sending a large file, the file is typically broken into chunks of size MSS.
- Many interactive applications send chunks of data smaller than the MSS.

<br/>

## Sequence Numbers and Acknowledgment Numbers

These two fields are a critical part of TCP's reliable data transfer service.

<br/>

### Sequence numbers

> TCP views `data` as an unstructured, **but ordered, stream of bytes**.

> The `sequence number for a segment` is **the byte-stream number of the first byte in the segment**.

<br/>

e.g.,

- Suppose the data stream consists of a file of 500,000 bytes.
- The MSS is 1,000 bytes.
- The first byte of the data stream is numbered 0.

<br/>

As shown below, TCP builds 500 segments out of the data stream, and each segment is assigned the following sequence number.

<br/>

<p align="center"><img width="700" alt="TCP segments" src="https://user-images.githubusercontent.com/86337233/211437602-133ef178-ba22-4269-86c4-7444efd50f76.png">


<br/>
<br/>

> 💡 Each sequence number is inserted into the `sequence number field` in the header of the corresponding TCP segment.

<br/>

### Acknowledgment numbers

Recall that TCP is **full-duplex**.  
(Host A can receive data from host B **while** it sends data to host B.)

<br/>

Each segment that arrives from host B has a `sequence number` for the data flowing from B to A.

> 💡 The `acknowledgment number` that host A puts in its segment is the `sequence number of the next byte` **host A is expecting from host B**.

<br/>

e.g.,   
Suppose host A has received from host B  
`one segment containing bytes 0 through 535` and `another segment containing bytes 900 through 1,000`.

*(For some reason, host A has not yet received `bytes 536 through 899`.)*

<br/>

Host A is still waiting for byte 536 (and beyond) **in order to re-create B's data stream**.

So A's next segment to B will contain 536 in the `acknowledgment number field`.

<br/>

> Because TCP **only acknowledges bytes up to the first missing byte in the stream**,  
> TCP is said to provide `cumulative acknowledgments`.


<br/>

---

<br/>

In the example above, host A received the `third segment (bytes 900–1,000)` before receiving the `second segment (bytes 536–899)`.

*In other words, the third segment arrived out of order.*

<br/>

So what does a host do in this situation?

> The TCP RFCs don't impose any rules on what a host should do when it receives out-of-order segments in a TCP connection;  
> they leave it up to the people implementing TCP.

<br/>

Two options

1. The receiver **immediately discards** out-of-order segments.

2. The receiver keeps the out-of-order bytes and **waits for the missing bytes to fill in the gaps.**

*The latter is more efficient in terms of network bandwidth, and it's the approach taken in practice.*

<br/>

## Telnet: A Case Study for Sequence and Acknowledgment Numbers

### Telnet

- A popular application-layer protocol used for remote login
- Runs over TCP and is designed to work between any pair of hosts.

<br/>

---

<br/>

Suppose **host A initiates a Telnet session with host B**.

- Host A initiates the session, so it's the `client`
- Host B is the `server`

<br/>

<p align="center"><img width="500" alt="Telnet application" src="https://user-images.githubusercontent.com/86337233/211437590-612a9b6b-4d54-49b3-ad1a-d0d925d64da7.png">

<br/>
<br/>

> 💡 A segment's `sequence number` = the sequence number of the first byte **in the data field**

- Client's initial sequence number: `42` → the first segment sent from the client has **sequence number 42**.
- Server's initial sequence number: `79` → the first segment sent from the server will have **sequence number 79**.

<br/>

> 💡 `Acknowledgment number` = the sequence number of the next byte of data **the host is waiting for**

After the TCP connection is established but **before any data is sent**,

- the client is waiting for byte `79`.
- the server is waiting for byte `42`.

<br/>

---

<br/>

Suppose the user types a single character, 'C', and then goes for a coffee.

As shown in the figure above, **three segments** are sent. (Not to be confused with the `three-way handshake` used to set up the connection.)

<br/>

> 1️⃣ First segment

- Sent from the client to the server.


- Contains `42` in its `sequence number field`.

<br/>

> 2️⃣ Second segment

- Sent from the server to the client.


- Serves two purposes.
    1. **Provides an acknowledgment** of the data the server has received

       > By putting `43` in the `acknowledgment field`,  
       (1) the server tells the client that it has successfully received byte 42, and  
       (2) that it is now waiting for byte 43.

    2. **Echoes back the character 'C'**

       → It puts the ASCII representation of 'C' in its data field.

       > The second segment has sequence number `79`, the `initial sequence number` of the server-to-client data flow of this TCP connection.  
       (This is the very first byte of data the server sends.)

<br/>

> 💡 The `acknowledgment for client-to-server data` is carried **inside a segment that carries server-to-client data**.  
> = The acknowledgment is `piggybacked` on the server-to-client data segment.

<br/>

> 3️⃣ Third segment

- Sent from the client to the server.


- Purpose: to acknowledge the data it has received from the server
    - **This segment has an empty data field.**
    - In other words, the acknowledgment is **not piggybacked** on any client-to-server data.


- The segment has `80` in its `acknowledgment field`.
    - Because the client has received the stream of bytes up through the byte with `sequence number 79`.
    - It is now waiting for bytes starting at `80`.

<br/>

> It may seem odd that this segment has a sequence number even though it carries no data,  
> but **since TCP has a sequence number field, the segment needs to have some sequence number.**

## 3.5.3 Round-Trip Time (RTT) Estimation and Timeout

> 💡 TCP uses a `timeout/retransmit mechanism` **to recover from lost segments**.

The timeout should be somewhat larger than the connection's `round-trip time (RTT)`.

<br/>

### Estimating the round-trip time

> 💡 `Round-trip time (RTT)`: the time from when a segment is sent until it is acknowledged

Let's look at how TCP estimates the round-trip time between sender and receiver.

<br/>

✅  The RTT sample for a segment, denoted `SampleRTT`
: the amount of time **between when the segment is sent (passed to IP) and when an acknowledgment for that segment is received**

Most TCP implementations take **only one** `SampleRTT` **measurement at a time**.

- That is, at any point in time, `SampleRTT` is being measured **for only one of the transmitted but currently unacknowledged segments**.
- This yields a new `SampleRTT` value approximately once every RTT.

<br/>

✅ Because SampleRTT values **fluctuate from segment to segment** due to congestion in routers and varying load on end systems,  
it's natural to take `some sort of average of the SampleRTT values` to estimate the RTT.

→ TCP maintains an average of the SampleRTT values, called `EstimatedRTT`.

> EstimatedRTT = (1 - α) × EstimatedRTT + α × SampleRTT  
> (recommended value of α: 0.125)

<br/>

> 💡 `EstimatedRTT` is a <b>weighted average</b> of the `SampleRTT` values.

- This weighted average gives **more weight to recent samples** than to old ones.


- More recent samples better reflect the current congestion in the network. → `exponential weighted moving average (EWMA)`

<br/>

Below are `SampleRTT` values and `EstimatedRTT` for a TCP connection with `α = 1/8`.

<br/>

<p align="center"><img width="600" alt="RTT samples and RTT estimates" src="https://user-images.githubusercontent.com/86337233/211437598-d947f320-f340-4b47-8f64-fb2fc7558e95.png">

<br/>
<br/>

✅  `DevRTT` represents the **variability of the RTT**.

It is defined as a measure of how much `SampleRTT` typically deviates from `EstimatedRTT`.

> DevRTT = (1 - β) × DevRTT + β × | SampleRTT - EstimatedRTT |  
> (recommended value of β: 0.25)


*DevRTT is an EWMA of the difference between SampleRTT and EstimatedRTT.*

<br/>

### Setting and managing the retransmission timeout interval

Given the values of `EstimatedRTT` and `DevRTT`, what value should be used for TCP's `timeout interval`?

<br/>

- The interval should be greater than or equal to `EstimatedRTT`.  
  (Otherwise, unnecessary retransmissions would be sent.)

- It shouldn't be too much larger than `EstimatedRTT`.  
  (If it's too large, TCP won't quickly retransmit a segment when it's lost.)

→ It's desirable to set the timeout to `EstimatedRTT` plus some margin.

<br/>

> TimeoutInterval = EstimatedRTT + 4 × DevRTT

- An initial `TimeoutInterval` value of 1 second is recommended.


- When a timeout occurs, the value of `TimeoutInterval` is doubled  
  **to avoid a premature timeout** for a subsequent segment that will soon be acknowledged.

<br/>

## 3.5.4 Reliable Data Transfer

> 💡 TCP creates a `reliable data transfer service` *on top of IP's unreliable best-effort service*.

- It ensures that the data stream a process reads out of its receive buffer is **uncorrupted**.


- It ensures there are **no duplicates** and that **ordering is preserved**.

<br/>

In other words, the byte stream is exactly the same byte stream that was sent by the sender.

<br/>

**Timer management** can involve considerable overhead.

So even if there are multiple transmitted but not yet acknowledged segments,  
the recommended **TCP timer management procedure** uses only a `single retransmission timer`.

(The TCP protocol described in this chapter follows the `single-timer` approach.)

<br/>

### Three major events related to data transmission and retransmission in the TCP sender

> 1️⃣ Data received from the application above

When the first event occurs,

1. TCP receives data **from the application**,
2. encapsulates the data in a `segment`,
3. and passes the segment **to IP**.

<br/>

- Each segment includes a `sequence number`, which is the byte-stream number of the segment's first data byte.


- If the timer is not already running for some other segment,
  **TCP starts the** `timer` **when the segment is passed to IP.**

<br/>

> 2️⃣ Timer timeout

1. TCP responds to the timeout event by **retransmitting the segment that caused the timeout**.
2. TCP then restarts the timer.

<br/>

> 3️⃣ ACK receipt

When this event occurs, TCP compares the ACK value `y` with its variable `SendBase`.

- `SendBase`: the sequence number of the **oldest** / **unacknowledged** byte
- `SendBase-1`: the sequence number of the last byte known to have been received correctly and in order at the receiver

<br/>

> TCP uses cumulative acknowledgments, so `y` acknowledges the receipt of all bytes before byte number y.

If `y > SendBase`, the ACK is acknowledging one or more previously unacknowledged segments.

1. The sender updates its `SendBase` variable.
2. It restarts the timer **if there are still any not-yet-acknowledged segments**.

<br/>

## Is TCP Go-Back-N or Selective Repeat?

> 💡 `TCP acknowledgments` are cumulative, and **correctly received but out-of-order segments are not individually ACKed by the receiver**.

> The TCP sender only needs to maintain the smallest sequence number of a transmitted but unacknowledged byte, `SendBase`, and the sequence number of the next byte to be sent, `NextSeqNum`.

From this perspective TCP looks a lot like a GBN-style protocol, but there's one key difference: **TCP buffers correctly received but out-of-order segments**.

e.g.,  
Suppose the **acknowledgment for packet `n < N` is lost**,  
but the remaining N-1 acknowledgments reach the sender before their respective timeouts.

1. `GBN`: retransmits not only packet n but **all of the subsequent packets n+1, n+2, …, N.**


2. `TCP`
    1. **Retransmits only segment n**
    2. If the acknowledgment for segment n+1 arrives before the timeout for segment n, it doesn't even retransmit that segment.

<br/>

> 💡 A proposed modification to TCP, `selective acknowledgment`
: lets a TCP receiver **acknowledge out-of-order segments selectively**,  
rather than just cumulatively acknowledging the last correctly received, in-order segment.

Combined with selective retransmission, this looks a lot like the SR protocol.

<br/>

So TCP's error-recovery mechanism is probably best categorized as **a hybrid of the GBN and SR protocols**.

<br/>

## Fast Retransmit

> The problem with timeout-triggered retransmission: the timeout period can be relatively long.

A long timeout period increases end-to-end delay,  
but fortunately, the sender can often detect packet loss well before the timeout occurs by noticing `duplicate ACKs`.

<br/>

> 💡 `Duplicate ACK`: an ACK that **reacknowledges a segment** for which the sender has already received an earlier acknowledgment

<br/>

### Why the receiver sends duplicate ACKs

> **Since TCP doesn't use negative acknowledgments**, the receiver can't send an explicit negative acknowledgment back to the sender.

1. When a TCP receiver receives a segment with a sequence number larger than the next expected one, it detects a `missing segment`.
2. The receiver simply reacknowledges the last in-order byte of data it has received.  
   That is, it generates a `duplicate ACK`.

<br/>

### TCP ACK generation recommendations

> Event 1️⃣  
> Arrival of an in-order segment with the expected sequence number.  
> **All data up to the expected sequence number has already been acknowledged.**

TCP receiver action: `delayed ACK`

1. Wait up to 500 ms for the arrival of another in-order segment.
2. If the next in-order segment doesn't arrive in this interval, send an ACK.

<br/>

> Event 2️⃣   
> Arrival of an in-order segment with the expected sequence number.  
> One other in-order segment is **waiting for ACK transmission**.

TCP receiver action: immediately send `a single cumulative ACK`, ACKing both in-order segments.

<br/>

> Event 3️⃣  
> Arrival of an out-of-order segment **with a higher-than-expected sequence number**. A gap is detected.

TCP receiver action
: immediately send a `duplicate ACK`, indicating the sequence number of the next expected byte (the lower end of the gap).

<br/>

> Event 4️⃣  
> Arrival of a segment that **partially or completely fills the gap** in the received data

TCP receiver action: immediately send an `ACK`, **provided the segment starts at the lower end of the gap**.

<br/>

### Fast retransmit

If the TCP sender receives **three duplicate ACKs** for the same data,  
it takes this as an indication that the segment following the segment that has been ACKed three times has been lost.

> 💡 When it receives `three duplicate ACKs`,
> TCP retransmits the missing segment **before that segment's timer expires**.

<br/>

In the figure below, the second segment is lost, and it is retransmitted **before** its timer expires.

## 3.5.5 Flow Control

> 💡 TCP provides a `flow-control service` to its applications
> **to eliminate the possibility of the sender overflowing the receiver's buffer**.

→ It matches the rate at which the sender is sending to the rate at which the receiving application is reading.

<br/>

> A TCP sender can also be **throttled** due to congestion within the IP network. = `congestion control`

*Flow control and congestion control are clearly taken for different reasons. (Be careful to tell them apart.)*

<br/>

### How it works

> 💡 TCP provides flow control by having the sender maintain a variable called the `receive window`.

- It's used to give the sender an idea of **how much free buffer space is available at the receiver**.


- Because TCP is `full-duplex`, the sender on each side of the connection maintains a distinct receive window.

<br/>

---

<br/>

e.g., suppose host A is sending a large file to host B over a TCP connection.

1. Host B allocates a receive buffer to this connection.  
   (The size of the allocated receive buffer: `RcvBuffer`)


2. The application process in host B reads from the buffer, and we define the following variables.
    - `LastByteRead`
      : the number of the last byte in the data stream **read** from the buffer by the application process in host B
    - `LastByteRcvd`
      : the number of the last byte in the data stream that has arrived from the network and been **placed** in the receive buffer at host B
    - `rwnd`
      - the receive window = **the amount of spare room in the buffer**
      - Because the spare room changes over time, this variable is dynamic.

<br/>

> LastByteRcvd - LastByteRead ≤ RcvBuffer

> rwnd = RcvBuffer - [LastByteRcvd - LastByteRead]

<br/>

<p align="center"><img width="480" alt="Receive window and receive buffer" src="https://user-images.githubusercontent.com/86337233/211437616-fd0b34a2-9117-4bd5-bfb0-3fe82e59e4c3.png">

<br/>
<br/>

---

<br/>

1. Host B puts its current `rwnd` value in the receive window field of every segment it sends to host A.
   > This tells host A **how much spare room is in the connection's buffer**.


2. Host A keeps track of two variables, `LastByteSent` and `LastByteAcked`.
   > LastByteSent - LastByteAcked = the amount of **unacknowledged** data host A has sent into the connection

<br/>

> 💡 By keeping the amount of unacknowledged data less than the value of `rwnd`,
> host A makes sure it doesn't overflow the receive buffer at host B.

<br/>

Throughout the connection's lifetime, host A ensures that

> LastByteSent - LastByteAcked ≤ rwnd

<br/>

### The problem and the fix

1. Host B's receive buffer becomes full, so `rwnd = 0`,
2. and after advertising rwnd = 0 to host A, **host B has nothing to send to host A**.

> Even as the application process at host B empties the buffer,  
> **TCP doesn't send new segments with new rwnd values to host A.**

<br/>

That's because TCP sends a segment to host A only if it has data to send or an acknowledgment to send.

→ Host A is blocked and can't transmit any more data.

<br/>

To solve this, the TCP specification requires host A to keep sending segments with one byte of data when B's receive window is zero.

## 3.5.6 TCP Connection Management

How is a TCP connection established and torn down?

<br/>

Suppose a process running on one host (the client) wants to initiate a connection with another process on another host (the server).

1. The client application process **tells the client TCP** that it wants to establish a connection to a process on the server.
2. The TCP in the client then proceeds to establish a TCP connection with the TCP in the server as follows.

<br/>

### Connection setup: the three-way handshake

<p align="center"><img width="450" alt="TCP three-way handshake" src="https://user-images.githubusercontent.com/86337233/211437617-b3a75ef9-8307-499f-b011-2bfb62f92916.png">

<br/>
<br/>

#### Step 1

1. The client-side TCP sends a special TCP segment, the `SYN segment`, to the server-side TCP.
    - It contains no application-layer data.
    - The `SYN bit` in the segment header is set to **1**.


2. The client randomly chooses an initial sequence number (`client_isn`) and puts it in the `sequence number field` of the initial TCP SYN segment.


3. This segment is encapsulated within an IP datagram and sent to the server.

<br/>

#### Step 2

Once the `IP datagram` containing the TCP SYN segment arrives at the server host,

1. the server extracts the TCP SYN segment from the datagram,


2. allocates the TCP buffers and variables for the connection,


3. and sends a **connection-granted segment**, the `SYNACK segment`, to the client TCP.
    - It contains no application-layer data.
    - The `SYN bit` is set to **1**.
    - The `acknowledgment field` of the TCP segment header is set to `client_isn+1`.
    - The server chooses its own initial sequence number (`server_isn`) and puts it in the `sequence number field` of the TCP segment header.

<br/>

#### Step 3

Upon receiving the connection-granted segment,

1. the client allocates buffers and variables for the connection.


2. The client host then sends the server **yet another segment**.
    1. The client acknowledges the server's connection-granted segment by putting `server_isn+1` in the `acknowledgment field` of the TCP segment header.
    2. Since the connection is established, the `SYN bit` is set to **0**.

<br/>

> The third step can carry client-to-server data in the `segment payload`.

<br/>

---

<br/>

Once these three steps are complete,

- the client and server hosts can send each other `segments containing data`.
- The `SYN bit` is set to **0**.

<br/>

### Closing the connection

Either of the two processes in a TCP connection can end the connection.

When a connection ends, **the "resources" (buffers and variables) in the hosts are deallocated.**

<p align="center"><img width="400" alt="Closing a TCP connection" src="https://user-images.githubusercontent.com/86337233/211437618-6aea0b08-6847-450d-b5d7-a1ae129d0c56.png">

<br/>
<br/>

1. The client application process issues a **close command**.


2. This causes the client TCP to send a `special TCP segment` to the server process.  
   (with the `FIN bit` set to **1**)


3. When the server receives this segment, it sends the client an `acknowledgment segment`.


4. The server then `sends its own shutdown segment`, which has the `FIN bit` set to **1**.


5. Finally, the client `acknowledges` the server's shutdown segment.

   > At this point, all the resources in the two hosts are deallocated.

## The SYN Flood Attack

### TCP's three-way handshake

1. In response to a `received SYN`, the server allocates and initializes connection variables and buffers.


2. The server then sends a `SYNACK` in response and waits for an `ACK segment` from the client.

<br/>

> If the client doesn't send an ACK to complete the third step of the handshake,  
> **eventually (often after a minute or more) the server terminates the half-open connection and reclaims the allocated resources.**

→ This sets the stage for the `SYN flood attack`.

<br/>

### SYN flood attack

A classic `Denial of Service (DoS) attack`

<br/>

1. The attacker sends a large number of `TCP SYN segments` without completing the third step of the handshake.


2. The server's connection resources get allocated to these half-open connections.


3. Eventually the server runs out of connection resources, and legitimate clients are denied service.

<br/>

### SYN cookies

This is **a defense against the SYN flood attack**, and it's now deployed in most major operating systems.

<br/>

#### How it works

1. Instead of creating a half-open TCP connection for the SYN,
   the server creates an `initial TCP sequence number (a cookie)`.
    - This is because when the server receives a SYN segment, it can't tell whether it came from a legitimate user or an attacker.
    - The cookie is generated by a hash function using the following.
        - A secret number
        - The source and destination IP addresses and port numbers of the SYN segment


2. The server sends a `SYNACK` packet with this special initial sequence number.

   > 💡 The server **does not remember** the cookie or any other state information related to the SYN.


3. A legitimate client returns an `ACK` segment.


4. When the server receives this ACK, it must verify that the ACK corresponds to some SYN it sent earlier.
    - It verifies this **using the** `cookie`.
    - The server runs the same hash function using the source and destination IP addresses and port numbers in the ACK, plus the secret number.

<br/>

**If the result of the function plus one equals the acknowledgment number (the cookie) in the client's ACK,**  
the server concludes that the ACK corresponds to an earlier SYN segment and is therefore valid.

→ The server then creates a fully open connection along with a socket.

<br/>

If the client doesn't return an ACK segment,  
the original bogus SYN does no harm to the server, since the server never allocated any resources for it.
