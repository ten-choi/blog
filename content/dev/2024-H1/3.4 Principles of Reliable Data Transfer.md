# 3.4 Principles of Reliable Data Transfer

Implementing `reliable data transfer` is a problem that comes up not only at the transport layer, but also at the link layer and the application layer.

So this section looks at the reliable data transfer problem in a general setting.

<br/>

The framework for studying reliable data transfer looks like this.

#### a. Service model

<p align="center"><img width="370" alt="Reliable data transfer - service model" src="https://user-images.githubusercontent.com/86337233/211394868-aedb95b8-5ff9-4484-a800-aae79619f52f.png">

<br/>
<br/>

#### b. Service implementation

<p align="center"><img width="370" alt="Reliable data transfer - service implementation" src="https://user-images.githubusercontent.com/86337233/211394864-647c6e5e-f9d2-4968-aba3-c12ee6bcf549.png">

<br/><br/>

The service abstraction provided to upper-layer entities is that of **a reliable channel through which data can be transferred**.

- With a reliable channel, no transferred data is corrupted or lost,
- and all data is delivered in the order in which it was sent.

= the service model `TCP` offers to Internet applications

<br/>

The job of a `reliable data transfer protocol` is to implement this reliable-channel service abstraction.

<br/>

---

<br/>

> In this section, we incrementally build up the sender and receiver sides of a reliable data transfer protocol, considering increasingly complex models of the underlying channel.

One assumption we'll adopt throughout: **packets are delivered in order (the underlying channel does not reorder packets).**

<br/>

Of the two figures above, b shows the **interface of the data transfer protocol**.

- The sending side of the protocol is invoked from above via a call to `rdt_send()`, and the receiving side hands data up to be delivered to the upper layer.
    - `rdt`: stands for the reliable data transfer protocol.
    - `_send`: indicates that the sending side of rdt is being called.


- On the receiving side, `rdt_rcv()` is called when a packet arrives from the receiving side of the channel.


- When the rdt protocol wants to deliver data to the upper layer, it calls `deliver_data()`.

<br/>

---

<br/>

> In this section we only consider `unidirectional data transfer`, i.e., data transfer from the sending side to the receiving side.

Bidirectional (full-duplex) data transfer is considerably more complex to explain.

<br/>

Even with unidirectional data transfer, **the sending and receiving sides of the protocol still need to send packets in both directions.**

That is, besides exchanging packets carrying the data being transferred, the sending and receiving sides of rdt also need to send `control packets` back and forth.

- Both the sending and receiving sides of rdt send packets to the other side by calling `udt_send()`.
    - udt: stands for unreliable data transfer

<br/>
<br/>

## 3.4.1 Building a Reliable Data Transfer Protocol

### Definitions for a finite-state machine (FSM)

- `Arrows` indicate a transition from one state to another.
- The initial state of the FSM is marked with a `dashed arrow`.

<br/>

- <b>The event</b> that causes a transition is shown `above the horizontal line` labeling the transition.
- The <b>actions</b> taken when the event occurs are shown `below the horizontal line`.

<br/>

- When no action is taken on an event, or no event occurs and an action is taken,  
  the `symbol 𝚲` is used below or above the horizontal line, respectively, to indicate **the lack of an action or event**.

<br/>
<br/>

## Reliable Data Transfer over a Perfectly Reliable Channel: rdt1.0

Let's start with the simplest case, where **the underlying channel is completely reliable**.

<br/>

### FSM for rdt1.0

The finite-state machines (FSMs) for the rdt1.0 sender and receiver are shown below.

<br/>

> 💡 There are **separate FSMs** for the sender and for the receiver.

- a defines the operation of the sender
- b defines the operation of the receiver

<br/>

<p align="center"><img width="450" alt="rdt1.0" src="https://user-images.githubusercontent.com/86337233/211394885-cee89e54-814d-4772-9083-617648a91488.png">

<br/>
<br/>


In rdt1.0, **each FSM has just one state**, so a transition necessarily goes from that state back to itself.

<br/>

#### Sender

1. On the `rdt_send(data)` event  
   (caused by a procedure call from the upper-layer application, e.g., `rdt_send()`), it
    1. accepts data from the upper layer, and
    2. creates a packet containing the data (`make_pkt(data)`).


2. It then sends the packet into the channel.

<br/>

#### Receiver

1. rdt receives a packet from the underlying channel via the `rdt_rcv(packet)` event.
   : This event is caused by a procedure call from the lower-layer protocol (e.g., `rdt_rcv()`).


2. It extracts the data from the packet (`extract(packet, data)`),


3. and delivers the data to the upper layer (`deliver_data(data)`).

<br/>

---

<br/>

Here there's no difference between a unit of data and a packet, and all packets flow from the sender to the receiver.

<br/>

> 💡 With a perfectly reliable channel, nothing can go wrong, so <b>the receiver doesn't need to provide any feedback to the sender.</b>

<br/>

We also assumed that **the receiver can receive data as fast as the sender sends it**.

So there's no need for the receiver to ask the sender to slow down.

<br/>
<br/>

## Reliable Data Transfer over a Channel with Bit Errors: rdt2.0

**This is a model in which bits in a packet may be corrupted in the underlying channel.**

Such bit errors typically occur in the physical components of a network as a packet is transmitted, propagates, or is buffered.

<br/>

### Automatic Repeat reQuest (ARQ) protocols

- `Positive acknowledgments ("OK")`
- `Negative acknowledgments ("Please repeat that")`

These control messages let the receiver tell the sender what was received correctly and what was received in error and needs repeating.

<br/>

**To handle bit errors**, ARQ protocols fundamentally require three additional protocol capabilities.

<br/>

#### Error detection

> A mechanism is needed for the receiver to detect when bit errors have occurred. → checksum

These techniques let the receiver detect, and possibly correct, packet bit errors.

<br/>

#### Receiver feedback

> The only way for the sender to learn the receiver's state is for the receiver to provide feedback to the sender.

Receiver's state: whether a packet was received correctly or not, etc.

<br/>

e.g., in the rdt2.0 protocol, the receiver sends ACK and NAK packets back to the sender.

- `Positive acknowledgment (ACK)`
- `Negative acknowledgment (NAK)`

→ In principle, these packets only need to be one bit long (0 or 1).

<br/>

#### Retransmission

> A packet that is received in error at the receiver is retransmitted by the sender.

<br/>

### FSM for rdt2.0

#### Sender

<p align="center"><img width="700" alt="rdt2.0 - sender" src="https://user-images.githubusercontent.com/86337233/211394874-2e37ba36-b8c3-454a-aa09-836435f51421.png">

<br/>
<br/>

There are two states.

1. In the **left state**, the send-side protocol **waits for data to be passed down from the upper layer.**

   When the `rdt_send(data)` event occurs,

    1. the sender creates a packet (`sndpkt`) containing the data to be sent, along with a packet checksum,
    2. and sends that packet via the `udt_send(sndpkt)` operation.


2. In the **right state**, the sender protocol **waits for an ACK or NAK packet from the receiver.**
    1. If an `ACK` packet is received (`rdt_rcv(rcvpkt) && isACK(rcvpkt)`),
        - the most recently transmitted packet has been received correctly.
        - So the protocol returns to the state of waiting for data from the upper layer.
    2. If a `NAK` is received,
        1. the protocol retransmits the last packet,
        2. and waits for an ACK or NAK to be returned by the receiver in response to the retransmitted data packet.

<br/>

A protocol like rdt2.0 is a `stop-and-wait protocol`.

> 💡 While the sender is in the state of waiting for an ACK or NAK, **it cannot get more data from the upper layer.**

That is, the `rdt_send()` event can't happen; it will only happen after the sender receives an ACK and leaves this state.

<br/>

So the sender won't send a new piece of data **until it's sure the receiver has correctly received the current packet**.

<br/>

#### Receiver

<p align="center"><img width="480" alt="rdt2.0 - receiver" src="https://user-images.githubusercontent.com/86337233/211394877-619eb70a-cbc0-4e6c-bd47-b29a80d28521.png">

<br/>
<br/>

It has a single state.

When a packet arrives, the receiver replies with either an `ACK` or a `NAK`, depending on whether the received packet is corrupted.

<br/>

### The flaw in rdt2.0

We haven't accounted for the possibility that `the ACK or NAK packet itself could be corrupted`.

If an ACK or NAK is corrupted, the sender has no way of knowing whether the receiver correctly received the last piece of transmitted data.

<br/>

> Option 1: **add enough checksum bits** to let the sender not only detect, but also recover from, bit errors.

This immediately solves the problem for a channel that can corrupt packets but not lose them.

<br/>

> Option 2: when the sender receives a garbled ACK or NAK packet, **simply resend the current data packet.**

However, this introduces `duplicate packets` into the sender-to-receiver channel.

- The receiver can't know whether the last ACK or NAK it sent was received correctly at the sender.
- So from the receiver's point of view, it can't know a priori whether an arriving packet contains new data or is a retransmission.

<br/>

### The solution

> 💡 Add a new field to the data packet and have the sender number its data packets by putting a `sequence number` in this field.

*This is the approach taken by almost all existing data transfer protocols.*

The receiver then only needs to check this sequence number to determine whether a received packet is a retransmission.

<br/>
<br/>

## A Fixed Version of rdt2.0: rdt2.1

> `rdt2.1` has twice as many states as rdt2.0.

That's because it has to reflect the following two things:

1. whether the packet currently being **sent** (by the sender) has sequence number 0 or 1, and
2. whether the packet the receiver is waiting for **should have sequence number 0 or 1**.

<br/>

> The rdt2.1 protocol uses **both positive and negative acknowledgments** from the receiver to the sender.

- **When an out-of-order packet is received**, the receiver sends `a positive acknowledgment for the packet it already received`.
- **When a corrupted packet is received**, the receiver sends `a negative acknowledgment`.

<br/>

Instead of sending a NAK,  
we can get the same effect **by sending an ACK for the last correctly received packet**.

That is, a sender that receives two ACKs for the same packet (i.e., receives `duplicate ACKs`)  
knows that the receiver did not correctly receive the packet following the one being ACKed twice. (Same meaning as a NAK.)

<br/>

## A NAK-Free Reliable Data Transfer Protocol for a Channel with Bit Errors: rdt2.2

Unlike rdt2.1, in `rdt2.2`:

1. The receiver must **include the sequence number of the packet** being acknowledged by an ACK message.
    - This is done by passing an `ACK, 0` or `ACK, 1` argument to `make_pkt()` in the receiver FSM.
2. The sender must **check the sequence number of the packet** being acknowledged by a received ACK message.
    - This is done by passing a `0` or `1` argument to `isACK()` in the sender FSM.

## Reliable Data Transfer over a Lossy Channel with Bit Errors: rdt3.0

Now let's also consider `the case where the underlying channel can lose packets`.

The protocol now has to deal with two additional concerns:

1. **How** to detect packet loss?
2. **What to do** when packet loss occurs?

<br/>

> 💡 We put the burden of detecting and recovering from lost packets **on the sender**.

Suppose the sender transmits a data packet, and either that packet or the receiver's ACK of that packet gets lost.

In either case, no reply comes back to the sender from the receiver.

<br/>

That is, the sender can't tell whether the data packet was lost, the ACK was lost, or the packet or ACK was simply overly delayed.

**If the sender is willing to wait long enough that it's certain a packet has been lost,** it can simply retransmit the data packet.

<br/>

---

<br/>

But **how long** must the sender wait to be certain that a packet has been lost?

<br/>

The sender must wait at least as long as:

> the `round-trip delay` between sender and receiver (including buffering at intermediate routers) + the `time needed to process a packet` at the receiver

<br/>

The approach adopted in practice is this:

> 💡 Pick a time value such that packet loss is likely, though not guaranteed, to have happened, and **if an ACK isn't received within that time, the packet is** `retransmitted`**.**

<br/>

This introduces the possibility of `duplicate data packets` in the sender-to-receiver channel,  
but as in rdt2.2, they can be handled using **packet sequence numbers**.

<br/>

---

<br/>

> Implementing a time-based retransmission mechanism requires  
<b>a `countdown timer` that can interrupt the sender after a given amount of time has expired</b>.

<br/>

So the sender needs to be able to:

1. start the timer each time a packet (either a first-time packet or a retransmission) is sent,
2. respond to a timer interrupt (i.e., take the appropriate action), and
3. stop the timer.

<br/>

## 3.4.2 Pipelined Reliable Data Transfer Protocols

rdt3.0 is a functionally correct protocol, but hardly anyone would be happy with its performance on today's **high-speed networks**.

<br/>

> 💡 The core performance problem with rdt3.0 comes from the fact that it's a `stop-and-wait protocol`.

A stop-and-wait protocol has very poor sender `utilization (or efficiency)`.

<br/>

<p align="center"><img width="380" alt="Stop-and-wait protocol in operation" src="https://user-images.githubusercontent.com/86337233/211394844-59fc6038-cbb8-4df0-823d-3a00bbc12081.png">

<br/>
<br/>

---

<br/>

The solution is:

> Allow the sender to **send multiple packets back-to-back without waiting for acknowledgments**. = `pipelining`

<br/>

In other words, fill the pipeline with many in-flight sender-to-receiver packets.

<br/>

<p align="center"><img width="380" alt="Pipelined protocol in operation" src="https://user-images.githubusercontent.com/86337233/211394855-29852bd1-16df-41bf-94a6-46cbda8a13fa.png">

<br/>
<br/>


The figures below show that if the sender is allowed to send three packets before having to wait for acknowledgments,  
**the sender's utilization is essentially tripled**.

In other words, efficiency increases by a factor of the window size.

<br/>

#### Stop-and-wait operation

<p align="center"><img width="700" alt="Stop-and-wait operation" src="https://user-images.githubusercontent.com/86337233/211394842-0a9b9db2-f2a5-4668-b5e8-bc8d634c323e.png">

<br/>
<br/>

#### Pipelined operation

<p align="center"><img width="700" alt="Pipelined operation" src="https://user-images.githubusercontent.com/86337233/211394851-46a5b475-2554-47f4-b33e-5699f909e4cb.png">

<br/>
<br/>

---

<br/>

Pipelining has the following consequences for reliable data transfer protocols.

<br/>

#### The range of sequence numbers must be increased.

Each in-flight packet must have a unique sequence number,

since there may be multiple in-flight, unacknowledged packets.

<br/>

#### The sender and receiver sides of the protocol may have to buffer more than one packet.

At a minimum, the sender has to buffer 'packets that have been transmitted but not yet acknowledged'.

Buffering of correctly received packets may also be needed at the receiver.

<br/>

#### The range of sequence numbers needed and the buffering requirements depend on how the data transfer protocol responds to lost, corrupted, and overly delayed packets.

Two basic approaches to pipelined error recovery:

1. `GBN (Go-Back-N)`
2. `SR (Selective Repeat)`

<br/>
<br/>

## 3.4.3 GBN

> 💡 In a `GBN (Go-Back-N) protocol`, the sender is allowed to transmit multiple packets (when available) without waiting for an acknowledgment.

> However, it may have no more than `a maximum allowable number, N, of unacknowledged packets` in the pipeline.

<br/>

The figure below shows the sender's view of the range of sequence numbers in a GBN protocol.

<br/>

<p align="center"><img width="850" alt="Sender's view of sequence numbers in GBN" src="https://user-images.githubusercontent.com/86337233/211394862-a28b3bd5-60b4-45b9-b16a-db23e1718476.png">

<br/>
<br/>

- `base` is defined as the sequence number of the oldest unacknowledged packet.
- `nextseqnum` is defined as the smallest unused sequence number (i.e., the sequence number of the next packet to be sent).

<br/>

This lets us identify four intervals in the range of sequence numbers:

1. Interval `[0, base-1]`: packets that have already been transmitted and acknowledged


2. Interval `[base, nextseqnum-1]`: packets that have been sent but not yet acknowledged


3. Interval `[nextseqnum, base+N-1]`: packets that can be sent immediately, should data arrive from the upper layer


4. `base+N and above`  
   → cannot be used until an unacknowledged packet currently in the pipeline (specifically, the packet with sequence number `base`) has been acknowledged.

<br/>

### Sliding-window protocol

> For packets that have been transmitted but not yet acknowledged,  
**the range of permissible sequence numbers** can be viewed as a '`window`' of size N over the range of sequence numbers.

- As the protocol operates, this window slides forward (to the right) over the sequence number space.
- N = window size

<br/>

That's why GBN is called a `sliding-window protocol`.

<br/>

### Packet sequence numbers

> In practice, a packet's sequence number is carried in a **fixed-length field** in the packet header.
>

- If `k` is the number of bits in the packet sequence number field, the range of sequence numbers is `[0, 2^k - 1]`.
- With a finite range of sequence numbers, all arithmetic involving sequence numbers must be done using `modulo 2^k arithmetic`.

<br/>

### Extended FSM for an ACK-based, NAK-free protocol

- Add the `base` and `nextseqnum` variables.
- Add operations on these variables and conditional actions involving them.

<br/>

#### Sender

<p align="center"><img width="770" alt="GBN - sender" src="https://user-images.githubusercontent.com/86337233/211394871-a9808254-013c-4858-b27c-6830d9602384.png">

<br/>
<br/>

The GBN sender must respond to three types of events.

<br/>

> 1️⃣ Invocation from above

1. When `rdt_send()` is called from above, the sender first checks whether the window is full  
   (i.e., whether there are N outstanding, unacknowledged packets).


2. If the window isn't full, a packet is created and sent, and the variables are updated accordingly.


3. If the window is full, the sender simply returns the data back to the upper layer.
    - This is an implicit indication that the window is full.
    - The upper layer will then presumably try `rdt_send()` again later.

<br/>

In a real implementation, the sender would more likely do one of the following:

1. Buffer (but not immediately send) this data.
2. Use a synchronization mechanism that only lets the upper layer call `rdt_send()` when the window isn't full  
   (e.g., a `semaphore` or a `flag`).

<br/>

> 2️⃣ Receipt of an ACK

In the GBN protocol,  
**an acknowledgment for a packet with sequence number n** is taken to be a `cumulative acknowledgment`.

This cumulative acknowledgment indicates that **all packets with sequence numbers up to and including n** have been correctly received at the receiver.

<br/>

> 3️⃣ A timeout event

The `timer` is used to **recover** from lost data or lost acknowledgment packets.

If a timeout occurs, **the sender resends ALL packets that have been previously sent but not yet acknowledged.**

<br/>

In the figure above, the sender uses a single timer,  
which can be thought of as a timer for <b>the oldest 'transmitted but not yet acknowledged' packet</b>.

- If an ACK is received but **there are still additional 'transmitted but not yet acknowledged' packets,**
  the timer is restarted.
- If there are no outstanding unacknowledged packets, the timer is stopped.

<br/>

#### Receiver

<p align="center"><img width="580" alt="GBN - receiver" src="https://user-images.githubusercontent.com/86337233/211394884-f585ef99-e84a-4b88-a268-794e31d1ad38.png">

<br/>
<br/>

- If a packet with sequence number `n` is received **correctly and in order**  
  (= the data last delivered to the upper layer came from a packet with sequence number `n-1`),  
  **the receiver sends an ACK for packet n and delivers the data portion of the packet to the upper layer.**


- In all other cases, the receiver discards the packet and `resends an ACK` **for the most recently received in-order packet**.

<br/>

### In GBN, the receiver discards out-of-order packets.

Suppose packet `n` is expected, but packet `n+1`, the one after it, arrives first.

*The receiver has to deliver data to the upper layer in order.*

Since data must be delivered in order, the receiver could buffer packet `n+1`  
**and deliver it to the upper layer later, after packet** `n` **has been received and delivered.**

<br/>

But if packet n is lost, the GBN retransmission rule means that **both** packet `n` and `n+1` will be retransmitted to the receiver anyway.

> 💡 Advantage: receiver buffering is simple (the receiver doesn't need to buffer **any out-of-order packets**!)

- What the **sender** must maintain
    1. the upper and lower bounds of its window
    2. the position of nextseqnum within this window
- What the **receiver** must maintain: the sequence number of the next in-order packet

<br/>

Of course, the downside of throwing away a correctly received packet is that a subsequent retransmission of that packet might be lost or garbled, so **even more retransmissions may be needed**.

<br/>

---

<br/>

The figure below shows GBN in operation with `a window size of four packets`.

- Window size is 4 → **the sender sends packets 0 through 3.**
- Before it can continue, it must **wait for one or more of these packets to be acknowledged.**

<br/>

<p align="center"><img width="500" alt="GBN in operation" src="https://user-images.githubusercontent.com/86337233/211394894-0ebcca6d-1174-446b-a2c4-e74ca263ab63.png">

<br/>
<br/>

- As each successive ACK (e.g., `ACK0`, `ACK1`) is received,
    1. the window slides forward, and
    2. the sender transmits one new packet (`pkt4` and `pkt5`, respectively).


- On the receiving side, since `pkt2` was lost, `pkt3, 4, 5` **are found to be out of order and are discarded.**

<br/>

### Event-based programming

Think back to the extended FSM we saw earlier.

An implementation would look like a set of procedures, each **implementing the actions to be taken in response to the various events that can occur**.

<br/>

> In this kind of `event-based programming`, the various procedures are  
> **called either by other procedures in the protocol stack or as the result of an interrupt.**

<br/>

Examples of such events at the sender:

1. A call from the upper-layer entity to invoke `rdt_send()`
2. A timer interrupt
3. A call from the lower layer to invoke `rdt_rcv()` when a packet arrives

<br/>

### Performance problems with GBN

GBN lets the sender fill the pipeline with packets, avoiding the channel utilization problems of stop-and-wait protocols.

<br/>

But there are scenarios where GBN itself suffers from performance problems.

When both the window size and the bandwidth-delay product are large, many packets can be in the pipeline.

<br/>

Because GBN retransmits many packets due to a single packet error, **it can end up retransmitting many packets unnecessarily.**

> As the probability of channel errors increases, the pipeline fills up with **unnecessary retransmissions**.


<br/>
<br/>

## 3.4.4 SR

> 💡 The `SR (Selective Repeat) protocol`  
> retransmits **only those packets it suspects** were received in error (lost or corrupted) at the receiver.

- This way, SR avoids unnecessary retransmissions.
- This individual, as-needed retransmission requires the receiver to **individually acknowledge** correctly received packets.

<br/>

A window size of `N` is used to **limit the number of outstanding, unacknowledged packets** in the pipeline.

Unlike GBN, though, the sender will already have received ACKs for some of the packets in the window.

<br/>

### SR sender's view of the sequence number space

<p align="center"><img width="720" alt="SR sender and receiver views of sequence-number space" src="https://user-images.githubusercontent.com/86337233/211394904-44a6f9a3-d889-487b-b88f-dbeb04e73e59.png">

<br/>
<br/>

- The SR receiver **acknowledges** `a correctly received packet` regardless of whether it's in order.


- When there's a `missing packet`:
    1. Out-of-order packets are buffered until the missing packet is received,  
       (missing packet = a packet with a lower sequence number that hasn't arrived yet)
    2. at which point a batch of packets can be delivered in order to the upper layer.  
       (re-order & reassemble the packets → in-order delivery to upper layer)

<br/>

### SR sender events and actions

> 1️⃣ Data received from above

When data is received from above, the SR sender checks the next available sequence number for the packet.

- If the sequence number is within the sender's window, the data is packetized and sent.
- Otherwise, as in GBN, it's either buffered or returned to the upper layer for later transmission.

<br/>

> 2️⃣ Timeout

`Timers` are again used to **protect against** lost packets.

However, since only a single packet is transmitted on timeout, **each packet must have its own logical timer.**

<br/>

> 3️⃣ ACK received

When an ACK is received, the SR sender marks that packet as received, provided it's within the window.

- If the packet's sequence number equals `send_base`, the window base is moved forward to the unacknowledged packet with the smallest sequence number.
- If the window moves and **there are untransmitted packets with sequence numbers that now fall within the window**, those packets are transmitted.

<br/>

### SR receiver events and actions

> 1️⃣ A packet with a sequence number in `[rcv_base, rcv_base+N-1]` is received correctly.

In this case, **the received packet falls within the receiver's window**, and a `selective ACK packet` is returned to the sender.

- If the packet wasn't received before, it's buffered.
- If the packet's sequence number equals the base of the receive window (`rcv_base`),  
  then this packet, along with any previously buffered, consecutively numbered packets (starting with `rcv_base`), is delivered to the upper layer.

<br/>

> 2️⃣ A packet with a sequence number in `[rcv_base-N, rcv_base-1]` is received.

In this case, **an ACK must be generated**, even though this is a packet the receiver has previously acknowledged.

<br/>

> 3️⃣ Otherwise, **ignore** the packet.

<br/>

## In SR, the Sender's and Receiver's Windows Aren't Always the Same

Step 2 of the SR receiver events and actions: a packet with a sequence number in `[rcv_base-N, rcv_base-1]` is received.

<br/>

> The important point here is that the receiver `re-acknowledges` **'already received packets' with certain sequence numbers below** the current window `base`, **rather than ignoring them**!

e.g.,  
Given the sender's and receiver's sequence number spaces, if there's no `ACK for packet send_base` going from the receiver to the sender,  
the sender will eventually retransmit packet `send_base` *(even though it's clear to us that the receiver has already received that packet)*.

<br/>

If the receiver didn't acknowledge this packet, the sender's window would never move forward.

<br/>

> 💡 **The sender and receiver won't always have the same view of what has and hasn't been received correctly.**

→ This means that in the SR protocol, the sender's and receiver's windows won't always coincide.

<br/>

---

<br/>

`The lack of synchronization between sender and receiver windows` has serious consequences **when we're faced with a finite range of sequence numbers**.

<br/>

e.g.,

- A finite range of four packet sequence numbers: `0, 1, 2, 3`
- Window size: `3`

<br/>

Suppose packets 0 through 2 are transmitted, correctly received, and acknowledged at the receiver.

At that point, the receiver's window is over the fourth, fifth, and sixth packets, which have sequence numbers `3, 0, 1`, respectively.

<br/>

#### Scenario 1

1. **The ACKs for the first three packets are lost**, and the sender retransmits these packets.


2. The receiver then receives a packet with sequence number `0` (a **copy** of the first packet sent).

<br/>

<p align="center"><img width="550" alt="Scenario 1" src="https://user-images.githubusercontent.com/86337233/211394834-3ca59693-1674-474f-b726-92b6b4db0f61.png">

<br/>
<br/>

#### Scenario 2

1. **The ACKs for the first three packets are all delivered correctly.**


2. The sender moves its window forward and sends the fourth, fifth, and sixth packets, with sequence numbers `3, 0, 1`, respectively.


3. The packet with sequence number `3` is lost, but the packet with sequence number `0` (a packet containing **new** data) arrives.

<br/>

<p align="center"><img width="550" alt="Scenario 2" src="https://user-images.githubusercontent.com/86337233/211394820-f3805860-5058-49e5-8e01-c63729a33699.png">

<br/>
<br/>

#### Now consider the receiver's point of view

*The receiver can't see the actions taken by the sender.*

<br/>

All the receiver observes is the sequence of messages it receives from and sends into the channel, and for the two scenarios above, that sequence is **identical**.

That is, **there's no way to distinguish** `the original transmission of the fifth packet` from `a retransmission of the first packet`.

<br/>

### How large can the window be?

> For SR protocols, the `window size` **must be less than or equal to half the size of the sequence number space.**

## Packet Reordering

At the very beginning, we discussed reliable data transfer protocols under `the assumption that packets cannot be reordered within the channel between sender and receiver`.

> This is generally a reasonable assumption when sender and receiver are connected by a single physical wire.  
> But when <b>the 'channel' connecting the two</b> is a network, `packet reordering` can occur.

<br/>

Because of packet reordering, old copies of a packet with sequence or acknowledgment number `x` can show up,  
even though neither the sender's nor the receiver's window contains `x`.

<br/>

> A `channel that reorders packets` can essentially be thought of as **buffering packets** and spontaneously emitting them at any point in the future.

Since sequence numbers can be reused, some care must be taken to guard against such duplicate packets.

<br/>

The approach taken in practice is to make sure a sequence number isn't reused  
**until the sender is 'sure' that any previously sent packets with sequence number x are no longer in the network.**

This is done by `assuming that a packet cannot "live" in the network for longer than some fixed maximum amount of time`.

<br/>
<br/>

## Summary of Reliable Data Transfer Mechanisms and Their Use

### Checksum

Used to detect **bit errors** in a transmitted packet.

<br/>

### Timer

Used to **time out/retransmit** a packet, possibly because the packet (or its ACK) was lost within the channel.

<br/>

### Timeout

Why it happens:

1. The packet was delayed but not lost (`premature timeout`)

2. The packet was received by the receiver, but the receiver-to-sender `ACK was lost`

→ So a packet received by the receiver may be a duplicate copy.

<br/>

### Sequence number

Used for sequential numbering of data packets flowing from sender to receiver.

- `Gaps in the sequence numbers of received packets`: let the receiver detect a lost packet.
- `Packets with duplicate sequence numbers`: let the receiver detect duplicate copies of a packet.

<br/>

### Acknowledgment

Used by the receiver to tell the sender that a packet or set of packets has been **received correctly**.

- Typically carries the sequence number of the packet or packets being acknowledged.
- Can be individual or cumulative, depending on the protocol.

<br/>

### Negative acknowledgment

Used by the receiver to tell the sender that a packet has **not been received correctly**.

- Typically carries the sequence number of the packet that wasn't received correctly.

<br/>

### Window, pipelining

The sender may be **restricted to sending only packets with sequence numbers that fall within a given range**.

By allowing multiple packets to be transmitted but not yet acknowledged, sender utilization can be increased over stop-and-wait operation.

The `window size` may be set based on the receiver's ability to receive and buffer messages, the level of congestion in the network, or both.
