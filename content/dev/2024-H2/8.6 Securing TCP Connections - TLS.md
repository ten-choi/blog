# 8.6 Securing TCP Connections: TLS

The enhanced version of TCP with added security services is commonly called `TLS (Transport Layer Security)`.

TLS extends TCP to provide security services: confidentiality, data integrity, server authentication, and client authentication.

Because TLS secures TCP, it can be used by any application that runs over TCP.

<br/>

<p align="center"><img width="500" src="https://user-images.githubusercontent.com/76640167/217584343-d3d9b2f4-36a8-4d8e-a158-8765be3623bf.png" alt="TLS"></p>

TLS provides a simple socket-based API, similar to TCP's API.

TLS lives in the application layer, but from a developer's point of view it's a transport protocol that provides TCP services enhanced with security services.

<br/>

## 8.6.1 The Big Picture: Almost-TLS

To understand TLS, let's first go over a simplified version of it, `almost-TLS`.

`almost-TLS` has three phases: handshake, key derivation, and data transfer.

<br/>

### Handshake

<p align="center"><img width="500" src="https://user-images.githubusercontent.com/76640167/217584333-c8cd0c65-1518-4207-82d2-bef569cd6208.png" alt="handshake"></p>

1. The client establishes a TCP connection with the server.
2. The client verifies that the server really is the server.
    - The client sends a hello message, and the server sends its CA-certified certificate, so the client can trust that the public key in the certificate belongs to the server.
3. The client generates a Master Secret (MS), which the server and client will use to generate all the symmetric keys needed for the TLS session, and sends it.
    - When sending the MS, the client encrypts it with the server's public key to create the EMS (Encrypted Master Secret).
    - The server decrypts the EMS with its private key to get the MS.
    - In other words, the two now share an MS that only they know.

<br/>

### Key derivation

The shared MS could be used as the symmetric session key for all encryption and data integrity checks, but it's generally safer to use different keys for each.

So the MS is used to create four keys:

- E(b) = session encryption key for data sent from the client to the server
- M(b) = session HMAC (message authentication code) key for data sent from the client to the server
- E(a) = session encryption key for data sent from the server to the client
- M(a) = session HMAC (message authentication code) key for data sent from the server to the client

This is done by simply slicing the MS into four keys.

The two encryption keys are used to encrypt data, and the two HMAC keys are used to verify data integrity.

<br/>

### Data transfer

Since TCP is a byte-stream protocol, it's natural for TLS to encrypt application data continuously and keep passing the encrypted data to TCP.

So when should the HMAC be computed?

Clearly, we can't defer the integrity check of all the data sent during the whole session until the TCP session ends.

TLS breaks the data stream into records, appends an HMAC to each record for integrity checking, and then encrypts the `record+HMAC`.

To create the HMAC, the client feeds the record data and the key M(b) into a hash function.

It then encrypts the `record+HMAC` package with E(b) and sends it over TCP.

<br/>

But if an intruder can insert, delete, or swap segments in the TCP segment stream, this approach isn't secure.

For example, if an intruder swaps the order of two segments, adjusts the TCP sequence numbers to match, and sends them to the server, the server's TLS will pass them up to the application layer without complaint.

<br/>

TLS solves this with sequence numbers.

The client maintains a sequence number counter and increments it for each TLS record it sends.

When computing the HMAC, it hashes the combination of the `HMAC key M(b)`, the `record data`, and the `sequence number`.

The server tracks the client's sequence numbers and includes the appropriate sequence number in its own HMAC calculation to verify the record's data integrity.

<br/>

### TLS record

The first three fields aren't encrypted.

The type field indicates whether the record is a handshake message or a message carrying data.

## 8.6.2 A More Complete Picture: TLS

Now let's look at the full version of TLS.

### TLS handshake

TLS doesn't force the server and client to use a specific symmetric key algorithm or public key algorithm.

Instead, they agree on the cryptographic algorithms during the handshake and send each other nonces to generate the session keys.

**Scenario**

1. The client sends a list of the cryptographic algorithms it supports, along with a nonce.
    - The reason for the nonce: if an intruder eavesdrops on all the messages and replays them to the server as-is, the values match even with sequence numbers, so the server would accept them as legitimate.
    - Including a nonce makes every session's messages unique, which strengthens security.
2. From the list, the server picks a symmetric key algorithm, a public key algorithm, and an HMAC algorithm along with HMAC keys.
3. The server sends its choices, its certificate, and a server nonce to the client.
4. The client verifies the certificate, extracts the server's public key, and generates a `PMS (Pre-Master Secret)`. It encrypts the PMS with the server's public key and sends it to the server.
5. Using the same key derivation function, the client and server compute the MS from the PMS and the nonces.
6. The MS is sliced up to generate the two encryption keys and two HMAC keys.
7. From then on, all messages are encrypted and authenticated.
8. The client sends an HMAC of all the handshake messages.
9. The server sends an HMAC of all the handshake messages.
    - Steps 8 and 9 check that the messages exchanged so far match, guarding against an intruder having tampered with the initial unencrypted messages.

<br/>

### Connection closure

Simply sending a TCP FIN segment right away to close the connection can cause problems.

It opens the door to a `truncation attack`, where an intruder sends its own TCP FIN segment to cut the session.

To fix this, the record's type field indicates whether the record is meant to close the TLS session.
