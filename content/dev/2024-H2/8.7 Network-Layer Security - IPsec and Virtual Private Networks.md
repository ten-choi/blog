# 8.7 Network-Layer Security: IPsec and Virtual Private Networks

The IP security protocol, known as IPsec, provides security at the network layer.

<br/>

### IPsec Characteristics

- It protects IP datagrams between any two network-layer entities, such as hosts or routers.
    - It **encrypts the payload of the datagram**, so things like TCP segments are encrypted.
- Beyond the confidentiality above, it can also provide security services such as source authentication, data integrity, and replay-attack prevention.

<br/>

## 8.7.1 IPsec and Virtual Private Networks

Organizations spread across multiple locations often want their own IP network so that their hosts and servers can send data to each other securely and confidentially.

To do this, they can actually deploy a physically separate network, with its own routers, links, and DNS infrastructure, completely isolated from the public Internet. Such a network is called a `private network`.

<br/>

Instead of a private network, which is expensive to maintain, organizations today deploy a `VPN` on top of the existing public Internet.

With a `VPN`, traffic between the organization's offices is sent over the public Internet.

However, to provide confidentiality, that traffic is encrypted before it enters the public Internet.

<br/>

<p align="center"><img width="500" src="https://user-images.githubusercontent.com/76640167/217747985-e18a7a43-82de-41fe-831c-cb5fee6a16d1.png" alt="VPN"></p>

When traffic doesn't cross the public Internet, plain IPv4 datagrams are used. When it does, an IPsec-capable router converts the IPv4 datagram into an IPsec datagram and then sends it out to the Internet.

An IPsec datagram has a standard IPv4 header, so routers on the public Internet forward it just like an ordinary IPv4 datagram.

The payload of an IPsec datagram actually includes an IPsec header, which is used for IPsec processing.

<br/>

## 8.7.2 The AH and ESP Protocols

When a source IPsec entity sends secure datagrams to a destination entity, it uses either the AH protocol or the ESP protocol.

- AH protocol
    - Provides source authentication and data integrity, but not confidentiality.
- ESP protocol
    - Provides source authentication, data integrity, and confidentiality.
    - Since confidentiality is needed in most cases, ESP is far more widely used.

<br/>

## 8.7.3 Security Associations (SA)

Before sending IPsec datagrams, the source and destination entities establish a logical connection at the network layer. This is called a `security association (SA)`.

An SA is unidirectional, so two SAs are needed for the two sides to send data to each other.

If there are n hosts in the organization, 2n SAs are needed; if there are m branch routers, another 2m are needed, for a total of `2n + 2m`.

<br/>

Not all traffic that a gateway router or laptop sends to the Internet is protected by IPsec.

For example, a host might connect to a web server on the public Internet such as Google, rather than a host inside the organization that needs security. So routers and laptops send both plain IPv4 datagrams and IPsec datagrams.

<br/>

<p align="center"><img width="500" src="https://user-images.githubusercontent.com/76640167/217747947-c3029c7f-3030-4b01-87e5-5cafe95c7f89.png" alt="SA"></p>

R1 keeps the following state information for the SA:

- A 32-bit identifier for the SA, called the SPI
- The origin interface of the SA (200.168.1.100) and the destination interface (193.68.2.23)
- The type of encryption used (AES, DES, etc.)
- The encryption key
- The type of integrity check (MD5, SHA, etc.)
- The authentication key

R1 uses these to encrypt and authenticate, and R2 maintains the same state information as well.

<br/>

Since there can be many SAs whose state must be maintained, an IPsec entity stores the state information for all of its SAs in a data structure in its OS kernel called the `SAD (security association database)`.

<br/>

## 8.7.4 The IPsec Datagram

<p align="center"><img width="500" src="https://user-images.githubusercontent.com/76640167/217747916-15b647c6-8c1f-4072-ab32-268dd279653b.png" alt="IPsec datagram format"></p>

Router R1 converts the original IPv4 datagram into an IPsec datagram using the following steps:

1. Append an ESP trailer to the back of the original IPv4 datagram.
    - The original IPv4 datagram contains the original destination and source IP addresses.
    - The **ESP trailer** consists of three fields: padding, pad length, and next header.
        - Padding: added to the original datagram so that the final message can be split into a whole number of fixed-length blocks.
        - Pad length: tells how many padding bits were inserted, so the padding can be removed.
        - Next header: indicates the type of data in the payload (e.g., UDP).
2. Encrypt the result using the algorithm and key specified by the SA.
3. Prepend the ESP header field to the encrypted result. Let's call the resulting package the "enchilada."
    - The ESP header contains the SPI and a sequence number.
        - SPI: tells the receiving entity which SA the datagram belongs to. The receiver uses the SPI to look up its SAD and determine the appropriate authentication and decryption algorithms and keys.
        - Sequence number: used to defend against replay attacks.
4. Create an authentication MAC over the whole enchilada using the algorithm and key specified by the SA.
5. Append the MAC to the enchilada to form the payload.
    - The secret MAC key is appended to the enchilada, and a fixed-length hash is computed over the result.
6. Create a brand-new IP header with the standard IPv4 header fields and prepend it to the payload.
    - The source and destination addresses in the new IP header are the router interfaces the datagram is sent between.
    - The upper-layer protocol field in the header doesn't indicate TCP/UDP; instead it uses a value indicating that this is IPsec using the ESP protocol.

The resulting IPsec datagram is a genuine IPv4 datagram: a standard IPv4 header followed by a payload.

The routers along the way forward it to the destination router interface without knowing it contains IPsec-encrypted information.

<br/>

When router R2 receives the IPsec datagram, it does the following:

1. It looks at the IP header and sees that the IPsec ESP protocol must be applied.
2. Looking into the enchilada, R2 uses the SPI to determine which SA the datagram belongs to.
3. It computes the MAC of the enchilada and checks that it matches the value in the ESP MAC field.
    - Only if they match has the datagram not been tampered with.
4. It checks the sequence number field to make sure the datagram isn't a replay.
5. It decrypts the encrypted part using the decryption algorithm and key associated with the SA.
6. It forwards the original IP datagram into the branch network so it can reach its final destination.

Along with the SAD, an IPsec entity maintains a data structure called the `SPD (security policy database)`.

The SPD indicates which kinds of datagrams (determined by source IP address, destination IP address, and protocol type) should be processed with IPsec, and which SA should be used for them.

In other words, the information in the SPD says what to do with an arriving datagram, and the information in the SAD says how to do it.

<br/>

### 8.7.5 IKE: Key Management in IPsec

In a large VPN made up of hundreds or thousands of IPsec routers and hosts, manually entering SA information into each endpoint's SAD is impossible.

So an automated way of creating SAs is needed, and for this we use the `IKE protocol`.

<br/>

Each IPsec entity has a certificate that includes its public key.

As in SSL, the IKE protocol lets the two entities exchange certificates and negotiate authentication and encryption algorithms, and it lets them securely exchange the key material needed to generate session keys for the IPsec SAs.

IKE goes through two phases to do this.

<br/>

### Phase 1

R1 and R2 exchange two pairs of messages.

- In the first exchange, the two sides use the Diffie-Hellman algorithm to establish an IKE SA between the routers.
    - An IKE SA is completely different from an IPsec SA.
    - The IKE SA provides an authenticated and encrypted channel between the two routers.
    - During this first exchange, the keys for encrypting and authenticating the IKE SA are established.
    - A master secret is also created, which will be used to compute the IPsec SA keys in phase 2.
    - In the first exchange, neither side reveals its identity by signing with its private key.
- In the second exchange, both sides reveal their identities to each other by signing their messages.
    - However, since the messages are sent over the secured IKE SA channel, their identities aren't exposed to a passive eavesdropper.
    - The two sides also negotiate the IPsec encryption and authentication algorithms to be used by the IPsec SAs.

<br/>

### Phase 2

The two sides establish one SA in each direction.

By the end of this phase, the encryption and authentication session keys for these two SAs have been established on both sides.

From then on, the SAs can be used to create secured datagrams.
