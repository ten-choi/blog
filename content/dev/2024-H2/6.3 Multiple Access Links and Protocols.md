# 6.3 Multiple Access Links and Protocols

### Two types of network links

- `Point-to-point link`
    - A single sender at one end of the link and a single receiver at the other end.
    - `PPP (point-to-point protocol)` and `HDLC (high-level data link control)` belong here. (Covered later.)
- `Broadcast link`
    - Multiple sending and receiving nodes are all connected to the same, single, shared broadcast channel.
    - The term "broadcast" is used because when any one node transmits a frame, the channel broadcasts it and every other node receives a copy.

<br/>

### Various multiple access channels

<p align="center"><img width="300" alt="Multiple access links" src="https://user-images.githubusercontent.com/76640167/214252181-cbe924c1-ba6e-4194-bb26-cb62090a1d55.png">

<br/>

### The multiple access problem

Since every node can transmit frames, two or more nodes may transmit on the broadcast channel at the same time, and when that happens **all nodes receive multiple frames at once**.

That is, **the transmitted frames collide at every receiver, and no receiving node can make sense of any of the transmitted frames.**

So all frames involved in a collision are lost, and if many nodes want to transmit frames frequently, there will be many collisions and much of the broadcast channel's bandwidth will be wasted.

<br/>

### Multiple access protocols

For a broadcast channel with a rate of R bits per second, a multiple access protocol should ideally have the following characteristics:

1. When only one node has data to send, that node has a throughput of R bps.
2. When M nodes have data to send, each node has a throughput of R/M bps.
    - Not necessarily at every instant; it means each node has an average throughput of R/M over some suitably defined interval of time.
3. It's decentralized, so there's no master node whose failure could bring down the whole system.
4. It's simple, so it's inexpensive to implement.

<br/>

## 6.3.1 Channel Partitioning Protocols

<p align="center"><img width="300" alt="TDM FDM" src="https://user-images.githubusercontent.com/76640167/214252177-bf3b863e-80dd-4ae6-a463-0c2c67af4e4e.png">

### Time-division multiplexing (TDM)

Suppose the channel supports N nodes and its transmission rate is R bps.

TDM divides time into `time frames` and further divides each time frame into N `time slots`.

Each time slot is then assigned to one of the N nodes.

Whenever a node has a packet to send, it **transmits the packet during its assigned time slot in the revolving TDM frame**.

<br/>

**Pros**

- Eliminates collisions.
- Perfectly fair.

<br/>

**Cons**

- A node is limited to a rate of R/N even when it's the only node with packets to send.
- A node must always wait for its turn in the transmission sequence.

<br/>

### Frequency-division multiplexing (FDM)

Divides the R bps channel into different frequencies, each with a bandwidth of R/N, and assigns each frequency to one of the N nodes.

That is, it creates N smaller channels of R/N bps out of a single, larger R bps channel.

It has the same pros and cons as TDM.

<br/>

### Code division multiple access (CDMA)

CDMA assigns a different **code** to each node.

Each node then **uses its unique code to encode the data bits it sends**.

<br/>

**Pros**

- If the codes are chosen carefully, CDMA networks allow different nodes to transmit simultaneously.
- Each receiver can still correctly receive a sender's encoded data bits despite interfering transmissions from other nodes.

<br/>

## 6.3.2 Random Access Protocols

In a random access protocol, a transmitting node always transmits at the channel's full rate, R bps.

When there's a collision, each node involved in the collision repeatedly retransmits its frame until it gets through without a collision.

<br/>

When a frame collides, the node doesn't retransmit it right away; it waits a random delay before retransmitting.

That way, one of the colliding nodes can pick a delay sufficiently shorter than the others' and sneak its frame onto the channel without a collision.

<br/>

### Slotted ALOHA

<p align="center"><img width="300" alt="Slotted ALOHA" src="https://user-images.githubusercontent.com/76640167/214252171-bb6a376c-f16c-4984-91a6-6360d106db1e.png">

**How it works**

1. When a node has a new frame to send, it waits until the beginning of the next slot and transmits the entire frame in that slot.
2. If there's no collision, the node has successfully transmitted its frame and doesn't need to retransmit it.
3. If there's a collision, the node detects it before the end of the slot. The node then retransmits the frame in each subsequent slot with probability p (between 0 and 1) until the frame is transmitted without a collision.
4. Step 3 is repeated until there's no collision.

<br/>

**Pros**

- Allows a single active node to continuously transmit frames at the channel's full rate, R.
- Highly decentralized, since each node detects collisions and independently decides when to retransmit.
- Extremely simple.

<br/>

**Cons**

- Nodes must be synchronized on when slots begin.
- When there are many active nodes, some slots end up wasted due to collisions.
- Some slots are left empty when all active nodes refrain from transmitting because of the probabilistic transmission policy.

The only slots that aren't wasted are those in which exactly one node transmits; such a slot is called a `successful slot`.

<br/>

**Efficiency**

With N nodes, the probability that a given slot is a successful slot is the probability that exactly one node transmits and the remaining N-1 nodes don't.

If each node transmits with probability p, the probability that a given node succeeds is `p x (1-p)^(N-1)`.

Since there are N nodes, the probability that any one node succeeds is `N x p x (1-p)^(N-1)`.

<br/>

To find the maximum efficiency, we need to find the p that maximizes this expression.

To get the maximum efficiency with a large number of active nodes, we take the limit as N approaches infinity.

Doing this, we find that the maximum efficiency is `1/e ≈ 0.37`.

<br/>

**In other words, when many nodes have lots of frames to send, at best only 37% of the slots do useful work.**

<br/>

### ALOHA

<p align="center"><img width="300" alt="ALOHA" src="https://user-images.githubusercontent.com/76640167/214252168-877732ca-dd9d-4dba-8dcd-253213b0a71c.png">

Pure ALOHA has no notion of slots.

<br/>

**How it works**

1. When a frame arrives, the node immediately transmits the entire frame onto the broadcast channel.
2. If there's a collision, the node immediately retransmits the frame with probability p.
3. If it doesn't retransmit immediately, the node waits for one frame transmission time.
4. After waiting, it transmits the frame with probability p, or waits another frame time with probability 1-p.

<br/>

**Efficiency**

At any given time, the probability that a node is transmitting a frame is p.

Suppose node i begins transmitting a frame at time t0.

<br/>

For this frame to be transmitted successfully, no other node can begin transmitting during `[t0-1, t0]`. If one did, its transmission would overlap with the beginning of node i's transmission and they would collide.

The probability that no other node begins transmitting during this interval is `(1-p)^(N-1)`.

Likewise, no other node can begin transmitting while node i is transmitting, and the probability of that is also `(1-p)^(N-1)`.
<br/>

So the probability of a successful transmission, including the probability p that node i transmits, is `p x (1-p)^(2(N-1))`. Taking the limit as with slotted ALOHA, the maximum efficiency is `1/(2e)`, exactly half that of slotted ALOHA.

<br/>

In other words, pure ALOHA is fully decentralized and needs no synchronization, but gives up some efficiency in return.

<br/>

### CSMA

In the two protocols above, a node transmits regardless of whether other nodes are already transmitting.

That leads to collisions and, ultimately, lower efficiency.

<br/>

Let's look at the rules for avoiding those collisions.

- Carrier sensing
    - If another node is transmitting a frame onto the channel, a node waits until it detects no transmission for a short amount of time, and then begins transmitting.
- Collision detection
    - If a node detects that another node is transmitting an interfering frame, it stops its own transmission, waits a random amount of time, and then repeats the sense-and-transmit-when-idle cycle.

<br/>

**When collisions happen in CSMA**

<p align="center"><img width="300" alt="CSMA" src="https://user-images.githubusercontent.com/76640167/214252166-c56ee5cb-eb17-48e2-92a5-f4d67029ce34.png">

1. At time t0, node B senses that the channel is idle, since no other node is transmitting.
2. B begins transmitting, and its bits propagate in both directions along the broadcast medium.
    - The downward propagation over time shows that B's bits take a nonzero amount of time to actually propagate along the broadcast medium.
3. At time t1, node D has a frame to send. Although B is transmitting at t1, B's bits haven't reached D yet, so D senses the channel as idle at t1.
4. D begins transmitting, and shortly afterward B's bits and D's bits start to interfere with each other.

That is, the longer the `end-to-end channel propagation delay` of the broadcast channel, the more often a carrier-sensing node will fail to sense a transmission that has already begun at another node. So the `end-to-end channel propagation delay` plays a crucial role in determining CSMA's performance.

<br/>

### CSMA/CD

<p align="center"><img width="300" alt="CSMA/CD" src="https://user-images.githubusercontent.com/76640167/214252158-5f9891cb-21c6-4792-8f30-d72bc2207215.png">

Whereas CSMA doesn't perform collision detection, CSMA/CD detects collisions and aborts the transmission immediately.

<br/>

**How it works**

1. The adapter obtains a datagram from the network layer, prepares a link-layer frame, and puts the frame in the adapter's buffer.
2. If the adapter senses that the channel is idle, it starts transmitting the frame.
    - If the adapter senses that the channel is busy, it **waits until it senses no signal energy and then starts transmitting the frame**.
3. While transmitting, the adapter **monitors for the presence of signal energy from other adapters** using the broadcast channel.
4. If the adapter transmits the entire frame without detecting signal energy from other adapters, it's done with the frame.
    - If it does detect such energy, it **aborts the transmission of its frame**.
5. After aborting, the adapter waits a **random amount of time** and then returns to step 2.
    - If the wait were a fixed time rather than a random one, nodes that transmitted at the same time would wait the same amount of time, transmit again, and keep colliding.

<br/>

**The algorithm for choosing the random time: binary exponential backoff**

<br/>

When transmitting a frame that has experienced n collisions, a node chooses a value K at random from `{0,1,2,…,2^n - 1}` and waits `K x bit times`.

For Ethernet, this is K x 512 bit times (K x the time needed to send 512 bits into the Ethernet), and the maximum value of n is capped at 10.

<br/>

So the more collisions a frame experiences, the larger the range K is chosen from, growing exponentially.

When a new frame is prepared, the node runs CSMA/CD without taking any recent collisions into account, so it may get transmitted ahead of frames from nodes that experienced collisions.

<br/>

**Efficiency**

```
d(prop) = the maximum time it takes signal energy to propagate between any two adapters
d(trans) = the time to transmit a maximum-size Ethernet frame

efficiency = 1/(1+5d(prop)/d(trans))
```

As the propagation delay d(prop) approaches 0, the efficiency approaches 1, because colliding nodes abort immediately without tying up the channel.

As d(trans) becomes very large, the efficiency also approaches 1, because once a frame grabs the channel it holds on to it for a very long time.

<br/>

So the channel is doing productive work nearly all of the time.

<br/>

## 6.3.3 Taking-Turns Protocols

The two desirable properties of a multiple access protocol are:

1. When only one node is active, it has a throughput of R bps.
2. When M nodes are active, each node has a throughput of nearly R/M bps.

The ALOHA and CSMA protocols have the first property but not the second.

This is what motivated the development of `taking-turns protocols`.

<br/>

### Polling protocol

One of the nodes is designated as the master node.

**The master node polls each of the nodes in a round-robin fashion.**

<br/>

Specifically, the master node first sends a message to node 1 telling it the maximum number of frames it can transmit; after node 1 has sent its frames, the master does the same with the next node, and continues this way, polling each node in a cyclic manner.

<br/>

**Pros**

- Eliminates empty slots.

<br/>

**Cons**

- Introduces a polling delay.
    - If only one node is active, then every time that active node has sent its maximum number of frames, the master node still has to poll each of the inactive nodes in turn.
- If the master node fails, the entire channel becomes inoperative.

<br/>

### Token-passing protocol

A small, special-purpose frame known as a `token` is passed among the nodes in a fixed order.

For example, node 1 always sends the token to node 2, node 2 to node 3, and node N to node 1.

<br/>

When a node receives the token, it holds onto it only if it has frames to transmit; otherwise, it passes the token on.

After transmitting up to the maximum number of frames, it forwards the token to the next node.

<br/>

**Pros**

- Decentralized and highly efficient.

<br/>

**Cons**

- If a single node fails, the whole channel can go down.
- If a node fails to release the token, some recovery procedure must be invoked to get the token back in circulation.

<br/>

## 6.3.4 DOCSIS: The Link-Layer Protocol for Cable Internet Access

<p align="center"><img width="300" alt="DOCSIS" src="https://user-images.githubusercontent.com/76640167/214252151-206f9c41-58d2-4547-915a-25b1389c9e20.png">

<br/>

`DOCSIS (Data-over-Cable Service Interface Specifications)` defines the architecture and protocols of a cable data network.

DOCSIS uses FDM to divide the downstream and upstream network segments into multiple frequency channels.

Each upstream and downstream channel is a broadcast channel.

<br/>

### Downstream channels

Each downstream channel sits in the 24 to 192 MHz range and provides a maximum throughput of roughly 1.6 Gbps.

Frames sent down a downstream channel by the CMTS are received by all cable modems receiving on that channel. (Since there's only a single CMTS transmitting on the downstream channel, there's no multiple access problem.)

The CMTS sends a control message known as a MAP message on the downstream channel, telling each cable modem which `mini-slots` it may transmit in during the time interval specified in the MAP message.

<br/>

### Upstream channels

Upstream channels sit in the 6.4 to 96 MHz range and provide a maximum upstream throughput of roughly 1 Gbps.

Multiple cable modems share the same upstream channel (frequency) to the CMTS, so collisions can occur.

Like TDM, each upstream channel is divided into intervals of time, and each interval consists of a sequence of `mini-slots` in which cable modems can transmit to the CMTS.

Because `mini-slots` are explicitly assigned to individual cable modems, the CMTS can be sure there will be no collisions during those `mini-slots`.

<br/>

Among the `mini-slots`, there's a specific set of `mini-slots` for sending `mini-slot-request frames` to the CMTS.

Each cable modem sends a `mini-slot-request frame` to the CMTS, which is how the CMTS learns which cable modems have data to send.

<br/>

`Mini-slot-request frames` are sent in a random access manner, so they can collide.

A cable modem doesn't perform collision detection; if it doesn't receive a response to its requested allocation in the next downstream control message, it infers that its mini-slot-request frame collided.

A cable modem that infers a collision uses `binary exponential backoff` to defer retransmitting.
