# 6.7 Retrospective: A Day in the Life of a Web Page Request

<p align="center"><img width="700" alt="Web page request" src="https://user-images.githubusercontent.com/76640167/214876874-d91c588c-09fc-4b25-ae23-2b2c655da4bc.png">

Let's walk through what happens when a student, Bob, connects his laptop to his school's Ethernet switch and downloads `www.google.com`.

<br/>

## 6.7.1 Getting Started: DHCP, UDP, IP, and Ethernet

Bob turns on his laptop and plugs it into an Ethernet cable connected to the school's Ethernet switch.

Assume the school's router is connected to the ISP `comcast.net`, which provides DNS service for the school; the DNS server lives in the Comcast network rather than the school network, and the DHCP server runs on the router.

1. The operating system on Bob's laptop creates a **DHCP request message** and puts it in a UDP segment with destination port 67 (DHCP server) and source port 68 (DHCP client).
   This UDP segment is placed in an IP datagram with the **broadcast** `IP destination address (255.255.255.255)` and a source `IP address of 0.0.0.0` (since the laptop doesn't have an IP address yet).

2. The IP datagram containing the DHCP request message is placed in an Ethernet frame.
   **The Ethernet frame's destination MAC address is set to** `FF:FF:FF:FF:FF:FF` **so that the frame is broadcast** to every device connected to the switch.
   The frame's source MAC address is that of Bob's laptop, `00:16:D3:23:68:8A`.

3. The broadcast Ethernet frame containing the DHCP request is the first frame Bob's laptop sends to the Ethernet switch. **The switch broadcasts it out of all of its output ports**.
    - At this point, the switch also updates its switch table through **self-learning**.
4. The router receives the broadcast Ethernet frame containing the DHCP request on its interface with MAC address `00:22:6B:45:1F:1B`, and extracts the IP datagram from the Ethernet frame.
   The datagram's broadcast IP destination address indicates that this IP datagram should be processed by upper-layer protocols at this node.
   So the datagram's UDP segment is demultiplexed up to UDP, and the DHCP request message is extracted from the UDP segment and handed to the DHCP server.

5. Suppose the DHCP server running on the router can allocate IP addresses in the CIDR block `68.85.2.0/24`.
   Assume the DHCP server allocates address `68.85.2.101` to Bob's laptop.
   The DHCP server creates a **DHCP ACK message** containing this IP address, the DHCP server's IP address, the IP address of the default gateway router, and the subnet block.
   This message goes into a UDP segment, the segment into an IP datagram, and the datagram into an Ethernet frame.
   The Ethernet frame has the MAC address of the router's interface on the school network as its source MAC address, and the MAC address of Bob's laptop as its destination MAC address.

6. The Ethernet frame containing the DHCP ACK is sent (unicast) by the router to the switch.
   Because the switch is **self-learning** and previously received an Ethernet frame (containing the DHCP request) from Bob's laptop, it knows to forward a frame addressed to `00:16:D3:23:68:8A` only out of the output port leading to Bob's laptop.

7. Bob's laptop receives the frame containing the DHCP ACK, extracts the UDP segment from the Ethernet frame, and then extracts the DHCP ACK message.
   Bob's DHCP client records its IP address and the DNS server's IP address, and also installs the default gateway's address in its **IP forwarding table**.
   From then on, Bob's laptop sends every datagram whose destination is outside its subnet to the default gateway.

<br/>

## 6.7.2 Still Getting Started: DNS and ARP

Finding the IP address of `www.google.com`

1. The laptop's operating system creates a **DNS query message**, putting `www.google.com` in the question section of the message.
   The DNS query message goes into a UDP segment with destination port 53 (DNS server).
   The UDP segment is then placed in an IP datagram with destination IP address `68.87.71.226` (the DNS server address from the DHCP ACK message).

2. The resulting Ethernet frame is to be sent to the gateway router in Bob's school network.
   Bob's laptop knows the IP address of the school's gateway router from the DHCP ACK message, but not its MAC address, so it uses the **ARP protocol**.

3. Bob's laptop creates an ARP query message with target IP address `68.85.2.1`, places it in an Ethernet frame with the broadcast destination address `FF:FF:FF:FF:FF:FF`, and sends it to the switch.
   The switch delivers the frame to every connected device, including the gateway router.

4. The gateway router receives the frame on its school-network interface, finds the target IP address `68.85.2.1` in the ARP message, and sees that it matches its own interface's IP address.
   So the gateway router prepares an **ARP reply containing the MAC address** corresponding to `68.85.2.1`.
   It puts the reply in an Ethernet frame addressed to the laptop's MAC address and sends it to the switch, which delivers it to the laptop.
5. Bob's laptop receives the frame and extracts the gateway router's MAC address.
6. The laptop sends the DNS query to the switch with **the gateway router's MAC address as the destination MAC address** and **the DNS server as the IP destination address**, and the switch delivers the frame to the gateway router.

<br/>

## 6.7.3 Still Getting Started: Intra-Domain Routing to the DNS Server

1. The gateway router receives the frame and extracts the IP datagram containing the DNS query.
   The router looks up the datagram's destination address `68.87.71.226` in its **forwarding table** and determines that the datagram should be sent to a router in the Comcast network. It places the IP datagram in a link-layer frame appropriate for the link connecting the school's router to the Comcast router, and sends the frame over that link.
2. The upper-left router in the Comcast network receives the frame, extracts the IP datagram, and uses the datagram's destination address and its **forwarding table** (filled in by **BGP**, the Internet's inter-domain protocol, and by Comcast's intra-domain routing protocols such as **RIP**, **OSPF**, or **IS-IS**) to determine the output interface on which to forward the datagram toward the DNS server.
3. The IP datagram arrives at the DNS server, which extracts the DNS query message and looks up `www.google.com` in its DNS database, finding the **DNS resource record** that contains its IP address.
   The DNS server builds a DNS reply message, wraps it in a UDP segment and then a datagram, and sends it to Bob's laptop.
    - Assume the answer was cached in the DNS server, i.e. the authoritative DNS server for google.com had supplied the cached data earlier.
4. Bob's laptop extracts the IP address of `www.google.com` from the DNS message.

<br/>

## 6.7.4 Web Client-Server Interaction: TCP and HTTP

1. Bob's laptop first **creates a TCP SYN segment with destination port 80 (HTTP)**, places it in an IP datagram with destination address `64.233.169.105` (`www.google.com`), puts that in a frame whose destination MAC address is the gateway router's MAC address, and sends the frame to the switch.
2. The routers in the school network, the Comcast network, and Google's network forward the datagram containing the TCP SYN toward `www.google.com` using their forwarding tables, as in steps 14-16.
    - The forwarding table entries a router uses to send packets over the inter-domain link between Comcast and Google are determined by the BGP protocol.
3. The datagram containing the TCP SYN arrives at `www.google.com`. The TCP SYN message is **demultiplexed to the welcome socket** associated with port 80.
   A connection socket is created for the TCP connection between Google's HTTP server and Bob's laptop.
   The server **generates a TCP SYNACK segment**, places it in a datagram addressed to Bob's laptop, and then places that in a link-layer frame appropriate for the link connecting `www.google.com` to its first-hop router.
4. The datagram containing the TCP SYNACK travels through the Google, Comcast, and school networks and arrives at the Ethernet controller in Bob's laptop. The datagram is **demultiplexed to the TCP socket created in step 18**.
5. Bob's browser creates an HTTP GET message containing the URL to fetch and writes it into the socket; the message becomes the payload of a TCP segment.
   The TCP segment is placed in a datagram and delivered to `www.google.com`, as in steps 18-20.
6. The HTTP server at `www.google.com` reads the HTTP GET message from the TCP connection socket, creates an HTTP response message with the requested web page's content in its body, and sends it into the TCP socket.
7. The HTTP response message is delivered to Bob's laptop. Bob's web browser reads the HTTP response from the socket, extracts the HTML for the web page from the body, and finally displays the web page.
