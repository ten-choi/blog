# 8.9 Operational Security: Firewalls and Intrusion Detection Systems

### 8.9.1 Firewalls

A `firewall` is a combination of hardware and software that isolates an organization's internal network from the Internet at large, allowing some packets to pass and blocking others.

It lets a network administrator control access by managing the traffic flowing into and out of the network.

<p align="center"><img width="500" src="https://user-images.githubusercontent.com/76640167/218083755-bbfd6ae9-2b06-443f-b9b6-4ca04c7225a6.png" alt="Firewall"></p>

<br/>

### Goals of a Firewall

- All traffic going between the outside and the inside passes through the firewall.
- Only authorized traffic, as defined by the local security policy, is allowed through.
- The firewall itself must be immune to penetration.

<br/>

### Traditional Packet Filters

An organization typically has a gateway router connecting its internal network to its ISP.

All traffic going between the outside and the inside must pass through this router, and this is where **packet filtering** happens.

<br/>

**What filtering decisions are based on**

- IP source or destination address
    - Unfortunately, this can't stop datagrams with spoofed source addresses.
- Protocol type in the IP datagram: TCP, UDP, OSPF, etc.
- TCP or UDP source and destination ports
- TCP flag bits: SYN, ACK
    - If you filter incoming segments whose ACK bit is 0, you reject all TCP connections initiated from the outside while still allowing connections initiated from the inside.
- ICMP message type
- Different rules for datagrams leaving and entering the network
- Different rules for different router interfaces

A network administrator configures the firewall based on the organization's policy.

For example, if you don't want to accept any TCP connections except those to your public web server, you can block all TCP SYN segments except those with destination port 80 and the web server's destination address.

Firewall rules are implemented in the router with access control lists.

<br/>

### Stateful Packet Filters

A stateful filter tracks TCP connections and uses that information to make packet-filtering decisions.

By tracking all ongoing TCP connections in a connection table, a stateful filter also handles packets that a traditional packet filter would simply let through. (Without this, it couldn't stop attacks like DoS.)

For example, by observing SYN/SYNACK/ACK/FIN, it can assume a connection has already ended if it hasn't been used for 60 seconds.

<br/>

A stateful filter adds a new column to the access control list: **check connection**.

For example, suppose an attacker on the outside tries to send a forged packet into the network with TCP source port 80 and the ACK flag set to 1.

A traditional packet filter can't stop this, but a stateful filter uses the check-connection column to verify whether the incoming packet belongs to a connection in its connection table. The forged packet isn't in the table, so it gets filtered out.

<br/>

### Application Gateways

For finer-grained security, a firewall needs to combine packet filters with application gateways.

An application gateway is an application-specific server through which all application data must pass.

Multiple application gateways can run on the same host, but each gateway is a separate server with its own processes.

<br/>

<p align="center"><img width="450" src="https://user-images.githubusercontent.com/76640167/218083750-2fd7ea3d-31ca-4a3a-817f-3ec8612fac1a.png" alt="Gateway"></p>


Let's design a firewall that allows only a restricted set of internal users to Telnet out, and prevents all external clients from Telnetting in.

1. Configure the router's filter to block all Telnet connection attempts except those originating from the IP address of the application gateway.
    - This forces all outbound Telnet connections to go through the application gateway.
2. The user first sets up a Telnet session with the application gateway.
3. An application on the gateway, listening for incoming Telnet session requests, prompts the user for a user ID and password.
4. When the user enters them, the application gateway checks whether the user is allowed to Telnet out.
    - If not, the gateway terminates the connection.
    - If so, it asks the user for the name of the external host they want, sets up a Telnet connection between the gateway and the external host, and relays data from the internal user to the external host.
    - In other words, the application gateway performs not only authentication but also data relaying.

**Drawbacks**

1. A different application gateway is needed for each application.
2. There's a performance penalty, since all data is relayed through the gateway.
3. The client software must know how to contact the gateway when the user makes a request, and must be able to tell the application gateway which external server to connect to.

<br/>

### Anonymity and Privacy

What if you want anonymity: you don't want to leave your IP address with a website, and you don't want your local ISP to know you visited that site?

You can use a combination of a trusted proxy server and SSL.

1. Establish an SSL connection to the proxy, then send an HTTP request for the desired site over that connection.
2. The proxy decrypts the SSL-encrypted HTTP request and forwards the plaintext HTTP request to the website.
3. The website sends its response to the proxy, and the proxy sends the response back to the host over SSL.

However, the proxy ultimately knows everything, so it's important to use a proxy server you can trust.

<br/>

## 8.9.2 Intrusion Detection Systems

There's a need for a new kind of niche device that not only looks at the headers of passing packets but also performs deep packet inspection.

A device that raises an alert when it detects potentially malicious traffic is called an **intrusion detection system (IDS)**.

A device that filters out suspicious traffic is called an **intrusion prevention system (IPS)**.

What matters most for both is how they detect suspicious traffic, so we'll refer to both collectively as IDS systems.

<p align="center"><img width="500" src="https://user-images.githubusercontent.com/76640167/218083738-b32b455d-c9c3-421c-9e8b-be449923b355.png" alt="IDS"></p>


An organization may deploy multiple IDSs. They work together: when suspicious traffic is detected, it's reported to a central IDS processor, and the network administrator is alerted.

The figure above shows a network divided into a high-security region, protected by a packet filter and an application gateway and monitored by IDSs, and a lower-security region that uses only a packet filter and an IDS.

Because an IDS has to compare each passing packet against tens of thousands of signatures, it requires a lot of processing. So IDSs are placed further inside the network, where each one only has to observe a fraction of the total traffic.

<br/>

### Signature-Based Systems

A signature-based IDS maintains an extensive database of attack signatures.

Each signature is a set of rules pertaining to an intrusion activity.

A signature may simply be a list of characteristics of a single packet, or it may relate to a series of packets.

Network administrators can customize signatures and add them to the database.

A signature-based IDS reads every passing packet and compares it against the signatures in its database.

If a packet matches a signature in the database, it raises an alert.

However, this approach can't defend against new attacks, and performance suffers because every packet must be compared against the database.

<br/>

### Anomaly-Based IDS

It builds a traffic profile as it observes traffic.

It then looks for packet streams that are statistically unusual, such as an abnormally high rate of ICMP packets or a sudden spike in port scans and ping messages.
