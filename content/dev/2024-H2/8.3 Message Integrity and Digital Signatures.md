# 8.3 Message Integrity and Digital Signatures

### Message integrity

1. Did the message really come from the claimed source?
2. Was the message altered on its way?

<br/>

## 8.3.1 Cryptographic Hash Functions

<p align="center"><img width="500" src="https://user-images.githubusercontent.com/76640167/217287702-32d4aaf1-c3c3-4bba-aaf9-e13590ddf6e6.png" alt="Hash algorithm"></p>

A hash function takes an input m and computes a fixed-size string H(m), called a hash.

With a cryptographic hash function, it's computationally infeasible to find two different messages x and y such that `H(x) = H(y)`.

In other words, if (m, H(m)) is the original message and the hash the sender computed for it, an intruder can't forge another message y with the same hash value as the original.

<br/>

Simple checksums like the Internet checksum make it easy to produce the same value, so they're far too weak to use as cryptographic hash functions.

<br/>

### MD5, SHA

The MD5 hash algorithm is widely used today.

1. Padding step
    - Append a single 1 to the message, then enough 0s so that the message length meets the required block-length condition.
2. Append step
    - Append the message length before padding, as a 64-bit value
3. Accumulator initialization
4. Loop step
    - Split the message into 16-word blocks and process them in 4 rounds.

The SHA algorithm uses principles similar to those used in MD4 and is widely used.

<br/>

## 8.3.2 Message Authentication Code (MAC)

### Achieving message integrity

1. The sender creates message m and computes the hash H(m).
    - Something like SHA is used here.
2. The sender appends H(m) to m to create the extended message (m, H(m)) and sends it to the receiver.  
   (From the receiver's side, it looks like (m, h).)
3. The receiver, having received (m, h), computes H(m) and, if it equals h, concludes everything is fine.

The catch: if an intruder sends (m', H(m')) while claiming to be the sender, it passes the steps above, and the receiver can't tell the message is illegitimate.

<br/>

### Message integrity with an authentication key

<p align="center"><img width="500" src="https://user-images.githubusercontent.com/76640167/217287697-14b03fb4-a2f7-4ada-8a7e-4a77a8f914f0.png" alt="MAC"></p>

To verify the sender, the sender and receiver must share an **authentication key** (a secret key) in the form of a bit string.

1. The sender creates message m, concatenates it with the authentication key s to form m+s, and computes H(m+s).
   - H(m+s) is called the **message authentication code** (MAC — not to be confused with the MAC in the link layer).
2. The sender sends (m, H(m+s)). (From the receiver's side, it looks like (m, h).)
3. When the receiver gets (m, h), it computes H(m+s) and, if the value equals h, concludes everything is fine.

A message authentication code doesn't require a complex encryption algorithm.

The most widely used MAC standard, used with MD5 or SHA, is HMAC.

To distribute the authentication key to the communicating entities, a network administrator can configure each router directly, or the key can be encrypted with each router's public key and sent over the network.

<br/>

## 8.3.3 Digital Signatures

In the digital world, we want to indicate who owns a document or show that someone agrees with its contents, and **digital signatures** serve exactly that purpose.

A signature must be able to prove that the person actually signed it, and that only that person could have signed the document.

Public key encryption, with its separate private and public keys, works well for digital signatures. (No one else can sign with your private key.)

<br/>

### **Scenario**

1. The signer wants to sign document m.
2. The signer creates K(m) with their private key. That's the digital signature.
   - Since the digital signature K(m) **is created with the signer's private key, only the signer can create it.**
3. Anyone who receives the digital signature K(m) can use the signer's public key to recover the original m.
   - In other words, **it's verified that the signature was made by the signer who owns the public key**.
   - If someone tampered with the document along the way to create m', it won't match the original m, so it can be identified as invalid. In other words, message integrity can be verified.

The reason you can encrypt with your private key first and decrypt with the public key is that `m^ed mod n = m^de mod n = m mod n`.

Encrypting and decrypting m itself is computationally expensive.

A hash algorithm solves this.

That is, compute a fixed-length fingerprint of m, H(m), and then compute K(H(m)) to reduce the computational load.

<br/>

### Signer scenario

<p align="center"><img width="500" src="https://user-images.githubusercontent.com/76640167/217287692-f4cb6f71-268c-4e63-bbf3-e9585238217f.png" alt="Signer"></p>

1. Use a hash algorithm to turn message m into a fixed-length H(m).
2. Encrypt H(m) with your private key.
3. Send (m, K(H(m))).

<br/>

### Receiver scenario

<p align="center"><img width="500" src="https://user-images.githubusercontent.com/76640167/217287687-ae074dd6-8ec7-4444-8b3c-d9bbed130fbe.png" alt="Receiver"></p>

1. Receive (m, K(h)) from the signer.
2. Decrypt K(h) with the signer's public key to get h.
3. Run m through the hash algorithm to get H(m) and check that it matches h.

<br/>

### MAC vs. digital signatures

Digital signatures are a heavier technology than MACs because they require a public key infrastructure with certification authorities.

Many protocols use MACs.

<br/>

### Public key certification

With digital signatures, there has to be a guarantee that a public key belongs to a specific entity. (This is used in many secure networking protocols, including IPsec and TLS.)

<p align="center"><img width="500" src="https://user-images.githubusercontent.com/76640167/217287677-cc52a14c-bb39-4d05-8204-5f8c55750d55.png" alt="Why public key certification is needed"></p>

An intruder in the middle sends a message claiming to be the signer, and includes their own public key as the public key.

The receiver will decrypt the message with the intruder's public key and wrongly conclude the signature was made by the signer.

<br/>

In other words, to use public key cryptography, you have to verify that what you think is the signer's public key really belongs to the signer.

<br/>

<p align="center"><img width="500" src="https://user-images.githubusercontent.com/76640167/217287665-97222fd0-2638-4a7a-9cc2-76c893dc97ab.png" alt="Public key certification"></p>

Guaranteeing which entity (signer) a public key belongs to is generally the job of a CA (Certification Authority).

The CA verifies identities and issues certificates.

1. The CA verifies that an entity (a person or a router) really is who it claims to be.
   - There's no mandated method for this; you have to trust that the CA performs rigorous identity verification in an appropriate way.
2. Once the CA has verified the identity, it creates a certificate that binds the entity's public key to its identity.
   - The certificate is signed by the CA.
