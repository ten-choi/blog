# 5.7 Network Management with SNMP and NETCONF/YANG

What is `network management`?

<br/>

[Saydam 1996] gives a nicely put, one-sentence definition:

> Network management includes the deployment, integration, and coordination of the hardware, software, and human elements  
> to monitor, test, poll, configure, analyze, evaluate, and control the network and element resources  
> to meet the real-time, operational performance, and Quality of Service requirements at a reasonable cost.

<br/>

Out of this broad definition, this section covers only the basics of network management,  
that is, the architecture, protocols, and data that a network administrator uses to do the job.

<br/>
<br/>

## 5.7.1 The Network Management Framework

The figure below shows the key components of network management.

<br/>

<p align="center"><img width="600" alt="Components of network management" src="https://user-images.githubusercontent.com/86337233/213753123-ebbbe96e-5b67-41aa-9d30-058924368adb.png">

<br/>
<br/>

### Managing server

> The managing server is an application, running in a centralized network management station in the  
> `network operations center (NOC)`, that typically **interacts with** `network managers (humans)`.

- It's the locus of network management activity, controlling the collection, processing, analysis, and dispatching of network management information.
- This is where actions are initiated to configure, monitor, and control the network's managed devices.
- A network can have several managing servers.

<br/>

### Managed device

> A managed device is a piece of network equipment (including its software) residing on the managed network.

- e.g., hosts, routers, switches, middleboxes, modems, thermometers, and other network-connected devices
- These devices have many **manageable components** (e.g., a network interface card is a component of a host or router)  
  and **configuration parameters for these hardware and software components** (e.g., an intra-AS routing protocol such as OSPF).

<br/>

### Data

> Each managed device has data associated with it, also known as its "`state`."

<br/>

Types of data:

- `Configuration data`
    - Device information explicitly assigned and configured by the administrator on the device's interfaces
    - e.g., an IP address or interface speed


- `Operational data`
    - Information the device acquires as it operates
    - e.g., the list of immediate neighbors in the OSPF protocol


- `Device statistics`
    - Status indicators and counters updated as the device operates
    - e.g., the number of packets dropped on an interface, or the device's cooling fan speed

<br/>

The managing server maintains not only data about the network as a whole, such as the network topology,  
but also **copies of the configuration, operational, and statistics data of the managed devices**.

<br/>

### Network management agent

> A network management agent is a software process running on a managed device that communicates with the managing server.

It takes local actions on the managed device under the command and control of the managing server.

<br/>

### Network management protocol

> A network management protocol runs between the managing server and the managed devices,  
> (1) letting the managing server query the status of managed devices and  
> (2) take actions on those devices via their agents.

<br/>

Agents can use the network management protocol to inform the managing server of exceptional events.  
(e.g., component failures or violations of performance thresholds)

<br/>

> 💡 The network management protocol does not itself manage the network.

Instead, it provides capabilities that let network administrators manage (monitor, test, poll, configure, analyze, evaluate, and control) the network.

<br/>

---

<br/>

There are three commonly used ways for a network operator to manage the network using the components above.

<br/>

### 1️⃣ CLI

> A network operator can send commands directly to a device through a `Command Line Interface (CLI)`.
>

These commands can be  
(1) typed directly on the managed device's console, if the operator is physically in the same place as the device, or  
(2) delivered over a Telnet or SSH (secure shell) connection to the managed device.

<br/>

This approach tends to be error-prone, and it's hard to automate or to manage large networks efficiently this way.

<br/>

### 2️⃣ SNMP/MIB

> In this approach, the network operator uses `SNMP (Simple Network Management Protocol)`  
> to query or set the data in a device's `MIB (Management Information Base)`.

<br/>

Some MIB data is device- and vendor-specific,

while other MIB data (e.g., the number of IP datagrams discarded at a router due to errors in the IP datagram header, or the number of UDP segments received at a host)  
**is device-agnostic, abstract, and general**.

<br/>

Typically, a network operator

1. uses this approach to query and monitor operational state and device statistics, and then
2. uses the command line interface to actually control and configure devices.

<br/>

> 💡 Both CLI and SNMP/MIB manage devices **individually**.

Even with `SNMP/MIB`, configuring devices and managing large networks remains difficult.

<br/>

This led to the most recent approach to network management, using `NETCONF` and `YANG`.

<br/>

### 3️⃣ NETCONF/YANG

> This approach takes a more abstract, network-wide, holistic view of network management,  
> with a much stronger emphasis on configuration management, including specifying correctness constraints and providing atomic management operations across multiple devices.

- `YANG`: a data modeling language used to model configuration and operational data
- `NETCONF protocol`: used to communicate YANG-compatible actions and data to/from/among remote devices

<br/>
<br/>

## 5.7.2 SNMP and the MIB

### SNMP

> `SNMPv3 (Simple Network Management Protocol version 3)` is used to convey network-management control and information messages  
> between a managing server and an agent executing on behalf of that managing server.

<br/>

#### Request-response mode

This is the most common way SNMP is used.

1. The SNMP managing server sends a `request` to the agent
    - Requests are typically used to query (retrieve) or modify (set) MIB object values associated with a managed device.
2. The SNMP agent receives it, performs the operation, and sends a `reply` to the request.

<br/>

#### Trap message

The second common use of SNMP is  
for an agent to send an unsolicited message, known as a `trap message`, to a managing server.

Trap messages are used to notify a managing server  
of an exceptional situation (e.g., a link interface going up or down) that has changed MIB object values.

<br/>

---

<br/>

The table below is for SNMPv2, which defines seven types of messages, generally known as `PDUs (Protocol Data Units)`.

<br/>

<p align="center"><img width="760" alt="SNMPv2 PDU types" src="https://user-images.githubusercontent.com/86337233/213753140-ac78f753-0be9-4df6-ba9e-4642edef2460.png">

<br/>
<br/>

- The `GetRequest`, `GetNextRequest`, and `GetBulkRequest` PDUs are all  
  **sent from a managing server to an agent** to request the value of one or more MIB objects in the agent's managed device.
    - They differ in the granularity of their data requests.
    - The agent responds with a `Response` PDU containing the object identifiers and their associated values.


- The `SetRequest` PDU is used by a managing server to set the value of one or more MIB objects in a managed device.
    - The agent replies with a `Response` PDU carrying the "noError" error status to confirm that the value has indeed been set.


- `SNMPv2-Trap` is the trap message and is generated asynchronously.
    - That is, it's generated not in response to a received request, but when an event occurs for which the managing server requires notification.
    - A received trap request requires no response from the managing server.

<br/>

<br/>

> Although SNMP PDUs can be carried by many different transport protocols, **they are typically carried in the payload of a UDP datagram**.

<br/>

However, UDP is an **unreliable** transport protocol,  
so there's no guarantee that a request, or its response, will reach its intended destination.

<br/>

So, as described below, the `request ID field` can be used by the managing server to detect lost requests or replies.

- The request ID field of the PDU is used by the managing server to number its requests to an agent.
- The agent's response takes its request ID from that of the received request.

<br/>
<br/>

### MIB

MIB objects are specified in a data description language known as `SMI (Structure of Management Information)`,  
*a rather oddly named component of the network management framework whose name gives no hint of its functionality.*

`SMI` refers to the structure of management information in `SNMP` (the protocol for carrying management information for network management),  
and it is **a collection of general rules for defining MIB objects**.

<br/>

---

<br/>

The `MIB` is **a large, structured collection of management information about network-managed resources**.

Earlier we learned that in SNMP/MIB-style network management,  
**a managed device's operational state data is represented as objects gathered into that device's MIB**.

<br/>

A MIB object might be information such as:

- The number of datagrams discarded at a router due to errors in the IP datagram header
- A **counter** of the number of carrier-sense errors on an Ethernet interface card
- **Descriptive information** such as the version of the software running on a DNS server
- **Status information** such as whether a particular device is functioning correctly
- **Protocol-specific information** such as a routing path to a destination, and so on.

<br/>

Related MIB objects are gathered into MIB modules.

<br/>
<br/>

## 5.7.3 The Network Configuration Protocol (NETCONF) and YANG

### NETCONF

The `NETCONF protocol` operates between the managing server and the managed network devices, providing messaging to

1. retrieve, set up, and modify configuration data on managed devices,
2. query operational data and statistics on managed devices, and
3. subscribe to notifications generated by managed devices.

<br/>

To control a managed device, the managing server sends it **configurations in the form of structured XML documents**, which are then activated on the device.

- NETCONF uses a `remote procedure call (RPC) paradigm`.
- Protocol messages, encoded in XML, are exchanged between the managing server and the managed device  
  over a **secure, connection-oriented session**, such as the `TLS (Transport Layer Security) protocol` over TCP.

<br/>

e.g., the NETCONF `<get>` command

This command lets the server learn about the device's configuration.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<rpc message-id="101"
     xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
    <get/>
</rpc>
```

<br/>

---

<br/>

Below is an example NETCONF session.

<br/>

<p align="center"><img width="520" alt="NETCONF" src="https://user-images.githubusercontent.com/86337233/213753150-51b2a371-d411-44a2-bba2-98cd5f379c0a.jpg">

<br/>
<br/>

1. The managing server establishes a secure connection with the managed device.


2. Once the secure connection is established, the managing server and managed device exchange `<hello>` messages,  
   declaring any additional "capabilities" that supplement the base NETCONF specification.


3. Interactions between the managing server and the managed device take the form of remote procedure calls using `<rpc>` and `<rpc-reply>` messages.
    - These messages are used to retrieve, set, query, and modify device configuration data, operational data, and statistics, and to subscribe to device notifications.


4. The session is closed with a `<close-session>` message.

### YANG

> `YANG` is the **data modeling language** used to precisely specify the structure, syntax, and semantics of the network management data used by NETCONF.

All YANG definitions are contained in modules, and an XML document describing a device and its capabilities can be generated from a YANG module.
