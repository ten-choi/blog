# 7.5 Mobility Management: Principles

<br/>

> 💡 Mobile device = a node that changes its point of attachment to the network over time

<br/>

# 7.5.1 Device Mobility: A Network-Layer Perspective

## The spectrum of mobility from the network layer's point of view

When a physical mobile device moves its point of attachment to the network, it raises different problems for the network layer **depending on how active the device is while it moves**.

<br/>

<p align="center"><img width="910" alt="Mobility spectrum" src="https://user-images.githubusercontent.com/86337233/216779475-b016ac83-e675-4ca7-aa9a-3abe4ee3771b.png">

<br/>
<br/>

### (a) Device mobility between access networks, powered off while moving

This is the user who physically moves between networks but turns the device off while moving.

While powered on, the device is attached to a single network and stays put, so from a networking perspective it isn't moving, i.e., it isn't `mobile`.

<br/>

### (b) Device mobility within a single wireless access network

The device can physically move but stays connected to the same access network.

From the network layer's perspective, this device isn't mobile either.

<br/>

And if the device stays associated with the same 802.11 AP or LTE base station, it isn't mobile from the link layer's perspective either.

<br/>
<br/>

_This is where device mobility starts to matter from a networking perspective._

### (c) Device mobility within a single provider's network, maintaining ongoing connections

1. The mobile device keeps its higher-level connections (such as TCP) and keeps sending and receiving IP datagrams
2. while it changes access networks (802.11 WLAN or LTE cell).

<br/>

Here the network must provide `handover` as the device moves between WLANs or LTE cells.  
(Handing responsibility for forwarding datagrams from one AP/base station to another.)

<br/>

### (d) Device mobility across multiple provider networks, maintaining ongoing connections

This is the case where the mobile device roams across multiple providers' networks.

The providers have to cooperate on handover, which makes the handover procedure considerably more complex.

<br/>
<br/>
<br/>

# 7.5.2 Home Networks and Roaming on Visited Networks

We learned earlier that every cellular user has a "home" — the provider they subscribe to —  
and that the `HSS (Home Subscriber Service)` stores various information about subscribers, such as:

- Which services the subscriber can access
- Encryption keys used for communication
- Billing and charging information

<br/>

> When a mobile device connects to a cellular network other than its home network,  
> the device is said to be `roaming` on a `visited network`.

This requires coordination between the home network and the visited network.

<br/>

The idea that `a mobile device has a home network` brings two important advantages:

1. The home network provides a single place where information about the device can be found.
2. It can serve as a **coordination point** for communicating with a roaming mobile device.

<br/>
<br/>
<br/>

# 7.5.3 Direct and Indirect Routing to/from a Mobile Device

The elements of a mobile network architecture are shown below.

Let's use them to look at the challenge faced by a host connected to the Internet.  
(The fundamental problems of supporting device mobility, and the basic solutions, apply equally to cellular networks and the Internet.)

<br/>

<p align="center"><img width="700" alt="Elements of a mobile network architecture" src="https://user-images.githubusercontent.com/86337233/216780033-bd92e6d4-685c-4ba8-a556-f51b723e5406.png">

<br/>
<br/>

The host is called the `correspondent`,  
and it wants to communicate with a mobile device that is either in its home network or roaming on a visited network.

<br/>

We assume every mobile device has a unique identifier.

- In a 4G LTE cellular network, this identifier is the `IMSI (International Mobile Subscriber Identity)` and the associated phone number,  
  stored on the SIM card.
- For an Internet user, the identifier would be a permanent IP address in the home network's address range, as in the Mobile IP architecture.

<br/>
<br/>

There are three basic approaches a network architecture can take to make sure datagrams sent by the correspondent reach the mobile device.

The latter two are the ones actually adopted in practice.

- Leveraging the existing IP address infrastructure
- Indirect routing to the mobile device
- Direct routing to the mobile device

<br/>
<br/>

## 1️⃣ Leveraging the Existing IP Address Infrastructure

### How it works

The simplest way to route to a mobile device in a visited network is to use the `existing IP addressing scheme`.

1. The `visited network` advertises the mobile device's permanent 32-bit IP address,  
   telling other networks it has a route that can be used to forward datagrams to that device.
    - An `ISP` advertises routes to destination networks via `BGP` by listing the CIDRized address ranges of the networks it can reach.
    - Here, by advertising a highly specific address, the visited network can **tell every other network that a particular mobile device is in its network.**


2. Neighboring networks **propagate this information across the network** using the normal BGP procedures for updating routing information and forwarding tables.

<br/>

### Advantages

No changes to the network-layer infrastructure are needed at all.

Other networks know where the mobile device is,  
and since forwarding tables direct datagrams to the visited network, datagrams can easily be routed to the device.

<br/>

### Disadvantages

Scalability.

Network routers would have to maintain forwarding table entries for potentially billions of mobile devices,  
and update a device's entries every time it roams to another network.

<br/>

### The alternative

A more practical approach, and the one actually adopted, is  
to push `mobility management functionality` out of the network core to the **network edge**, via the mobile device's home network.

<br/>

The `MME`, the mobility management entity in the mobile device's home network, can track the visited network where the device is located.  
(This information may live in the `HSS` database.)

Updating which network the mobile device is in requires a protocol that runs between the visited network and the home network.

<br/>

The mobile device needs an `IP address in the visited network`.

Options include  
(1) a permanent IP address associated with the mobile device's home network,  
(2) a new address allocated from the visited network's address range, or  
(3) an IP address provided via NAT.

- In cases (2) and (3), the mobile device has a temporary identifier (the newly assigned IP address) in addition to the permanent identifier stored in the home network's HSS.
- With a NAT address,  
  datagrams headed to the mobile device reach the visited network's NAT gateway router, go through NAT translation, and are then delivered to the device.

<br/>
<br/>

*So how does a `datagram` find its way to the mobile device?*

Since **only the home network's HSS knows where the mobile device is** — not every router in the network —  
simply putting the device's permanent address as the datagram's destination won't work.

The solutions to this are `direct routing` and `indirect routing`.

<br/>
<br/>

## 2️⃣ Indirect Routing to the Mobile Device

In `indirect routing`, the correspondent doesn't know whether the mobile node is in its home network or a visited network;  
**it simply sets the datagram's destination address to the mobile node's permanent address and sends it into the network.**

In other words, the sending correspondent doesn't need to know the mobile device's current location, which gives the correspondent complete transparency with respect to mobility.

<br/>

### Rerouting through the home network

<p align="center"><img width="700" alt="Indirect routing" src="https://user-images.githubusercontent.com/86337233/216779484-23edff49-e8d4-4f43-b5ab-5acf67f50262.png">

<br/>
<br/>

1. The `datagram` is delivered to **the mobile device's home network**.


2. (1) The `home network gateway` intercepts the datagram, consults the `HSS` to determine the visited network where the mobile device is, and  
   (2) forwards the datagram to the visited network's `gateway router`.
    - `HSS`: interacts with visited networks to track the mobile device's location and manages the home network's gateway router.
    - `Gateway router`: watches for arriving datagrams addressed to devices whose home is this network but which are currently in a visited network.


3. The visited network's `gateway router` forwards the datagram to the mobile device.
    - If NAT translation is used, the visited network's gateway router performs it.

<br/>
<br/>

The two goals below can be met by having **the home network gateway encapsulate the correspondent's original datagram** inside a larger datagram.

- The `home network gateway` must forward the arriving datagram to the `visited network's gateway router`.
- It's better for the receiving application not to notice that the datagram was forwarded through the home network,  
  so **it's desirable to leave the correspondent's datagram intact.**

<br/>

The larger datagram is delivered to the addressed gateway router in the visited network,  
which then decapsulates it, **recovers the original datagram from inside the larger one, and forwards it to the mobile device.** (This happens in step 3 above.)

<br/>

---

<br/>

> Now consider the mobile device sending a datagram to the correspondent.

In the context of the figure, the mobile device has to send datagrams through the visited gateway router so it can perform NAT translation,  
so how does the visited gateway router deliver the datagram to the correspondent?

<br/>

There are two options here (4a and 4b), shown below.

<br/>

<p align="center"><img width="700" alt="Indirect routing 2" src="https://user-images.githubusercontent.com/86337233/216779488-751ef052-38f3-41ad-a08c-2b5476654d22.png">

<br/>
<br/>

- 4a: The datagram can be tunneled back to the home gateway router and forwarded from there to the correspondent.
- 4b: The datagram can be forwarded directly from the visited network to the correspondent. (`local breakout`)

<br/>

### Network-layer functionality needed to support mobility

> ✅ Mobile-device-to-visited-network protocol

The `mobile device` must **associate** with the `visited network`, and likewise disassociate when it leaves the visited network.

<br/>

> ✅ Visited-network-to-home-network HSS registration protocol

The `visited network` must register the mobile device's location with the `home network's HSS`,  
and use the information obtained from the HSS to perform **device authentication**.

<br/>

> ✅ Datagram tunneling protocol between the home network gateway and the visited network gateway router

The sending side **encapsulates** the correspondent's original datagram inside a new datagram and forwards it to the destination.

On the receiving side, the gateway router performs **decapsulation and NAT translation** and forwards the original datagram to the mobile device.

<br/>

### The triangle routing problem

Indirect routing is inefficient because  
datagrams addressed to the mobile device **must first go to the home network and only then to the visited network**,  
even when a much more efficient route exists between the correspondent and the roaming mobile device.

<br/>
<br/>

## 3️⃣ Direct Routing to the Mobile Device

`Direct routing` solves indirect routing's triangle routing problem, but at the cost of additional complexity.

<br/>

<p align="center"><img width="700" alt="Direct routing" src="https://user-images.githubusercontent.com/86337233/216779489-175e7cd6-5e92-4078-9642-c31c1ea54269.png">

<br/>
<br/>

- Steps 1 and 2: The correspondent first discovers the visited network where the mobile device is located.
    - This is done by querying the `HSS in the mobile device's home network`,  
      assuming the device's visited network is registered with the HSS.


- Step 3: The correspondent tunnels the datagram **directly** to the mobile device's visited network.

<br/>

### Problems

1. For the correspondent to ask the HSS for the mobile device's visited network (steps 1 and 2), a `mobile-user location protocol` is needed.


2. Additional protocol mechanisms are needed to proactively update the correspondent every time the mobile device moves.

   > When the mobile device moves from one visited network to another,  
   > how does the correspondent know it should now forward datagrams to the new visited network?

    - With `indirect routing`, this is easily solved by updating the home network HSS and changing the tunnel endpoint to the new visited network's gateway router.
    - With `direct routing`, the correspondent queries the HSS only once, at the start of the session, and has a hard time learning about later changes, so the problem isn't easy to solve.
