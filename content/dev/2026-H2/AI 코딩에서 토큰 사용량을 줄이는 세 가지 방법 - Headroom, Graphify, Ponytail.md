## 들어가며

AI 코딩 도구를 쓰다 보면 어느 순간 토큰 사용량이 눈에 들어온다. 처음에는 프롬프트를 짧게 쓰는 것으로 대응하지만, 실제로 토큰이 새는 곳은 프롬프트가 아니다. 에이전트가 읽어 들이는 **로그와 도구 실행 결과**, 관련 코드를 찾느라 뒤지는 **탐색 과정**, 그리고 필요 이상으로 길게 뽑아내는 **생성 코드**에서 대부분 소비된다.

즉 토큰은 **입력, 탐색, 출력**이라는 세 지점에서 각각 새고 있고, 이 셋은 서로 다른 방법으로 줄여야 한다. 이 글에서는 그 세 지점을 하나씩 맡는 오픈소스 도구 세 가지를 소개한다.

| 도구 | 줄이는 지점 | 방식 |
|---|---|---|
| Headroom | 입력 컨텍스트 | 도구 출력과 로그를 모델에 넣기 전에 압축 |
| Graphify | 코드 탐색 | 코드베이스를 지식 그래프로 만들어 관련 코드만 조회 |
| Ponytail | 코드 생성량 | 에이전트가 최소한의 코드만 쓰도록 유도하는 스킬 |

## 1. Headroom: 입력 컨텍스트를 압축한다

Headroom은 도구 출력, 로그, 파일 내용, RAG 청크처럼 **모델에 전달되기 전의 컨텍스트를 압축하는 레이어**다. 에이전트가 테스트를 돌리거나 검색 결과를 받아 오면 그 결과가 통째로 컨텍스트에 들어가는데, 그중 현재 작업에 필요한 부분은 일부에 불과하다. Headroom은 이 결과에서 핵심 정보만 남기고 나머지를 걷어낸다.

몇 가지 특징을 짚어 보면 다음과 같다.

- 라이브러리, 프록시, MCP 서버 세 가지 형태로 붙일 수 있어 기존 에이전트 구성을 크게 바꾸지 않아도 된다.
- 압축은 로컬에서 수행되고, 압축을 위해 프롬프트나 파일 내용을 외부로 보내지 않는다고 밝히고 있다.
- 프로젝트 측 수치로는 코딩 에이전트에서 약 20%, JSON 형태의 출력에서는 60~95% 정도 입력 토큰이 줄어든다.

입력 토큰이 줄어드는 것만이 이점은 아니다. 불필요한 정보가 빠지면 모델이 요구사항과 오류 원인에 더 집중하게 되어, 긴 로그 속에서 핵심을 놓치는 문제도 함께 완화된다.

## 2. Graphify: 코드 탐색 범위를 줄인다

Graphify는 코드베이스를 **질의 가능한 지식 그래프**로 바꾼다. 파일, 함수, 클래스, 개념이 노드가 되고 import, 참조, 포함, 호출 관계가 엣지가 된다. 에이전트는 grep으로 파일을 넓게 훑는 대신 그래프를 따라가며 작업과 직접 관련된 코드에 도달한다.

대규모 프로젝트에서 에이전트가 토큰을 가장 많이 쓰는 순간은 "어디를 고쳐야 하는지" 찾는 단계다. 관련 없는 파일까지 읽어 들이면 토큰도 늘고, 쓸데없는 맥락 때문에 답의 정확도도 떨어진다. Graphify는 이 탐색 단계를 구조화한다.

- 임베딩 없이 그래프 구조만으로 동작하고, 에이전트가 어떤 관계를 따라 결론에 이르렀는지 근거를 인용할 수 있다.
- 각 관계에 EXTRACTED, INFERRED, AMBIGUOUS 같은 신뢰도 태그가 붙어, 코드에서 직접 추출한 관계와 모델이 추론한 관계를 구분할 수 있다.
- 코드뿐 아니라 SQL 스키마, 셸 스크립트, 아키텍처 문서까지 같은 그래프에 들어가므로 DB 테이블에서 API 핸들러, 프런트엔드 컴포넌트까지 한 번에 추적할 수 있다.

## 3. Ponytail: 불필요한 코드 생성을 억제한다

Ponytail은 코딩 에이전트에 붙이는 **오픈소스 스킬**이다. 도구라기보다 에이전트의 작업 규칙에 가깝다. 코드를 생성하기 전에 "이 코드가 정말 필요한가", "이미 코드베이스에 있지 않은가", "표준 라이브러리로 해결되지 않는가", "한 줄로 쓸 수 있지 않은가" 같은 질문을 순서대로 통과시켜 YAGNI 원칙을 강제한다.

생성 코드가 길어질수록 그 코드를 검토하고, 수정하고, 다시 생성하는 데 드는 토큰도 함께 늘어난다. 그래서 출력 토큰 절감은 생성 시점 한 번으로 끝나지 않고 이후 리뷰와 유지보수 비용까지 이어진다.

한 가지 중요한 점은 **검증, 에러 처리, 보안, 접근성은 최소화 규칙에서 명시적으로 제외**된다는 것이다. 짧게 쓰라고 해서 안전장치까지 빼는 도구가 아니다. 프로젝트 벤치마크에서는 같은 작업 기준으로 변경 라인이 절반 이상 줄고 토큰은 약 20% 줄었다고 보고한다.

## 입력, 탐색, 출력을 함께 최적화하기

세 도구는 역할이 겹치지 않는다. Headroom은 **입력 컨텍스트**, Graphify는 **코드 탐색**, Ponytail은 **코드 생성량**을 줄인다. AI 코딩 흐름의 앞단부터 뒷단까지, 토큰이 새는 지점을 각각 하나씩 맡는 조합이다.

셋을 함께 쓰면 토큰 사용량이 낮아지는 데서 그치지 않는다. 더 짧은 맥락으로도 필요한 답을 얻게 되므로, 컨텍스트 창이 꽉 차서 대화를 끊고 다시 시작하는 일이 줄어들고 응답의 정확도도 안정된다.

굳이 도입 순서를 정한다면 Ponytail이 가장 가볍다. 스킬 파일 하나를 추가하는 것이라 인프라 변경이 없다. Headroom은 프록시나 MCP 서버를 하나 세우는 작업이고, Graphify는 코드베이스 전체를 인덱싱하므로 준비 비용이 가장 크다.

## 도입 전에 확인할 것: 보안

다만 세 도구 모두 **코드와 실행 결과를 다루는 위치에 들어간다**는 점은 짚고 넘어가야 한다.

- Headroom을 프록시로 쓰면 모델로 가는 모든 요청이 그 프록시를 지난다. 압축 자체는 로컬에서 처리된다고 하지만, 무엇이 어디까지 기록되는지는 직접 확인하는 편이 좋다.
- Graphify는 코드베이스 전체를 읽어 그래프로 만든다. 그래프가 어디에 저장되고 어떤 도구가 그것을 읽는지 파악해야 한다.
- Ponytail은 프롬프트 규칙에 가까워 데이터가 밖으로 나갈 여지는 가장 적다.

내 경우 회사 업무에 도구를 들이려면 보안 검토를 거쳐 신청해야 하는 환경이라, 회사 프로젝트에 적용할지는 아직 고민 중이다. 개인 프로젝트에서 먼저 써 보고 효과와 데이터 흐름을 확인한 뒤 판단할 생각이다. 도입을 검토한다면 토큰 절감 수치보다 **데이터가 어디를 거쳐 어디에 남는지**를 먼저 보길 권한다.


개인적인 프로젝트에서 써본결과 어느정도의 절감효과는 보인다 다만. 쓰다보면 헤드룸에서 감소되는 토그 ㄴ사용률이 높았는데  보안적으로는 사내에서 검토단계의 툴이기때문에 아쉽다.
