## 들어가며

이제는 AI에게 코드를 붙여 넣으며 확인을 받지않는다.
AI 에이전트 도구를 터미널에서 CLI로 쓰는 방식이 당연시 되었다.
CLI로 쓰다보면 처음엔 터미널 하나로 쓰다가 슬슬 불편해지면 터미널 3개쯤을 각각 실행을 돌리고
이러다보면 오케스트레이션 툴을 찾아서 쓰게된다. 
처음에는 `지인의 추천으로 herdr`를 썼다. 
`herdr`가 필요한 작업을 직접 지시하고 빠르게 실행하는 데 초점을 둔 도구였고
그냥 편안하게 빠르다. 지금도 

 오르카(Orca)는 아무래도 좀더 여러 프로젝트를 할때 쓰기도 하고 .


두 도구 모두 AI를 단순한 질의응답 도구가 아니라 실제 작업을 수행하는 에이전트로 쓰게 해 주지만, 작업 맥락을 다루는 방식이 다르다. `herdr`는 짧고 명확한 작업을 빠르게 처리할 때 편했고, 오르카는 코드 탐색부터 수정, 테스트와 검증까지 하나의 흐름으로 이어 가기 좋았다. 

그래서 프로젝트 단위의 작업이 많아지면서 오르카로 넘어갔다.

일반적인 챗봇이 **질문에 답하는 도구**라면, 에이전트는 **목표를 받고 필요한 작업을 여러 단계로 수행하는 도구**다. 파일을 읽고, 관련 코드를 찾고, 명령어와 테스트를 실행하고, 결과에 따라 다음 행동을 고른다.

| | 챗봇 | 에이전트 |
|---|---|---|
| 입력 | 질문 + 내가 복사한 코드 | 목표 + 범위 + 제약 |
| 맥락 확보 | 내가 직접 찾아서 전달 | 저장소를 스스로 탐색 |
| 실행 | 없음 (답만 받음) | 명령어, 테스트, 수정을 직접 수행 |
| 결과 | 코드 조각 | 검증까지 거친 변경 |

그렇다면 에이전트 도구를 쓰면 구체적으로 무엇이 좋아질까? 다섯 가지로 정리해 본다.

## 1. 파일을 일일이 설명하지 않아도 된다

챗봇을 쓸 때는 관련 파일을 직접 찾아 내용을 복사해 전달해야 한다. 프로젝트가 커질수록 이 과정 자체가 하나의 일이 된다. 어떤 파일이 관련 있는지 내가 먼저 알아야 하고, 빠뜨린 파일이 있으면 답도 어긋난다.

에이전트는 저장소를 직접 탐색하면서 다음 작업을 수행한다.

- 파일 이름과 코드 내용을 검색한다.
- 함수와 클래스의 정의와 사용처를 찾는다.
- 설정 파일과 의존성을 함께 확인한다.
- 변경된 코드와 주변 구현을 비교한다.

덕분에 개발자는 파일을 찾고 맥락을 조립하는 데 시간을 덜 쓰고, **무엇을 바꿔야 하는지와 왜 바꿔야 하는지**를 설명하는 데 집중할 수 있다.

## 2. 여러 단계를 한 번에 연결할 수 있다

실제 개발 작업은 코드 한 줄을 생성하는 것으로 끝나지 않는다. 예를 들어 버그를 고치는 과정은 다음처럼 이어진다.

1. 오류가 발생한 위치를 확인한다.
2. 관련된 호출 흐름과 설정을 조사한다.
3. 원인을 가설로 세운다.
4. 코드를 수정한다.
5. 테스트나 린터를 실행한다.
6. 실패하면 결과를 보고 다시 수정한다.

에이전트는 이 과정을 하나의 작업 흐름으로 연결한다. 사용자는 매 단계마다 "이제 이 파일을 열어 봐", "테스트를 실행해 봐"라고 지시하지 않아도 된다.

이것은 명령어 입력 횟수를 줄이는 문제만이 아니다. 조사 결과와 수정 결과가 같은 작업 맥락 안에서 이어지기 때문에, 중간 정보를 다시 설명하는 비용도 줄어든다. 챗봇이라면 5번에서 실패한 테스트 출력을 다시 복사해 붙여 넣어야 했을 일이다.

## 3. 코드베이스의 규칙을 반영한 변경이 쉬워진다

좋은 에이전트는 현재 프로젝트의 구조와 관례를 먼저 읽고 작업한다. 기존 테스트 방식, 파일 배치, 네이밍 규칙, 빌드 명령어를 확인한 뒤 그에 맞춰 변경한다.

예를 들어 새 API를 추가할 때 다음을 함께 처리하도록 요청할 수 있다.

- 기존 라우팅 구조에 맞는 엔드포인트 추가
- 입력 타입과 에러 처리 작성
- 관련 단위 테스트 추가
- 포맷터와 타입 검사 실행

매번 새로운 코드를 처음부터 생성하는 것보다, **기존 코드베이스에 어울리는 변경**을 만드는 데 유리하다. 챗봇이 만든 코드를 프로젝트 스타일에 맞게 손보는 시간이 사라지는 셈이다.

## 4. 반복 작업을 위임할 수 있다

에이전트의 강점은 사람이 하기 싫어하는 반복 작업에서 특히 잘 드러난다.

- 비슷한 형식의 파일을 여러 개 변환한다.
- deprecated API를 새 API로 교체한다.
- 테스트 케이스의 기본 구조를 추가한다.
- 문서와 코드의 예제를 최신 상태로 맞춘다.
- 여러 모듈의 설정 이름을 일괄 변경한다.

사람은 반복 작업의 규칙과 예외를 설명하고, 에이전트는 많은 파일에 그 규칙을 적용한다. 이후 사람은 전체 결과를 검토하고 중요한 예외만 직접 처리하면 된다.

## 5. 개발 도구를 하나의 인터페이스로 묶을 수 있다

에이전트는 파일 시스템, 검색 도구, 터미널, 테스트 러너, 버전 관리 시스템 같은 도구를 함께 사용한다. 개발자는 각 도구를 따로 오가는 대신, 자연어로 작업의 목표를 설명한다.

> 최근 로그인 관련 변경을 확인하고, 실패할 가능성이 있는 부분을 찾아 테스트를 추가한 뒤 전체 테스트를 실행해 줘.

이 요청에는 코드 검색, 변경 사항 확인, 테스트 작성, 테스트 실행이 모두 들어 있다. 에이전트는 필요한 도구를 골라 순서대로 실행하고, 작업 결과를 요약한다.

## 자동화가 곧 신뢰를 뜻하지는 않는다

에이전트가 코드를 직접 읽고 실행할 수 있다는 점은 장점이면서 위험 요소이기도 하다. 잘못된 가설을 세운 뒤 여러 파일을 연쇄적으로 수정할 수 있고, 테스트가 부족하면 잘못된 변경을 정상으로 판단할 수도 있다.

특히 다음 작업은 반드시 사람의 검토가 필요하다.

- 인증과 권한 처리
- 결제와 금전 계산
- 데이터베이스 스키마와 데이터 마이그레이션
- 개인정보와 보안 설정
- 운영 환경에 직접 영향을 주는 명령어

에이전트에게 권한을 줄수록 작업 범위는 작게 제한하는 편이 좋다. 먼저 읽기와 분석만 허용하고, 변경이 필요하면 diff를 확인한 뒤 적용한다. 코드 변경 후에는 테스트, 타입 검사, 린터를 실행하고 결과를 직접 확인한다.

## 에이전트를 잘 쓰는 방법

"알아서 해 줘"라고만 말하는 것보다 다음 네 가지를 명확히 전달하는 편이 좋다.

1. **목표**: 무엇을 해결해야 하는가?
2. **범위**: 어떤 파일이나 모듈만 다뤄야 하는가?
3. **제약**: 쓰면 안 되는 API나 유지해야 하는 규칙은 무엇인가?
4. **검증 방법**: 어떤 테스트나 명령어가 성공해야 하는가?

네 가지를 모두 담으면 요청은 이런 모양이 된다.

> `src/auth` 안의 만료된 토큰 처리 오류를 수정해 줘. 공개 API는 바꾸지 말고, 관련 테스트를 먼저 확인해. 수정 후 타입 검사와 인증 테스트를 실행하고 변경 내용을 요약해 줘.

이렇게 요청하면 에이전트가 탐색할 범위와 완료 조건이 분명해진다. 결과적으로 불필요한 변경과 검토 비용이 줄어든다.

반대로 챗봇이 더 나은 경우도 있다. 코드베이스와 무관한 개념 질문, 짧은 스니펫 하나를 확인하는 일, 아직 프로젝트가 없는 설계 초기 단계에서는 에이전트가 탐색에 쓰는 시간과 토큰이 오히려 낭비다. 도구를 고르는 기준은 "얼마나 똑똑한가"가 아니라 **작업이 저장소 맥락을 필요로 하는가**다.

## 결론

AI 에이전트 도구의 가장 큰 장점은 코드를 잘 생성한다는 데만 있지 않다. **탐색, 판단, 수정, 실행, 검증으로 이어지는 개발 작업 전체를 연결한다는 점**에 있다.

그래서 에이전트는 사람을 대신하는 자동 코더라기보다, 프로젝트를 함께 조사하고 반복 작업을 수행하는 개발 도구에 가깝다. 사람은 목표와 제약, 신뢰 경계를 정하고 에이전트는 그 안에서 실행한다.

결국 생산성 향상은 "AI에게 얼마나 많이 맡겼는가"가 아니라, **어떤 작업을 맡기고 어디에서 사람이 최종 판단하는가**에 달려 있다.
