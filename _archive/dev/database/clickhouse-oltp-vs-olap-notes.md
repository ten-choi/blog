> MySQL만 쓰다가 ClickHouse를 처음 만나면 "이게 왜 이렇게 빠르지?"와 "UPDATE가 왜 이래?"를 동시에 겪게 돼.
>
> 그 답은 전부 **OLTP와 OLAP은 목적 자체가 다르다**는 한 문장에서 출발해.

# ClickHouse 입문 — OLTP vs OLAP

## 1. 두 세계의 목적부터 다르다

### OLTP — 지금 이 순간의 거래를 처리한다

**OLTP(Online Transaction Processing, 온라인 트랜잭션 처리)**는 실시간으로 사용자의 데이터를 **생성하고, 갱신하고, 조회하는** 데이터 처리 방식이야.

- 주문 넣기, 회원 정보 수정, 내 주문 내역 보기 — 우리가 매일 쓰는 서비스의 백엔드
- 우리가 아는 **RDB(MySQL/InnoDB, PostgreSQL, Oracle)의 주 무대**라고 보면 돼
- 특징: **한 번에 소수의 행**을 건드리고, 그 행의 **모든 컬럼**이 필요하며, **1ms 단위의 응답**과 **완전한 ACID 트랜잭션**이 생명

### OLAP — 쌓인 데이터를 다각도로 분석한다

**OLAP(Online Analytical Processing, 온라인 분석 처리)**는 대량의 데이터를 여러 차원(시간, 지역, 상품 등)에서 **빠르고 다각도로 분석**해서 비즈니스 의사결정을 돕는 기술이야.

- "지난 90일간 지역별 일 매출 추이", "상품 카테고리별 전환율" 같은 질문에 답하는 쪽
- **ClickHouse**가 바로 이 판의 대표 선수
- 특징: **수억 행을 훑되**, 그중 **소수의 컬럼만** 읽고, 집계 결과 하나를 돌려준다

> 💡 감을 잡는 요령: ClickHouse도 SQL을 쓰니까, **"적은 컬럼만 골라서 RDB 하던 짓 똑같이 한다"**고 생각하면 얼추 맞아. 다만 밑바닥 구조가 완전히 달라서, 잘하는 것과 못하는 것이 정반대일 뿐이야.

## 2. 저장 구조 — 행으로 눕히느냐, 컬럼으로 세우느냐

같은 `orders` 테이블이라도 디스크에 놓이는 모양이 다르다.

```
행 저장 (InnoDB)                 컬럼 저장 (ClickHouse)
┌────────────────────┐          ┌─────────┐ ┌─────────┐ ┌─────────┐
│ id·date·region·amt │ ← 행1    │ id 파일 │ │date 파일│ │ amt 파일│
│ id·date·region·amt │ ← 행2    │ 1       │ │ 01-01   │ │ 1000    │
│ id·date·region·amt │ ← 행3    │ 2       │ │ 01-01   │ │ 2500    │
└────────────────────┘          │ 3       │ │ 01-02   │ │  800    │
  16KB 페이지에 행이 통째로       └─────────┘ └─────────┘ └─────────┘
                                  컬럼별 파일 + 압축 블록
```

- **InnoDB**: 16KB 페이지 안에 **행이 통째로 연속** 저장 → "id=3인 주문의 모든 정보"를 페이지 한 번 읽기로 가져온다. 소수 행 × 전 컬럼에 최적.
- **ClickHouse(MergeTree)**: **컬럼마다 별도 파일**로 저장 → `SELECT sum(amt)`라면 **amt 파일 하나만** 읽으면 끝. 나머지 컬럼은 디스크에서 아예 안 건드려. 전 행 × 소수 컬럼에 최적.

컬럼 저장의 보너스가 **압축**이야. 같은 컬럼끼리 모아 놓으면 비슷한 값이 연속되니까 압축이 기가 막히게 잘 먹혀서, 보통 **5~20배**까지 줄어들어. 읽을 데이터 자체가 1/10이 되는 셈이니 그만큼 또 빨라진다.

## 3. 인덱스 — 촘촘한 B-Tree vs 성긴 스파스 인덱스

- **InnoDB의 B-Tree**는 **모든 행**을 가리킬 수 있는 촘촘한 인덱스야. "id=42인 행 하나"를 콕 집어내는 점 조회(point lookup)의 왕.
- **ClickHouse의 프라이머리 인덱스는 스파스(sparse, 성긴) 인덱스**야. 데이터를 정렬 키 순서로 쌓아 두고, **8192행(그래뉼)마다 하나씩만** 인덱스 엔트리를 남겨.

```
B-Tree:  행 하나하나에 도달하는 촘촘한 길   → "42번 행 줘" 에 강함
스파스:  8192행 단위의 이정표만 세움        → "1월~3월 구간 줘" 에 강함
```

스파스 인덱스는 "정확히 그 행이 어디냐"는 못 짚지만, **"이 범위는 이 그래뉼들 사이에 있다"**는 건 이정표 몇 개만 보고 바로 알아내. 그래서 ClickHouse는 **범위 조회 특화형**이야 — 시계열·로그 분석처럼 "기간으로 잘라서 훑는" 쿼리에 압도적으로 강한 이유가 이거야.

> ⚠️ 뒤집어 말하면, ClickHouse에서 `WHERE id = 42` 같은 점 조회는 그래뉼 하나(8192행)를 통째로 읽어야 해. **점 조회가 주력이라면 그냥 RDB를 쓰는 게 맞아.**

---

## 4. 실행 방식 — 한 행씩 vs 한 블록씩

- **InnoDB**는 기본적으로 **행 단위**로 처리해. 행 하나 읽고, 조건 평가하고, 다음 행.
- **ClickHouse**는 컬럼 값 수천 개를 **블록으로 묶어 벡터화(vectorized) 실행**하고, CPU의 **SIMD** 명령으로 한 번에 여러 값을 연산해. 집계 쿼리에서 자릿수가 다른 속도가 나오는 핵심 엔진이 이 부분이야.

```sql
-- 이런 쿼리가 ClickHouse의 홈그라운드
SELECT region, toDate(created_at) AS d, sum(amount)
FROM   orders
WHERE  d BETWEEN '2026-05-01' AND '2026-07-31'
GROUP  BY region, d;
-- 수억 행이어도: region, created_at, amount 세 컬럼 파일만 + 기간 그래뉼만 읽는다
```

## 5. 대신 포기한 것들 — UPDATE, 트랜잭션, 동시성

빠른 분석을 얻는 대가로 ClickHouse(MergeTree)는 OLTP의 미덕을 상당 부분 포기했어.

- **UPDATE/DELETE가 무겁다** — InnoDB는 해당 행만 즉시 고치면 끝이지만, MergeTree는 `ALTER TABLE ... UPDATE/DELETE`가 **비동기 뮤테이션**으로 동작하면서 **데이터 파트(part)를 통째로 다시 써**. 자주 고치는 데이터를 넣는 곳이 아니야. (수정 대신 **새 버전 행을 append**하고 `ReplacingMergeTree` 등으로 정리하는 패턴을 쓴다.)
- **트랜잭션이 사실상 없다** — 완전한 ACID를 기대하면 안 돼. 계좌 이체 같은 걸 ClickHouse에 올리면 안 되는 이유.
- **동시성의 단위가 다르다** — InnoDB는 **수천 커넥션**이 자잘한 쿼리를 던지는 걸 버티도록 설계됐고, ClickHouse는 **수십 개의 무거운 분석 쿼리**가 CPU를 나눠 쓰는 그림을 상정해.
- **데이터 모델도 반대** — RDB는 정규화가 기본이지만, OLAP은 조인을 줄이려고 **비정규화(넓은 한 방 테이블)**가 기본이야.

---

## 6. 한눈에 보는 요약표

| | OLTP (InnoDB) | OLAP (ClickHouse MergeTree) |
|---|---|---|
| 저장 단위 | 16KB 페이지, 행 연속 | 컬럼별 파일, 압축 블록 |
| 최적 쿼리 | 소수 행 × 전 컬럼 | 전 행 × 소수 컬럼 |
| 인덱스 | B-Tree, 행 단위 | 스파스, 8192행(그래뉼) 단위 |
| 실행 | 행 단위 | 블록 벡터화 + SIMD |
| 압축 | 낮음 | 5~20배 |
| UPDATE/DELETE | 즉시, 저렴 | 비동기 뮤테이션, part 재작성 |
| 트랜잭션 | 완전한 ACID | 사실상 없음 |
| 동시성 | 수천 커넥션 | 수십 쿼리 |
| 데이터 모델 | 정규화 | 비정규화 |
| 지연 목표 | 1ms | 100ms~1s |

---

## 7. 그래서 언제 뭘 쓰나

- **서비스의 원장(源帳) 데이터** — 주문, 결제, 회원: **OLTP(RDB)**. 트랜잭션과 점 조회가 생명.
- **로그·이벤트·시계열 분석, 대시보드, 리포트**: **OLAP(ClickHouse)**. 기간으로 잘라 집계하는 쿼리가 주력.
- 실무의 정석은 **둘 다** 쓰는 거야 — RDB가 거래를 받고, 그 데이터를 CDC나 배치로 ClickHouse에 흘려보내 분석은 그쪽에서 한다. 하나로 둘 다 잘하려는 순간 둘 다 어중간해져.

### 📝 한 줄 정리

> **"OLTP는 '지금 이 행 하나'를 완벽하게, OLAP은 '전체를 몇 개 컬럼으로' 빠르게 — ClickHouse는 후자에 모든 것을 건 범위 조회 특화형 컬럼 저장소다."**
