## Problem

Given an integer array `nums` and an integer `k`, return the **total number of subarrays** whose sum equals `k`.

A subarray is a **contiguous, non-empty** sequence of elements within the array.

```
Input:  nums = [1,2,3], k = 3
Output: 2      → [1,2] and [3]
```

**Constraints**
- `1 <= nums.length <= 2 * 10^4`
- `-1000 <= nums[i] <= 1000`
- `-10^7 <= k <= 10^7`

---

## How I'd explain it in an interview

### 1. Clarify first

- We need a **count**, not the subarrays themselves.
- Elements can be **negative** (this matters a lot — see below).
- `k` can be `0` or negative.
- Subarrays must be contiguous; subsequences don't count.

### 2. Why brute force fails

Try every `(i, j)` pair and sum the range → O(n²) with a running sum.
With `n = 2 * 10^4` that's ~2 * 10^8 operations — borderline, and it's not the answer the interviewer wants.

### 3. Why sliding window does **not** work here

My first instinct was a two-pointer window: extend `j`, and when `total > k` shrink from `i`.

```java
// ❌ Wrong — do not use
while (j < nums.length) {
    total += nums[j];
    while (total > k) total -= nums[i++];
    if (total == k) result++;
    j++;
}
```

Sliding window relies on **monotonicity**: adding an element must never make the sum smaller, so "too big → shrink" is a safe decision.
With negative numbers that assumption breaks:

```
nums = [1, -1, 0], k = 0
```

The correct answer is `3` (`[1,-1]`, `[0]`, `[1,-1,0]`), but the window returns `1` — and even that one is a phantom empty window. Shrinking on `total > k` throws away a left edge that a later negative would have brought back down to `k`. **Sliding window is only valid when all elements are non-negative.**

### 4. Key insight — prefix sums

Let `prefix[i]` = sum of `nums[0..i]`. Then

> `sum(nums[j+1..i]) = prefix[i] − prefix[j]`

So a subarray ending at `i` sums to `k` exactly when some earlier prefix equals `prefix[i] − k`.

That turns the question into: *"how many times have I seen the value `sum − k` before?"* — a HashMap lookup.

- `Map<prefixSum, count>` — how many times each running sum has appeared
- Seed it with `{0: 1}` — the empty prefix, so subarrays that start at index 0 are counted
- For each element: `sum += num`, then `count += map[sum − k]`, then `map[sum]++`

**Order matters**: look up first, then record. Otherwise with `k = 0` you'd match the current prefix against itself and count an empty subarray.

### 5. Walkthrough — `[1,2,3]`, `k = 3`

| num | sum | look up `sum − k` | found | count | map after            |
|-----|-----|-------------------|-------|-------|----------------------|
| –   | 0   | –                 | –     | 0     | {0:1}                |
| 1   | 1   | −2                | 0     | 0     | {0:1, 1:1}           |
| 2   | 3   | 0                 | 1     | 1     | {0:1, 1:1, 3:1}      |
| 3   | 6   | 3                 | 1     | 2     | {0:1, 1:1, 3:1, 6:1} |

## Solution

```java
class Solution {
    public int subarraySum(int[] nums, int k) {
        // key: a prefix sum seen so far, value: how many times it appeared
        Map<Integer, Integer> prefixCount = new HashMap<>();
        prefixCount.put(0, 1);  // empty prefix — required to count subarrays starting at index 0

        int sum = 0;    // running prefix sum
        int count = 0;  // answer

        for (int num : nums) {
            sum += num;


            // If a prefix equal to (sum - k) appeared before, the elements
            // *after* that point up to here sum to exactly k.
            count += prefixCount.getOrDefault(sum - k, 0);

            // Record the current prefix sum (after the lookup, not before)  결국에 이게 누적값 하는게 마이너스 역할이다 . 
            prefixCount.merge(sum, 1, Integer::sum);
        }

        return count;
    }
}
```

## Complexity

- **Time O(n)** – one pass, O(1) average per HashMap operation
- **Space O(n)** – up to `n + 1` distinct prefix sums

## Follow-ups

| Question | Answer |
|----------|--------|
| All numbers positive? | Sliding window works and drops space to O(1) |
| Return the subarrays, not the count? | Store lists of indices per prefix sum instead of counts (worst case O(n²) output) |
| Sum divisible by `k`? | LC 974 – key the map by `sum mod k` (normalize negatives) |
| Longest / shortest subarray with sum `k`? | LC 325 – store the **first** index of each prefix sum, not a count |
| Binary array, count of `1`s equals count of `0`s? | LC 525 – treat `0` as `−1`, then it's this problem with `k = 0` |

**Pattern:** *"count pairs `(j, i)` with `prefix[i] − prefix[j] = k`"* — the same HashMap-of-prefix-sums trick behind Two Sum, but over running totals.
